# Workflow Validation

Как сценарий конструктора показывает проблемы: где они берутся, чем
отличаются друг от друга и как из строки списка попасть к причине.

Устройство сценария — `docs/EDITOR_WORKFLOW.md`. Пользовательская
сторона — `docs/USER_WORKFLOW.md`. Сам расчёт готовности —
`docs/PRODUCTION_READINESS.md`, конвейер —
`docs/PRODUCTION_CALCULATION_PIPELINE.md`.

---

## 1. ВТОРОЙ ПРОВЕРКИ НЕТ

Сценарий не проверяет ничего сам. Он **раскладывает по шагам** то, что
уже посчитали существующие проверки:

```
buildGeometry           → GeometryResult.diagnostics   (Issue[])
validateProject         → Issue[]
calculateProduction     → bom.errors, bom.warnings, bom.confirmations
validateProductionReadiness → ProductionReadinessResult (8 разделов)
```

`src/app/workflow/steps.ts` берёт готовый список `Issue[]`, спрашивает у
каждого «к какому шагу ты относишься» и складывает ответы в счётчики.
Ни одного собственного правила, ни одного собственного порога, ни одной
собственной формулы там нет — и не должно появиться: два места, решающих
«изготовимо ли», рано или поздно разойдутся.

---

## 2. КАК ПРОБЛЕМА НАХОДИТ СВОЙ ШАГ

`stepOfIssue(issue)` разбирает **уже существующие** поля диагностики.
Ни `Issue.step`, ни какого-либо другого поля «для интерфейса» в домене
не заводится: домен не должен знать устройство экранов.

Разбор идёт в два приёма, в этом порядке:

1. **По пути к полю модели** — `issue.target.path`. Он точнее: путь
   `carcass.base.height` однозначно указывает на корпус, каким бы ни был
   код.
2. **По коду** — `issue.code`. Запасной разбор для диагностики движка, у
   которой пути может не быть.

| Путь / префикс кода                                                               | Шаг         |
| --------------------------------------------------------------------------------- | ----------- |
| `dimensions*`, `DIMENSION*`, `CARCASS_*`, `SHELL_*`                               | Размеры     |
| `carcass.back*`, `carcass.base*`, `BACK_WALL*`, `PLINTH*`                         | Корпус      |
| `root*`, `SECTION*`, `SPLIT*`, `HORIZONTAL*`                                      | Секции      |
| `CELL*`                                                                           | Ячейки      |
| `SHELF*`                                                                          | Полки       |
| `CONTENT*`, `ROD*`                                                                | Наполнение  |
| `facades*`, `DOOR*`, `DRAWER*`, `OPENING*`                                        | Фасады      |
| `materials*`, `settings.defaultMaterialId`, `MATERIAL*`, `EDGE*`, `GLASS*`        | Материалы   |
| остальной `carcass.*`, `COUNTERTOP*`, `OVERHANG*`, `FALSE_PANEL*`, `TOP_SECTION*` | Конструкция |

Проблема, не попавшая ни в одну строку таблицы, шага не получает — и это
правильно. Ошибки самой деталировки (`PART_*`, `INNER_VOLUME_*`)
принадлежат расчёту целиком, а не какому-то одному шагу настройки;
приписать их наугад значило бы отправить человека править не то.
Такие проблемы видны в строке состояния и на экране проверки, но
счётчик шага не увеличивают.

## 3. ЧЕТЫРЕ РАЗНЫЕ ВЕЩИ

Смешивать их нельзя: у них разные последствия и разные действия
пользователя.

| Что                       | Откуда                | Мешает выпуску                 | Что делать человеку           |
| ------------------------- | --------------------- | ------------------------------ | ----------------------------- |
| **Информация**            | `severity: 'info'`    | нет                            | ничего; это справка           |
| **Предупреждение**        | `severity: 'warning'` | нет                            | посмотреть, если важно        |
| **Требует подтверждения** | `bom.confirmations`   | нет, но результат под вопросом | уточнить правило по референсу |
| **Ошибка**                | `severity: 'error'`   | да                             | исправить                     |

Работа не блокируется предупреждением и не блокируется неподтверждённым
правилом. Блокируется только ошибкой, и только там, где блокировка
осмысленна: выпуск производственных документов. Ходить по шагам,
менять размеры и смотреть сцену можно при любом состоянии проверок.

---

## 4. NEEDS_CONFIRMATION — НЕ ПРЕДУПРЕЖДЕНИЕ

Это отдельная категория, и показывается она отдельно.

Предупреждение говорит «возможно, вы не этого хотели». Неподтверждённое
правило говорит **«мы не знаем, как правильно, и подставили значение по
умолчанию»**. Разница принципиальная: по первому изделие изготовят
правильно, по второму — как получится.

Поэтому каждый такой пункт на экране проверки раскрыт до четырёх строк
(`ProductionScreen.tsx`), и все четыре берутся из существующего
`ConfirmationItem`:

| Строка        | Поле     | Отвечает на вопрос                    |
| ------------- | -------- | ------------------------------------- |
| Правило       | `rule`   | что именно неизвестно                 |
| Применяется   | `source` | где это правило работает              |
| Влияние       | `impact` | чем это грозит результату             |
| Идентификатор | `id`     | по чему искать в `docs/UNKNOWNS.json` |

Свернуть это в одно слово «подтвердить» значило бы требовать
подтверждения, не сказав чего.

Тот же принцип действует и раньше проверки — в самом интерфейсе. Там,
где правило не подтверждено, вариант не показывается вовсе, а не
подставляется наугад:

- **обувной модуль** (`T-FILL-01`) — состава нет в модели: число
  наклонных полок, угол, шаг и крепление референсом не подтверждены;
- **число ящиков в ячейке** (`T-DRW-05`) — искусственного предела нет:
  ограничивает только то, помещаются ли фасады по высоте;
- **зазоры фасада ящика** (`T-DRW-04`) — переиспользованы зазоры дверей,
  отдельных значений для ящиков референс не дал;
- **штанга** — вариант есть в модели, но геометрия для него не строится,
  поэтому в списке наполнения его нет: пункт, который ничего не меняет
  ни на сцене, ни в деталировке, обещал бы несуществующее.

Реестр — `docs/UNKNOWNS.json`, проверяется скриптом
`scripts/check-assumptions.mjs`: каждый маркер `ASSUMPTION(<id>)` в коде
обязан иметь запись в реестре, иначе сборка не проходит.

## 5. ОТ ОШИБКИ К ПРИЧИНЕ

Строка проблемы — кнопка. Нажатие делает три вещи подряд, и все три
нужны (`goToIssue` в `App.tsx`):

```
Issue → stepOfIssue → открыть шаг → выделить объект → нужное поле на экране
```

Выделить объект мало: человек увидит подсвеченную деталь, но останется
на шаге, где её параметра нет. Открыть шаг тоже мало: он увидит нужную
панель, но не поймёт, к какому из четырёх ящиков она относится. Поэтому
сначала открывается шаг, потом выделяется объект — деталь по
`target.partId`, узел дерева по `target.nodeId`.

Работает это из обоих мест, где показываются проблемы: из строки
состояния внизу и из чеклиста готовности на экране производства.

## 6. СОСТОЯНИЕ ШАГА В ЛЕСТНИЦЕ

Счётчики из §2 превращаются в состояние шага (`stepStates`):

- есть ошибка → `error`, тон `danger`, значок `✕`;
- есть предупреждение → `warning`, тон `warning`, значок `!`;
- иначе текущий → `current`, тон `info`, значок `●`;
- иначе заходили → `visited`, тон `success`, значок `✓`;
- иначе → `pending`, тон `neutral`, значок `○`.

Цвет не единственный носитель смысла: у каждого состояния свой значок и
своё слово в доступном имени кнопки («есть ошибка», «пройден», «не
открывали») — `docs/ACCESSIBILITY.md`.

Ошибка перевешивает «текущий». Иначе шаг, на котором стоишь, выглядел бы
благополучным ровно тогда, когда на нём проблема.

**Ошибка никогда не прячется в свёрнутом разделе.** На шаге
«Конструкция» редкие настройки лежат в дополнительном разделе, но если
проблема в них — шаг помечен ошибкой в лестнице, и раздел раскрыт.
