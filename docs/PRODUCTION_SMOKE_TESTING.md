# Дымовая проверка опубликованного приложения

PROMPT 41. Что проверяется после выкладки, зачем и что означает падение.

## Purpose — зачем, если E2E уже прошли

**Успешная выкладка не доказывает, что приложение работает.**

Между зелёным прогоном и живой страницей лежит всё, чего в прогоне не
было: чужой хостинг, его заголовки, его кэш и — чаще остального —
базовый путь. Сборка под неверную базу **не падает**. Она отдаёт разметку
со ссылками, по которым ничего нет, браузер получает 404 на главный чанк,
и человек видит белый экран без единого сообщения.

Локальный набор такого не поймает никогда: там база верная по
построению. Поймать это может только проверка по живому адресу — и до
неё белый экран увидел бы пользователь, а не CI.

Проверено, что ловит: корневая сборка, отданная в подкаталоге, роняет
проверку с диагнозом «оболочка приложения осталась пустой — похоже на
неверный базовый путь».

## Это НЕ повтор набора E2E

| | Что отвечает | Когда | Сколько идёт |
| --- | --- | --- | --- |
| `chromium` (157 сценариев) | работает ли продукт | до выкладки | ~2,5 минуты |
| `production-smoke` (1 сценарий) | доехало ли выложенное | после выкладки | секунды |

Гонять функциональные сценарии второй раз значило бы тратить минуты ради
ответа, который уже получен. Здесь ищутся дефекты именно выкладки.

## Trigger

Задача `smoke` в `.github/workflows/ci.yml`, цепочкой:

```
verify  ─→  build-pages  ─→  deploy  ─→  smoke
```

Только push в ветку по умолчанию. Pull request проходит ворота, но
ничего не публикует, поэтому и проверять ему нечего.

## Target — откуда берётся адрес

Адрес не записан в проекте. Его отдаёт сама выкладка:

```yaml
deploy:
  outputs:
    url: ${{ steps.deployment.outputs.page_url }}

smoke:
  env:
    PLAYWRIGHT_BASE_URL: ${{ needs.deploy.outputs.url }}
```

Так проверяется ровно то, что опубликовано, а не то, что кто-то однажды
вписал в конфигурацию.

## Ожидание готовности

После выкладки адрес отвечает не мгновенно. Ожидание не «на всякий
случай» — у него есть условие:

`build-pages` вычисляет отпечаток сборки (имя кэша service worker'а
содержит хеш содержимого) и отдаёт его наружу. `smoke` опрашивает
`<адрес>sw.js`, пока в нём не окажется **то самое** имя. Значит доехала
именно эта версия, а не предыдущая.

Предел жёсткий: **30 попыток по 10 секунд — пять минут.** Дальше шаг
падает. Ни бесконечного опроса, ни произвольного долгого `sleep`, ни
проглоченного таймаута.

## Checks — что именно проверяется

1. **Адрес отвечает** — код ответа меньше 400.
2. **Оболочка не пустая** — у `#root` появляется содержимое. Ровно это
   отличает работающее приложение от белого экрана.
3. **Критические файлы доехали** — главный чанк `assets/index-*.js` и
   таблица стилей реально загрузились, а не «страница вернула 200».
4. **Интерфейс на месте** — сцена изделия и лестница шагов видимы.
5. **Одно настоящее действие** — правка ширины на 1234 доходит до сцены.
   Это весь путь: интерфейс → команда → домен → геометрия → сцена.
6. **Приложение осталось пригодным** — раздел «Производство» открывается
   и показывает детали.
7. **Ни одной критической жалобы** — см. ниже.

### Что считается критическим

| Событие | Реакция |
| --- | --- |
| Необработанное исключение (`pageerror`) | падение |
| Ошибка в консоли | падение |
| Неудачный запрос `.js` / `.css` / `.html` | падение |
| Ответ 4xx / 5xx | падение |
| Прерванный запрос (`ERR_ABORTED`) | пропускается: так браузер снимает ненужное |
| Значок вкладки, `apple-touch-icon`, иконки | пропускаются: видно, но работе не мешает |
| Предупреждения консоли | пропускаются |

Список исключений намеренно короткий и каждое обосновано в коде.
Прощать больше — значит перестать ловить.

## Failure — что означает падение

Падение дымовой проверки означает: **выложенная версия сломана у
пользователя**, даже если все ворота были зелёными. Разбирать нужно не
код, а выкладку — базовый путь, состав артефакта, заголовки площадки.

Маскировки нет: ни `continue-on-error`, ни `|| true`. Задача падает, и
прогон становится красным.

Восстановление — откат обычным `git revert`
(`docs/GITHUB_PAGES_DEPLOYMENT.md`), потому что предыдущая версия уже
опубликована и проверена.

## Diagnostics

При падении выгружается артефакт `production-smoke-diagnostics`:

- `playwright-report/` — отчёт по шагам сценария;
- `test-results/` — трассы и **снимки экрана** упавшего сценария.

Хранятся 7 дней. Секретов в них нет: сценарий работает в пустом браузере
на публичном адресе, а проекты живут только в его IndexedDB.

## Local reproduction

Тот же сценарий, тем же инструментом, против любого адреса:

```bash
PLAYWRIGHT_BASE_URL=https://artemu1453.github.io/FurnityreBuilder/ npm run smoke
```

Второго тестового инструмента не заводится: это отдельный проект
Playwright `production-smoke`, а не отдельная система.

## Limitations

Только настоящие.

1. **Связь с конкретной выкладкой — по содержимому, а не по коммиту.**
   Отпечаток — это хеш состава сборки. Два коммита, не изменившие ни
   одного файла в `dist/` (например, правка только документации), дают
   один отпечаток. Тогда проверка подтвердит, что по адресу лежит нужное
   содержимое, но не различит, каким коммитом оно туда попало. Для
   вопроса «работает ли выложенное» этого достаточно; для аудита «какой
   коммит сейчас в production» — нет.

2. **Одновременные выкладки.** Группа `pages` не даёт публикациям
   наслаиваться, но если два push идут подряд, проверка первого может
   застать уже второй. Ложного «прошло» это не даёт: проверяется
   отпечаток, и при несовпадении шаг ждёт, а не соглашается. Ложное
   падение по таймауту в этом случае возможно.

3. **Проверяется один браузер.** Chromium — тот же, что и во всём
   наборе. Вторая среда даёт вторую причину ложных падений, но не второй
   класс дефектов выкладки.

4. **Проверка не заменяет приёмку.** Она отвечает на вопрос «доехало
   ли», а не «правильно ли считает». На второй отвечают 157 сценариев до
   выкладки.
