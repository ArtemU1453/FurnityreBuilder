## Шесть вопросов §3

**1. Как называется шаг 3?** «Секции» — «Вертикальное деление корпуса
перегородками» (`src/app/workflow/steps.ts`, `id: 'sections'`).

**2. Как называется шаг 4?** «Ячейки» — «Ряды и колонки **внутри
секции**. Ячейка — пространство, а не деталь» (`id: 'cells'`).

**3. Какое действие является default action?** Единственная кнопка
панели шага 4: «Применить сетку 1×1» — подпись собирается из черновых
полей «Строк» и «Колонок», по умолчанию 1 и 1.

**4. Почему оно изменяет существующую структуру?** Потому что выполняет
`SetRoot` — замену **всего дерева изделия**:

```ts
const root =
  rowsDraft <= 1 && columnsDraft <= 1
    ? createLeaf(ids)
    : createUniformGrid(ids, rowsDraft, columnsDraft, thickness, thickness, createLeaf);
execute({ type: 'SetRoot', furnitureIndex: 0, root }, `Сетка ${rowsDraft}×${columnsDraft}, …`);
```

При значениях по умолчанию (1 × 1) `root` — это **одиночный пустой
лист**. Всё, что построил шаг 3, заменяется одной пустой ячейкой.

**5. Это intentional / legacy / рассинхронизация / дубль / неверный
default?**

**Legacy behavior плюс incorrect default.** Разобрано по частям:

| Версия | Верна? | Почему |
| --- | --- | --- |
| intentional | нет | Подпись шага обещает «ряды и колонки **внутри секции**». Замена всего дерева — не то, что обещано |
| state synchronization | нет | Рассинхронизация была и её чинили (PROMPT 31, `drafts.ts`), но здесь дерево гибнет по-настоящему, а не расходится с полем |
| duplicate generation path | частично | `SetRoot` и `SetSectionCount` оба строят структуру, и первый умеет только «целиком» |
| **legacy** | **да** | `SetRoot` появился раньше, чем шаги, — как «атомарная альтернатива серии `SplitNode`» для построения сетки на пустом изделии. Когда сверху легла лестница из 11 шагов, действие осталось прежним, а его место в сценарии изменилось |
| **incorrect default** | **да** | Разрушительная операция стала действием по умолчанию следующего по счёту шага, с обычной подписью «Применить» |

**6. Измеренная цепочка.**

```
Шаг 3 «Секции»: 7 деталей, 3 секции, 2 перегородки
        ↓
Пользователь нажимает «Далее» → шаг 4 «Ячейки»
        ↓
Единственная кнопка панели: «Применить сетку 1×1»
        ↓
applyGrid() → losesWork() → диалог → buildGrid()
        ↓
createEmptyLeaf(ids)                    // 1×1 — это ОДИН пустой лист
        ↓
execute({ type: 'SetRoot', root })      // замена всего дерева
        ↓
5 деталей, 1 секция, 0 перегородок
```

## Классификация действий (§2)

| Тип | Что делает | Примеры в приложении |
| --- | --- | --- |
| `SAFE` | меняет только состояние интерфейса | выбор шага, выбор отделения, «Сцена / Схема» |
| `CONSTRUCTIVE` | добавляет или правит конструкцию | габариты, «Применить секций», «Добавить полки», «Добавить дверь» |
| `DESTRUCTIVE` | удаляет или заменяет существующее | «Применить сетку» (`SetRoot`), «Убрать дверь», «Очистить наполнение» |

**Смешение**, которое и есть дефект: `DESTRUCTIVE` действие носило
подпись и место `CONSTRUCTIVE` — «Применить сетку N×M» рядом с
«Применить секций: N», в одном визуальном ряду, тем же типом кнопки, на
следующем по счёту шаге пронумерованной лестницы.

## Почему предупреждения и отмены недостаточно (§7, §8)

Оба существуют и работают:

* диалог называет потерю поимённо — «Будет заменено: 3 секции»;
* Ctrl+Z возвращает 7 деталей, 3 секции, 2 перегородки полностью.

Но они отвечают на вопрос «как отменить беду», а не «почему беда
предлагается по умолчанию». Намерение пользователя — **продолжить
строить**; система читала его как **пересоздать основу**. Подтверждение
неверного прочтения не исправляет.

## Что уже есть для правильного действия

Ничего изобретать не требуется — обе части лежат в проекте с ранних
этапов.

**`SplitNode`** (`src/state/commands.ts`) делит **один узел** по оси на N
детей с перегородкой. Ровно то, что обещает подпись шага 4: ряды и
колонки внутри выбранного отделения. Всё, что вне узла, не затрагивается.

**Транзакции** (`src/state/document-store.ts`): `beginTransaction(label)`
→ несколько `execute` → `endTransaction()` складываются в **один шаг
истории**. То есть ряды + колонки + полки — одна запись и одно нажатие
Ctrl+Z, ради чего когда-то и был выбран `SetRoot`.

Следовательно новая команда, новое поле домена и новая схема **не
нужны**: безопасное действие собирается из существующих примитивов.

## Решение

1. **Действие по умолчанию шага «Ячейки» становится
   `CONSTRUCTIVE`**: делит **выбранное отделение** на ряды и колонки
   через `SplitNode` внутри транзакции. Секции, перегородки, габариты и
   всё за пределами отделения сохраняются.
2. **Пересборка всего изделия сеткой остаётся**, но становится
   **отдельным явным `DESTRUCTIVE` действием** с собственной подписью,
   собственным местом и прежним подтверждением.
3. Ничего не удаляется: `SetRoot`, `createUniformGrid`,
   `grid-replacement.ts` и диалог остаются на местах и продолжают
   проверяться теми же тестами.

## Чего это изменение НЕ делает (§10)

Не переделывает мастер, не меняет порядок шагов, не объединяет шаги, не
добавляет возможностей, не трогает производственный путь, не меняет
модель документа и не трогает `FR-05` (поля габарита за экраном).
