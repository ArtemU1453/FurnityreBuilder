# Библиотека проектов

PROMPT 25. Локальная библиотека и менеджер проектов: создание,
переименование, дублирование, удаление, открытие, поиск, порядок,
превью.

Смежные документы: `PROJECT_PERSISTENCE.md` (как проекты хранятся и
переносятся), `PROJECT_ROOM_INTEGRATION.md` (как проект попадает в
помещение), `REPOSITORY_ARCHITECTURE.md` (почему IndexedDB).

## 1. Что такое проект

Проект — это `Project` из `src/domain/project/types.ts`, тот же самый,
что открыт в редакторе. Второго понятия «проект библиотеки» не
существует: карточка в списке — это сводка (`ProjectSummary`)
одного и того же объекта, а не отдельная сущность со своей жизнью.

Из этого следует главное свойство: изменить проект, минуя проект,
нельзя. Всё, что показывает карточка — имя, дата, габарит, количество
изделий, превью, — выводится функцией `summarize` из самого проекта.

## 2. Идентичность

`Project.id` присваивается один раз при создании и не меняется НИКОГДА:
ни при переименовании, ни при сохранении, ни при экспорте и обратном
импорте. Он же стоит в `FurnitureInstance.projectId` — ссылке из
помещения.

Отсюда два следствия:

- переименование не рвёт расстановку (`renameProject` меняет `name` и
  `metadata.updatedAt`, но не `id`);
- импорт ранее экспортированного файла ОБНОВЛЯЕТ проект, а не создаёт
  второй: это тот же проект, вернувшийся с диска.

`metadata.updatedAt` меняется ровно в одном месте — при записи в
хранилище (`BaseProjectRepository.save`). Без автосохранения «проект
изменился» и «изменение записано» — одно и то же событие, и второго
момента, в который время правки могло бы измениться, не существует.

## 3. Операции

| Операция | Где живёт правило | Что делает |
|---|---|---|
| создать | `createProject` (домен) | те же умолчания, что при первом запуске |
| открыть | `ProjectRepository.load` | документ заменяется целиком, история сбрасывается |
| сохранить | `ProjectRepository.save` | ставит `updatedAt`, кладёт превью |
| переименовать | `renameProject` (домен) | `id` сохраняется |
| дублировать | `duplicateProject` (домен) | новый `id`, глубокая копия, новая история |
| удалить | `ProjectRepository.delete` | с подтверждением на карточке |
| проверить наличие | `ProjectRepository.has` | по ключу, без разбора документа |

Домен отвечает на вопрос «что такое переименовать проект», хранилище —
на вопрос «где он лежит». Поэтому операции написаны один раз и работают
одинаково и в IndexedDB, и в памяти (`BaseProjectRepository`).

### Дублирование

Копия получает новый `Project.id`, собственные `createdAt`/`updatedAt` и
глубокую копию всего содержимого (`structuredClone`): общих изменяемых
ссылок с оригиналом не остаётся, и правка ширины в копии оригинал не
двигает. История правок в копию не переносится вовсе — она живёт в
сторе документа, а не в проекте.

Внутренние идентификаторы (изделий, узлов, материалов) в копии
СОХРАНЯЮТСЯ. Они уникальны в пределах проекта, а ссылка из помещения —
пара «проект + изделие», поэтому совпадение внутренних id у двух
проектов ничему не мешает. Перевыпуск всех id стоил бы обхода всего
дерева и не решал бы никакой существующей задачи.

Имя копии: «Шкаф» → «Шкаф (копия)» → «Шкаф (копия 2)». Копия копии не
превращается в «(копия) (копия)»: список таких имён нечитаем.

### Удаление

Выбран **вариант C** из PROMPT 25 §12: удаление разрешено, а
размещения удалённого проекта помечаются недоступными.

Почему не A (запретить удаление, пока есть размещения): помещение живёт
внутри проекта, а не рядом с ним, и «размещения» бывают в ЧУЖИХ
документах, которых удаляющий не видит. Запрет опирался бы на знание,
которого у приложения нет.

Почему не B (снимок изделия в экземпляре): снимок — это копия мебели в
помещении, а вся модель построена на том, что копии нет
(`FURNITURE_INSTANCE.md` §2). Снимок пришлось бы поддерживать в
согласии с оригиналом, то есть завести вторую геометрию.

Вариант C согласуется с уже принятым решением про удалённое ИЗДЕЛИЕ
(PROMPT 24): экземпляр не исчезает молча, а становится видимой ошибкой
(`ROOM_INSTANCE_PROJECT_NOT_FOUND`). Перед удалением карточка сообщает,
сколько раз проект размещён в открытом помещении.

## 4. Поиск, порядок, недавние

`src/library/search.ts`, слой чистый.

- Поиск — по имени, без учёта регистра и различия `ё`/`е`, по
  подстроке. Человек не помнит имя полугодовой давности с точностью до
  буквы.
- Порядок: по времени правки (в обе стороны), по имени (в обе стороны),
  по времени создания. Список закрыт: «по размеру» или «по количеству
  деталей» потребовали бы посчитать геометрию всех проектов ради
  сортировки.
- При равенстве ключа порядок доопределяется идентификатором — иначе
  два проекта с одинаковым временем «прыгали» бы между показами.
- Недавние — это верхушка того же списка по `updatedAt`, а не второе
  состояние. Отдельный «список последних открытых» пришлось бы
  поддерживать в согласии с библиотекой и чинить при удалении.

## 5. Превью

`src/library/preview.ts`, слой чистый.

Цепочка: `Project → GeometryResult → SceneModel → SVG`. Первые два шага
— уже существующие `buildGeometry` и `buildScene`, те же самые, что
рисуют изделие на экране. Второго способа посчитать шкаф не появляется.

Проекция — изометрия из направления (1, 1, 1): видны верх, фасад и бок,
поэтому по картинке различимы шкаф и тумба. Видимые грани постоянны,
потому что постоянно направление взгляда. Порядок отрисовки —
художников алгоритм по глубине центра коробки.

Масштаб подбирается под сцену («вписать»), а не задаётся числом: и
тумба 400 мм, и шкаф-купе 3 м должны быть одинаково читаемы в карточке
320 × 240.

SVG, а не WebGL: превью строится вне кадра — при сохранении, для списка
из десятков карточек, в тестах и в Node, где живого канваса нет. SVG —
текст: он детерминирован, сравним посимвольно и хранится в том же JSON,
что и проект.

Показывается ПЕРВОЕ изделие проекта. Проект из нескольких изделий
потребовал бы раскладки «как они стоят рядом», а такой раскладки в
модели нет: взаимное положение задаётся уже в помещении. Количество
изделий карточка сообщает числом.

### Превью — производное состояние

Оно хранится в проекте только затем, чтобы список не считал геометрию
всех проектов ради карточек. Чтобы производное не выдавало себя за
текущее, рядом лежит `sourceFingerprint` — отпечаток состояния, из
которого картинка построена (изделия, материалы, настройки; имя и время
в него не входят). `isPreviewStale` отвечает, устарела ли картинка.

Превью строится ОДИН РАЗ НА СОХРАНЕНИЕ, в `useProjectStorage.save`.
Эффекта, который смотрел бы на проект и записывал в него превью, нет —
а значит нет и цикла обновлений (§8).

### Безопасность показа

Превью хранится в проекте, а проект можно импортировать из файла,
который приложение не создавало. Поэтому карточка показывает его через
`<img src="data:image/svg+xml,…">`, а не вставкой разметки в документ:
внутри `<img>` SVG не исполняется и ничего не загружает.

## 6. Интерфейс

`src/app/editor/ProjectLibrary.tsx` — панель «Мои проекты», открывается
переключателем в тулбаре. Маршрутизации в приложении нет, и заводить её
ради одной панели значило бы построить вторую навигацию рядом с
существующим переключателем видов.

Карточка показывает превью, имя, дату правки, габарит, количество
изделий, признак «открыт» и количество размещений в помещении.
Действия: открыть, переименовать, дублировать, экспортировать, удалить.

Раскладка — сетка карточек, на телефоне одна колонка. Список строк
«Новый проект, 12.03.2026» не позволяет отличить один шкаф от другого.

Доступность: панель — `<section aria-label>`, список — `<ul>`,
превью — `<img>` с осмысленным `alt`, ошибки — `role="alert"`,
переименование — форма с подписанным полем. Всё управление доступно с
клавиатуры; фокус виден (`:focus-visible` в токенах).

## 7. Состояния (§22)

| Состояние | Когда | Что видит пользователь |
|---|---|---|
| `LOADING` | список читается | «Загружается…» |
| `READY` | проект открывается | карточка с превью |
| `WARNING` | файл открыт с замечаниями | текст замечания |
| `INVALID` | файл не читается | причина словами |
| `MIGRATION_REQUIRED` | файл новее приложения | «нужна другая версия» |
| `MISSING` | проект удалён, ссылка осталась | «Проект недоступен» |

Стек и текст ошибки схемы пользователю не показываются: они лежат в
`details` рядом. Пользователю нужен ответ «что делать», а не место в
коде.

## 8. Чего в библиотеке нет

Ни регистрации, ни входа, ни облака, ни синхронизации, ни телеметрии,
ни рекламы, ни публичного каталога, ни совместного редактирования.
Хранилище — IndexedDB в браузере пользователя, а без него — память
вкладки с честным предупреждением. Ни одного сетевого запроса:
проверяется `npm run check:brand`.
