# Развёртывание

PROMPT 32 §18. Приложение — статический сайт. Ни базы данных, ни
серверного кода, ни переменных окружения ему не нужно: их у продукта нет
вовсе.

## 1. Порядок

```bash
npm ci               # установка ровно тех версий, что в package-lock.json
npm run verify       # полная проверка: типы, линтер, тесты, сборка, аудиты
npm run build        # результат — dist/
# выложить содержимое dist/ на статический хостинг
```

`npm run build` выполняет четыре шага подряд:

1. `tsc --noEmit` — проверка типов (Vite её не делает);
2. `vite build` — сборка в `dist/`;
3. `node scripts/build-sw.mjs` — service worker со списком файлов сборки;
4. `node scripts/build-404.mjs` — `404.html` как копия входной страницы.

Порядок обязателен: список предзагрузки воркера собирается из готового
`dist/`, поэтому шаг 3 не может идти раньше шага 2.

## 2. Что попадает на хостинг

Только содержимое `dist/` — около 2.3 МБ, 17 файлов:

| Файл | Назначение |
| --- | --- |
| `index.html` | входная страница |
| `404.html` | её копия для хостингов без rewrite (см. §3) |
| `sw.js` | service worker |
| `manifest.webmanifest` | манифест приложения |
| `assets/index-*.js`, `assets/index-*.css` | приложение |
| `assets/pdf-*.js`, `assets/xlsx-*.js` | отложенные модули экспорта |
| `favicon.svg`, `icon-*.png`, `apple-touch-icon.png` | значки |
| `fonts/LiberationSans-Regular.ttf` | шрифт для PDF |
| `fonts/README.md` | уведомление о лицензии шрифта (требование SIL OFL) |

Состав проверяется автоматически: `npm run check:release` откажет, если в
пакете не окажется обязательного файла или окажется лишний — карта
исходников, тест, артефакт прогона, файл с секретами.

## 3. SPA-fallback

У приложения один адрес: экраны переключаются внутри страницы, отдельных
маршрутов нет (см. §6). Но на несуществующий путь пользователь всё равно
попадёт — по опечатке или старой ссылке. Настройте хостинг так, чтобы он
отдавал приложение, а не свою страницу ошибки.

**Nginx**

```nginx
location / {
  try_files $uri $uri/ /index.html;
}
```

**Caddy**

```
handle {
  try_files {path} /index.html
  file_server
}
```

**Apache** (`.htaccess`)

```apache
RewriteEngine On
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule . /index.html [L]
```

**Netlify** (`_redirects`)

```
/*  /index.html  200
```

**Vercel** (`vercel.json`)

```json
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
```

**GitHub Pages, Cloudflare Pages и подобные** — настраивать нечего: они
сами отдают `404.html`, а он у нас копия входной страницы, поэтому
приложение откроется и по неизвестному адресу.

## 4. HTTPS обязателен

Не пожелание, а условие работы. Без защищённого контекста браузер не даёт:

| Возможность | Без HTTPS |
| --- | --- |
| Service worker | не регистрируется |
| Работа без сети | не работает — нечему кэшировать |
| Установка приложения (PWA) | не предлагается |
| Cache Storage | недоступен |

IndexedDB и сам конструктор работают и по `http://`, но продукт при этом
теряет половину того, ради чего сделан. Исключение только одно и оно
браузерное: `http://localhost` считается защищённым контекстом, поэтому
`npm run preview` проверяет всё честно.

Приложение это учитывает: `serviceWorkerAvailable()`
(`src/app/service-worker.ts`) проверяет `window.isSecureContext` и молча
не регистрирует воркер там, где он невозможен. Приложение продолжает
работать как обычная страница — без офлайна и без установки.

## 5. Заголовки

Обязательных нет: приложение работает с настройками хостинга по
умолчанию. Рекомендуемые:

| Путь | Заголовок | Зачем |
| --- | --- | --- |
| `/assets/*` | `Cache-Control: public, max-age=31536000, immutable` | имена содержат хеш содержимого — файл никогда не меняется |
| `/index.html`, `/404.html` | `Cache-Control: no-cache` | иначе браузер отдаст старую страницу со ссылками на удалённые чанки |
| `/sw.js` | `Cache-Control: no-cache` | иначе новая версия не будет замечена |
| `/fonts/*` | `Cache-Control: public, max-age=31536000` | шрифт не меняется |

Ошибиться критично только в одном месте: **`index.html` и `sw.js` нельзя
кэшировать надолго.** Тогда после выкладки браузер продолжит просить
старые чанки, которых на хостинге уже нет.

Безопасные заголовки, если хостинг позволяет их задать:

```
Content-Security-Policy: default-src 'self'; img-src 'self' data: blob:; style-src 'self' 'unsafe-inline'; connect-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
```

`style-src 'unsafe-inline'` нужен: CSS-модули Vite подставляют стили
инлайном. `connect-src 'self'` можно ставить смело — наружу приложение не
ходит вообще.

## 6. У экранов нет отдельных адресов

Решение архитектурное и принято сознательно (см.
`src/app/shell/AppShell.tsx`): переключатель разделов — одно состояние, а
не второй источник истины о том, где находится пользователь. Отсюда:

- ссылку на конкретный экран отправить нельзя — открывается приложение
  целиком;
- кнопки «назад» и «вперёд» браузера не ходят по экранам;
- перезагрузка страницы возвращает на начальный экран, но **открытый
  проект восстанавливается** — он лежит в IndexedDB, а не в адресе.

Это ограничение, а не дефект: у продукта без сервера и без учётных
записей адрес ничего не удостоверяет. Записано в `README.md` и в
`docs/FINAL_DEFECT_LIST.md`.

## 7. Проверка после выкладки

```bash
# 1. Страница отдаётся
curl -sI https://example.org/ | head -1              # 200

# 2. Неизвестный путь отдаёт приложение, а не страницу хостинга
curl -s https://example.org/нет-такого | grep -c 'id="root"'   # 1

# 3. Манифест и воркер на месте и с правильным типом
curl -sI https://example.org/manifest.webmanifest | head -1    # 200
curl -sI https://example.org/sw.js | head -1                   # 200

# 4. index.html не закэширован навсегда
curl -sI https://example.org/ | grep -i cache-control
```

Дальше — в браузере: открыть, дождаться регистрации воркера
(инструменты разработчика → Application → Service Workers), отключить
сеть, перезагрузить. Приложение обязано открыться и работать. Полный
список проверок — `docs/RELEASE_CHECKLIST.md`.

## 8. Выкладка новой версии

Достаточно заменить содержимое `dist/`. Дальше срабатывает механизм
обновления (`docs/PWA_OFFLINE.md` §4):

1. открытая вкладка замечает новый `sw.js`;
2. новая версия скачивается и **ждёт**, не подменяя работающее
   приложение;
3. приложение показывает «Доступна новая версия» с кнопкой;
4. по нажатию новая версия встаёт, страница перезагружается, старый кэш
   удаляется.

Проекты пользователя при этом не затрагиваются: код лежит в Cache
Storage, проекты — в IndexedDB.

**Не меняйте имя базы IndexedDB и ключи хранения без миграции.** Схема
проекта версионируется (`docs/PROJECT_PERSISTENCE.md` §6), и старые файлы
читаются миграциями. Смена ключей в обход этого механизма означает потерю
проектов у всех, кто уже пользуется приложением.
