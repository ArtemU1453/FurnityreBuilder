# Хранение и перенос проектов

PROMPT 25. Где живут проекты, как они читаются и записываются, как
переносятся файлом и что происходит с файлами прежних версий.

Смежные документы: `REPOSITORY_ARCHITECTURE.md` (почему IndexedDB, а не
localStorage), `DATA_MODEL.md` (что такое проект), `PROJECT_LIBRARY.md`
(операции библиотеки).

## 1. Одно хранилище

```
UI → useProjectStorage / useProjectLibrary → ProjectRepository → IndexedDB | память
```

`ProjectRepository` существует с PROMPT 2. Библиотека НЕ завела рядом
второго хранилища: операции `has`, `create`, `rename`, `duplicate`
добавлены к тому же интерфейсу, а общая для обеих реализаций часть
живёт в `BaseProjectRepository`. Отдельный «LibraryStore» означал бы два
ответа на вопрос «какие проекты есть у пользователя», и они разошлись бы
при первой же ошибке записи.

Соединение с базой тоже одно: `sharedRepository()` в
`src/app/repository.ts` запоминает обещание на модульном уровне.
Редактор и библиотека работают с одним и тем же объектом.

Реализации:

- `IndexedDbProjectRepository` — постоянное хранилище браузера;
- `InMemoryProjectRepository` — рабочий режим для приватного окна, где
  IndexedDB недоступен. `isPersistent() === false`, и интерфейс обязан
  об этом сказать (говорит: и строка состояния, и панель библиотеки).

Ни сети, ни учётной записи, ни синхронизации. Всё лежит на машине
пользователя.

## 2. Запись и время изменения

`save(project)` возвращает записанный проект, а не `void`. Причина в
том, что запись — единственное место, где меняется `metadata.updatedAt`
(`BaseProjectRepository.save` → `touchProject`). Если бы приложение не
принимало возвращённую версию, на экране осталось бы старое время, а в
хранилище — новое.

Принимает её `DocumentState.markSaved`: он меняет только то, что
появляется при сохранении (время и превью), и НЕ трогает историю.
«Отменить сохранение» не значит ничего, а сброс истории после каждого
сохранения отнял бы у пользователя возможность отменить только что
сохранённую работу.

Автосохранения в приложении нет и PROMPT 25 §24 предписывает его не
вводить: молчаливая запись поверх файла — это потеря работы, если
пользователь экспериментировал. Несохранённые правки видны постоянно
(механизм «грязного» состояния тот же, что с PROMPT 22: сравнение
ссылки на проект, возможное благодаря иммутабельности).

### 2.1. Предупреждение перед потерей работы

Раз автосохранения нет, закрытие вкладки — единственный момент, когда
работа исчезает молча, и единственное место, где браузер даёт её
отстоять. Приложение вешает `beforeunload`, когда выполнены ОБА условия:

1. `storage.status === 'unsaved'` — на диске не то, что на экране;
2. `history.past` не пуст — выполнена хотя бы одна команда.

Оба слагаемых обязательны. Первое одно не годится: пустой, ещё не
тронутый проект тоже «не сохранён», и диалог выскакивал бы у человека,
который просто закрыл вкладку сразу после открытия. Второе отличает
«есть что терять» от «ничего не делали»; откат всех правок через Ctrl+Z
снова опустошает историю, и предупреждение исчезает — на экране опять
то, с чего начали.

Текст диалога задаёт браузер, а не страница: свой показать нельзя уже
много лет. Второго механизма «грязного» состояния при этом не заводится
— это тот же `storage.status`, который уже показан в строке состояния.

> **Исправлено на PROMPT 31 (§8, дефекты D-003 и D-004).**
> Предупреждения не было вовсе, а восстановленный при запуске проект
> помечался несохранённым, хотя на диске лежал ровно он: `restore()`
> подменял документ, но не звал `markClean`. Ложная тревога при каждом
> открытии вкладки обесценивала само сообщение — и сделала бы
> бессмысленным любое предупреждение поверх него. Теперь восстановление
> отмечает документ сохранённым тем же способом, что и открытие проекта
> из библиотеки.

## 3. Сводка записи

`ProjectSummary` несёт то, что показывает карточка: имя, даты, число
изделий, габарит первого изделия, превью. В IndexedDB она хранится
рядом с документом, чтобы список не разбирал каждый проект целиком.

Записи, сделанные до библиотеки, сводки не содержат. Тогда список
выводит её из документа этой записи — медленнее, но правильно; при
первом же сохранении запись обновляется. Подставлять нули значило бы
показать в карточке неправду.

Повреждённая запись пропускается, а не роняет весь список: один битый
проект не должен закрывать доступ к остальным.

## 4. Формат

Формат хранения и формат обмена — ОДИН И ТОТ ЖЕ:

```json
{ "schemaVersion": 1, "project": { … } }
```

Экспорт — `toJson`, импорт — `fromJson`. Второй «формат обмена» означал
бы вторую схему, вторые миграции и второй набор ошибок. Файл открывается
текстовым редактором: пользователь без аккаунта должен уметь физически
забрать свой проект.

## 5. Конвейер импорта

```
File → Parse → Validate → Migrate → Normalize → Save
```

| Шаг | Где | Что делает |
|---|---|---|
| Size | `checkImportSize` | размер файла ДО чтения; предел `MAX_IMPORT_BYTES` = 32 МБ |
| Parse | `fromJson` | `JSON.parse`, ошибка «файл не является корректным JSON» |
| Validate | `versionProbeSchema`, `projectDocumentSchema` (Zod) | проверка версии и структуры |
| Migrate | `migrateDocument` | последовательные миграции до текущей версии |
| Normalize | `normalizeProject` | достраивает то, что зависит от проекта целиком |
| Save | `ProjectRepository.save` | проект попадает в библиотеку сразу |

`importProjectFromText` не выбрасывает исключений наружу: причина —
часть результата, потому что интерфейс обязан показать её словами.

### Почему размер проверяется до чтения

Предел стоит не против «слишком больших проектов»: самый крупный из
зафиксированных в тестах документов не доходит и до мегабайта. Он стоит
против файла, который проектом не является — выбранный по ошибке образ
диска или видео прочитался бы через `file.text()` целиком в память
вкладки, и человек увидел бы не сообщение об ошибке, а зависшую
страницу. Проверить это можно ТОЛЬКО до чтения; после уже поздно
(PROMPT 31 §17, дефект D-008).

Отдельного типа ошибки для этого не заведено: `checkImportSize`
возвращает тот же `ImportRejected`, который интерфейс уже умеет
показывать.

### Почему нормализация — отдельный шаг

Схема отвечает на вопрос «правильной ли формы файл», миграции — «какой
он версии». Ни та, ни другая не могут ответить на вопрос «чего в нём не
хватает по смыслу»: подставить экземпляру ссылку на проект способен
только тот, кто знает, ЧЕЙ это файл, а это значение появляется лишь
когда проект разобран целиком.

Нормализация не чинит ошибки. Экземпляр, ссылающийся на удалённое
изделие, остаётся как есть и становится видимой ошибкой размещения:
тихо «починенный» файл хуже честно помеченного.

## 6. Совместимость со старыми файлами

`SCHEMA_VERSION` остаётся равной 1. Новые поля добавлены к существующей
схеме с `.default()` или как необязательные — тот же приём, что у `unit`
фурнитуры (PROMPT 16), параметров раскроя (PROMPT 17) и полей помещения
(PROMPT 24):

- `project.preview` — необязательное;
- `room.furnitureInstances[].projectId` — необязательное; недостающее
  значение подставляет `normalizeProject` из проекта-хозяина. Для файла
  PROMPT 24 это ровно то, чем оно и было: проект тогда был один.

Файл, созданный более новой версией приложения, отклоняется целиком с
состоянием `MIGRATION_REQUIRED`: частично применённый импорт хуже
отказа — пользователь решит, что файл открылся.

## 7. Ошибки, которые видит человек

| Что случилось | Сообщение |
|---|---|
| не JSON | «Файл не является корректным JSON.» |
| нет версии схемы | «Файл не является проектом: отсутствует версия схемы.» |
| структура не та | «Файл проекта не соответствует ожидаемой структуре.» |
| версия из будущего | «Файл создан в более новой версии приложения…» |
| проект уже существует | «Проект с таким идентификатором уже существует: …» |

Техническая подробность (текст ошибки Zod, номера версий) лежит в
`details` рядом и пользователю по умолчанию не показывается. Стек не
показывается никогда.

## 8. Имя файла при экспорте

Имя проекта, а не идентификатор: в папке «Загрузки» пользователь ищет
«Шкаф в прихожую», а не `a3f1…`. Запрещённые в именах файлов символы
заменяются на дефис — иначе браузер молча сохранит файл под другим
именем. Пустое имя даёт `Проект.json`.

Файл собирается в браузере (`Blob` + `URL.createObjectURL`) и никуда не
отправляется.
