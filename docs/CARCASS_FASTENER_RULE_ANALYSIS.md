# PM-18 — корпусный крепёж: разбор

PROMPT 66 §2. Аудит существующего `findCarcassJoints` и того, чего не
хватает, чтобы стык превратился в строку спецификации.

Базовый коммит `20c40d0`. Алгоритм **не переписывался**: §2 запрещает
трогать его до подтверждения правил.

---

## FACT — что алгоритм делает сегодня

```ts
const VERTICAL_ROLES = new Set(['side', 'partition']);
const HORIZONTAL_ROLES = new Set(['top', 'bottom', 'shelf-fixed']);
```

Для каждой пары «вертикаль × горизонталь» проверяются два условия:
`touchesAlongX` (перекрытие или примыкание по X с допуском 0.5 мм) и
`meetsAlongY` (встреча по высоте с тем же допуском).

### Замер на контрольном изделии

1800 × 2200 × 600, три секции, полки в первой, дверь на третьей.
Геометрия деталей:

| Деталь | Габарит |
| --- | --- |
| Боковина левая | x[0…16] y[0…2200] z[3…600] |
| Боковина правая | x[1784…1800] y[0…2200] z[3…600] |
| Дно | x[16…1784] y[0…16] z[3…600] |
| Крышка | x[16…1784] y[2184…2200] z[3…600] |
| Перегородка 1 | x[594.7…610.7] y[16…2184] z[3…600] |
| Перегородка 2 | x[1189.4…1205.4] y[16…2184] z[3…600] |
| Полки 1–4 | `shelf-adjustable`, съёмные |

Найдено **8 стыков**:

| Тип стыка | Количество |
| --- | --- |
| боковина ↔ дно | 2 |
| боковина ↔ крышка | 2 |
| перегородка ↔ дно | 2 |
| перегородка ↔ крышка | 2 |

## A. Какие соединения находятся правильно (§2 A)

**Все восемь — настоящие стыки, ложных нет.** Проверено по координатам:

- боковина левая x[0…16] и дно x[16…1784] примыкают ровно в x = 16;
- по Y боковина y[0…2200] накрывает дно y[0…16];
- перегородки y[16…2184] примыкают к дну в y = 16 и к крышке в y = 2184.

Съёмные полки **правильно не дают стыков**: они лежат на
полкодержателях, и крепёж им не нужен. Роль `shelf-fixed` в списке
горизонталей есть, то есть стационарная полка стык даст.

## B. Какие настоящие соединения отсутствуют (§2 B)

| Отсутствует | Почему это настоящий стык | Насколько серьёзно |
| --- | --- | --- |
| Цоколь (`plinth`) ↔ боковины | царги цоколя крепятся к корпусу | роль не входит ни в один список |
| Столешница (`countertop`) ↔ боковины | столешница притягивается к корпусу | роль не входит |
| Фальшпанель (`filler`) ↔ боковина | панель крепится к корпусу | роль не входит |
| Задняя стенка ↔ корпус | отдельный вид крепежа | **намеренно**: это `PM-17` |
| Горизонталь ↔ горизонталь, вертикаль ↔ вертикаль | в текущей модели не встречаются | не требуется |

### Скрытая слабость: проверки по Z нет вовсе

`touchesAlongX` и `meetsAlongY` смотрят только на X и Y. Две детали,
разнесённые по глубине и не касающиеся друг друга, будут признаны
стыком.

Сегодня это не проявляется: все корпусные детали занимают z[3…600].
Проявится, как только появится деталь на другой глубине — столешница со
свесом, цоколь с отступом, антресоль. **Это не текущий дефект, а
ловушка** при добавлении ролей из таблицы выше.

## C. Чего не хватает, чтобы стык стал строкой BOM (§2 C)

`CarcassJoint` хранит обе детали целиком, поэтому уже доступно: роли,
названия, идентификаторы, габариты, положения, материалы, толщины.

| Нужно | Есть? | Комментарий |
| --- | --- | --- |
| перечень стыков | **да** | 8 из 8 верных |
| тип обеих деталей | **да** | из `role` |
| различение видов стыка | **да, выводится** | пара ролей уже даёт «боковина ↔ крышка» |
| **длина стыка** | **НЕТ** | не вычисляется. Здесь это протяжённость по Z — 597 мм |
| **тип соединения** | **есть в модели, не читается** | см. ниже |
| **количество на стык** | **НЕТ** | `CARCASS_FASTENERS_PER_JOINT = undefined` |

### Находка: тип соединения модель знает, а правило игнорирует

```ts
export type JointType = 'confirmat' | 'eccentric' | 'dowel' | 'eccentric+dowel';
```

`ConstructionScheme.jointType` — обязательное поле схемы сборки. Правило
крепежа корпуса **его не читает** и жёстко печатает конфирмат:

```ts
kind: 'confirmat' as const,
```

Следствие: проект, настроенный на эксцентрик со шкантом, получил бы в
спецификации конфирматы. Сегодня это не проявляется, потому что позиций
не выдаётся вовсе, — но как только количество подтвердится, ошибка
станет видимой.

### Находка: интерфейс `CarcassJoint` не переживёт правила «на погонный метр»

Сейчас в модели заложено «N крепежа на стык». Если подтверждённое
правило окажется шаговым («крепёж каждые N мм по длине стыка»),
`CarcassJoint` придётся расширять: длины у него нет.

Оба варианта правдоподобны, и выбирать между ними **нельзя** до
источника. Поэтому интерфейс не меняется в этом промпте.

| сколько элементов на соединение | **не подтверждено** |

| пороги и интервалы | не подтверждены |
| надо ли различать виды стыка | **не подтверждено**; различение технически доступно |

## DESIGN DECISION

| Решение | Обоснование |
| --- | --- |
| Алгоритм не трогать | §2 запрещает до подтверждения. Все 8 стыков верны — менять нечего |
| Длину стыка не добавлять | пока неизвестно, нужна ли она, поле было бы догадкой о форме правила |
| `jointType` не подключать | подключение без правила количества ничего не даёт, а выбор соответствия «тип → позиция реестра» сам требует подтверждения |
| Недостающие роли не добавлять | цоколь, столешница и фальшпанель дали бы стыки без проверки по Z, то есть ложные |

## IMPLEMENTATION GAP

Порядок работ, когда источник появится:

1. Подтвердить количество (или шаг) — **блокер**.
2. Если правило шаговое — добавить длину в `CarcassJoint`.
3. Подключить `jointType` к выбору позиции реестра.
4. Добавить проверку по Z, затем роли цоколя, столешницы, фальшпанели.
5. Только после 1–3 снять `CARCASS_FASTENERS_PER_JOINT = undefined`.

Шаги 2–4 без шага 1 бессмысленны: позиция всё равно не выдаётся.
