# Проверка готовности к производству

Реализация: `src/workflow/readiness.ts`. Общий сценарий —
`docs/PRODUCTION_WORKFLOW.md`.

Форма описания: **Спецификация → Доменное правило → Реализация → Тест**.

---

## 1. Что это

`validateProductionReadiness(project, {calculation?})` →
`ProductionReadinessResult`. Функция чистая, не знает ни о React, ни о
DOM (граница проверена архитектурным тестом) и **ничего не считает
заново**: у каждого слоя уже есть собственная валидация, и повторять её
здесь значило бы завести второй свод правил, который разойдётся с
первым.

Задача проверки — разложить уже найденное по разделам и вывести один
статус. Раздел отвечает на вопрос «что мешает запустить изделие в
работу»: технолог, увидев «Раскрой — ошибка», знает, к кому идти, а
увидев «две ошибки в спецификации» — нет.

## 2. Результат

```ts
interface ProductionReadinessResult {
  status: ProductionStatus;          // общий статус производства
  calculationStatus: CalculationStatus;  // статус расчёта, как есть
  checks: ProductionCheck[];         // восемь разделов
  errors: Issue[];                   // собраны из проверок
  warnings: Issue[];
  needsConfirmation: ConfirmationItem[];
}

interface ProductionCheck {
  id: ProductionCheckId;   // стабильный, не текст сообщения
  title: string;
  status: 'PASS' | 'WARNING' | 'ERROR' | 'NEEDS_CONFIRMATION';
  errors: Issue[]; warnings: Issue[];
  needsConfirmation: ConfirmationItem[];
  details: string;         // что проверялось и что получилось
}
```

Идентификатор проверки стабильный и типизированный: по нему адресуются,
а не по тексту сообщения (§4). Текст меняется при первой же правке
формулировки — идентификатор нет.

## 3. Проверки

| ID | Что проверяет | Источник |
| --- | --- | --- |
| `GEOMETRY_VALID` | диагностика геометрии всех изделий, кроме материальной | `ProductionCalculationResult.geometry[].result.diagnostics` |
| `MATERIALS_VALID` | материал позиции существует, толщина определена, формат листа задан | диагностика `MATERIAL_*`, ошибки слоёв деталей и раскроя, обход `bom.parts` |
| `EDGES_VALID` | материал кромки существует; неназначенный — предупреждение | `bom.parts[].edgeBanding`, `bom.edgeBanding` |
| `HARDWARE_VALID` | ошибки и предупреждения расчёта фурнитуры | `HardwareBOM` |
| `DRILLING_VALID` | координаты, грани, диаметры, глубины, конфликты операций | `DrillingPlan` |
| `CUTTING_VALID` | листы, раскладка, неразмещённые детали | `CuttingResult` + `BOM_PART_NOT_PLACED` |
| `BOM_VALID` | количество против источников, отсутствие двойного счёта | обход `bom.parts` |
| `EXPORT_VALID` | данные документа собираются и совпадают со спецификацией по числу строк | `buildProductionExportData` |

**Почему материальная диагностика уходит из геометрии.** Сломанную
ссылку на материал первой замечает геометрия — она первой к ней
обращается. Но относится проблема к разделу материалов: технолог, увидев
«ошибка геометрии», пойдёт проверять размеры, а дело в реестре
материалов. Поэтому диагностика с кодом `MATERIAL_*` перекладывается в
`MATERIALS_VALID` независимо от того, кто её выдал.

**Что проверяет `EXPORT_VALID`.** Не «файл создался» — а что данные
документа собираются и что число строк совпадает со спецификацией.
Расхождение здесь означает документ, не соответствующий расчёту, и это
худший из возможных исходов: он выглядит правдоподобно.

**Тест.** `tests/unit/workflow/readiness.test.ts` Test 1–11.

## 4. Уровни

| Уровень | Значение | Примеры |
| --- | --- | --- |
| `ERROR` | производство невозможно | нулевой размер, неизвестный материал, деталь не размещена, конфликт отверстий |
| `WARNING` | производство возможно, но стоит посмотреть | материал кромки не назначен, формат листа не задан |
| `NEEDS_CONFIRMATION` | правило не подтверждено референсом | пропил, параметры присадки, правила количества фурнитуры |

Неподтверждённые правила разложены по своим разделам: `T-CUT-01` — в
раскрой, `T-DRILL-*` — в присадку, правила количества фурнитуры — в
фурнитуру. Общий список из пятнадцати строк не говорит, куда идти.

## 5. Правило перехода в READY_FOR_PRODUCTION

```
status = INVALID              если есть хотя бы одна ошибка
       = NEEDS_CONFIRMATION   иначе, если есть неподтверждённые правила
       = HAS_WARNINGS         иначе, если есть предупреждения
       = READY_FOR_PRODUCTION иначе
```

Статус не может оказаться выше самой слабой проверки. Автоматического
перехода из `NEEDS_CONFIRMATION` в готовность нет и не будет: правило,
которое никто не подтвердил, не становится подтверждённым оттого, что по
нему что-то посчиталось.

**Тест.** Test 4–7, Test 15.

## 6. Трассируемость

Каждая ошибка несёт `Issue` с кодом и, где это применимо, `target`
(`partId`/`nodeId`). Дальше цепочка восстанавливается уже существующими
средствами: `Part → origin.nodeId → Cell`, `PartBOMItem →
productionPartIds → ProductionPart → sourcePartIds`, `DrillingOperation →
sourceHardwareId → HardwareItem`. Новых идентификаторов проверка не
создаёт и существующих не теряет (§7).

## 7. Сегодняшний результат

Любой проект получает `NEEDS_CONFIRMATION`: не подтверждены пропил
(`T-CUT-01`), база процента использования (`T-CUT-02`), обрезная кромка
(`T-CUT-03`), правила кромки (`T-EDG-02`, `T-EDG-03`), конструкция
короба ящика (`T-DRW-02`), все параметры присадки (`T-DRILL-01…05`) и
правила количества фурнитуры (`T-HW-03`, `T-HW-08`, `T-DOOR-05`).

Это состояние знаний, а не состояние кода: каждое правило реализовано
целиком и ждёт одного подтверждённого значения.
