# Система координат трёхмерной сцены

Как координаты изделия попадают в рендерер (PROMPT 23 §4). Координаты
самой мебели — `docs/COORDINATE_SYSTEM.md`; этот документ описывает
только переход между ними и экраном.

---

## 1. Одна система координат, а не две

Оси сцены **совпадают** с осями изделия. Это не совпадение и не
везение: система координат мебели была выбрана на PROMPT 2 правой,
с осью Y вверх и Z на зрителя, а WebGL использует ровно такую же.

```
        Y (вверх)
        │
        │
        └───── X (вправо)
       ╱
      Z (на зрителя, «наружу» изделия)
```

| Направление | Ось | Знак |
| --- | --- | --- |
| вправо (right) | X | + |
| влево (left) | X | − |
| вверх (up) | Y | + |
| вниз (down) | Y | − |
| вперёд, к зрителю (front) | Z | + |
| назад, к стене (back) | Z | − |

Начало координат — **левый-нижний-задний угол изделия**. Задняя
плоскость изделия целиком, включая заднюю стенку, лежит в `Z = 0`
(`docs/COORDINATE_SYSTEM.md` §3).

Единица длины — миллиметр, и в сцене тоже. Никакого перевода в
«условные единицы» не делается: масштаб — забота камеры, а не данных.
Шкаф 2000 мм высотой — это 2000 в мировых координатах сцены.

## 2. Единственное преобразование: угол → центр

Домен хранит коробку как «минимальный угол + габарит»; параллелепипед
рисуется от центра. Поэтому адаптер делает ровно одно действие:

```
scene.position = part.position + part.size / 2
scene.size     = part.size                      (без изменений)
```

Это преобразование системы координат, а не расчёт мебели: изменение
конструкции не меняет здесь ничего, и обратный переход всегда точен.

Больше в слое сцены арифметики над размерами нет.

## 3. Проверка по каждому виду деталей

Требование §4 — убедиться, что двери, ящики, полки, задняя стенка,
цоколь и перегородки попадают в сцену без перепутанных осей. Проверено
тестами (`tests/unit/scene/adapter.test.ts`) и наблюдением сцены:

| Деталь | Толщина по оси | Проверено |
| --- | --- | --- |
| Боковина | X | `size.x` = толщина панели |
| Крышка, дно, полка | Y | `size.y` = толщина панели |
| Перегородка | X | вертикальная стойка, `size.x` = толщина |
| Задняя стенка | Z | стоит в `Z = 0`, `size.z` = толщина стенки |
| Дверная створка | Z | стоит впереди корпуса, `size.z` = толщина фасада |
| Фасад ящика | Z | там же, стопка делится вдоль Y |
| Ручка | Z | выступает вперёд от фасада |
| Цоколь | Y снизу | смещает корпус вверх на свою высоту |

Осей рендерер не переставляет ни для одной роли. Если деталь
выглядит повёрнутой, это ошибка движка, а не сцены, — и её видно на
схеме тоже.

Соответствие ЛОКАЛЬНЫХ сторон детали (`front`/`back`/`left`/`right`
у кромки и присадки) мировым осям задаёт `Part.orientation`; сцена
локальные стороны не использует вовсе.

## 4. Камера

Состояние камеры — сферические координаты вокруг цели, а не матрица:

```ts
interface Camera {
  target: Vec3;        // точка, вокруг которой вращаемся, мм
  distance: number;    // расстояние до цели, мм
  azimuth: number;     // 0 — строго спереди, растёт против часовой
  elevation: number;   // 0 — на уровне цели, +π/2 — сверху
  projection: 'perspective' | 'orthographic';
  fovY: number;
}
```

Хранить матрицу и править её приращениями значит копить погрешность:
через сотню кадров орбиты базис перестаёт быть ортонормированным, и
картинка едет. Матрица собирается заново из этих пяти чисел на каждом
кадре — это дешевле, чем ортонормировать.

`elevation` ограничен полюсами с зазором 0.001 рад: ровно на полюсе
направление взгляда совпадает с `up`, базис вида вырождается, картинка
схлопывается.

Свободного вращения (кватерниона) нет намеренно: «заваленный горизонт»
дезориентирует, а в мебели пользователь обязан всегда понимать, где верх
шкафа.

## 5. Стандартные виды

| Вид | azimuth | elevation | Проекция |
| --- | --- | --- | --- |
| Общий | −36° | +20° | перспектива |
| Спереди | 0° | 0° | ортографическая |
| Сзади | 180° | 0° | ортографическая |
| Слева | −90° | 0° | ортографическая |
| Справа | +90° | 0° | ортографическая |
| Сверху | 0° | +90° | ортографическая |
| Снизу | 0° | −90° | ортографическая |

**Плоские виды ортографические, и это не украшение.** В перспективе на
«виде спереди» левая и правая боковины получаются разной ширины, и по
картинке нельзя сравнить два размера. Плоский вид обязан быть измеримым.

Расстояние подбирается так, чтобы охват сцены поместился целиком, и
считается по вертикальному и горизонтальному углу отдельно — берётся
большее: узкое высокое окно обрезает изделие по ширине, широкое низкое —
по высоте.

Вписывается ИЗМЕРЕННЫЙ охват (`GeometryResult.boundingBox`), а не
заявленный габарит (`bounds`): столешница со свесом и ручка выступают за
номинальный габарит, и камера по `bounds` их обрезала бы.

## 6. Экран → мир

Луч выбора строится из нормализованных координат устройства
(x, y ∈ −1…1, y вверх) обращением матрицы «проекция × вид»:

```
ndc → invert(viewProjection) → две точки (z = −1 и z = +1) → луч
```

Перевод пикселей в NDC делает компонент: только он знает
`getBoundingClientRect`, а слою сцены DOM недоступен.

Вырожденную матрицу (холст ещё не получил размер) `invert` не обращает,
а возвращает `undefined`. Тихо вернуть мусор означало бы выбирать деталь
в случайной точке.

## 7. Пиксели → миллиметры

Ручкам изменения размера нужен коэффициент «сколько миллиметров в одном
пикселе вдоль мировой оси». Он зависит и от расстояния, и от угла, под
которым ось смотрит на экран, поэтому считается прямо: проецируются две
точки оси, разнесённые на 100 мм, и измеряется, на сколько пикселей они
разошлись. Работает одинаково для перспективы и ортографии.

Если ось смотрит почти точно в камеру (меньше сотой доли пикселя на
миллиметр), жест не начинается вовсе: за один пиксель размер менялся бы
на метр, и это не управление, а рулетка.

Знак берётся из той же проекции: при взгляде сзади правая грань уходит
влево, и без этого изделие сжималось бы, когда пользователь тянет
наружу.
