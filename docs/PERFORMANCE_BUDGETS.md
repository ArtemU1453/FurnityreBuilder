# Бюджеты производительности

PROMPT 44. Цифры измерены, а не назначены. Каждая получена командой,
указанной рядом, и воспроизводится на любой машине.

Смысл бюджета не в том, чтобы гордиться числами, а в том, чтобы заметить
день, когда зависимость въехала в загрузку по умолчанию.

## Baseline

| | |
| --- | --- |
| Когда | 2026-09-10, версия 0.1.0 |
| Чем | `npm ci && npm run build` на чистой установке |
| Где хранится | `performance/bundle-baseline.json` |
| Чем проверяется | `npm run check:bundle` |

Меток времени в файле baseline намеренно нет: они сделали бы сравнение
бессмысленным. Сжатие — gzip уровня 9, тот же, что в проверке.

## Metrics

Что измеряется и почему именно это.

| Метрика | Единица | Что ловит |
| --- | --- | --- |
| `initial-js-gzip` | gzip | библиотеку, въехавшую в загрузку по умолчанию |
| `initial-css-gzip` | gzip | въехавший фреймворк стилей |
| `largest-initial-chunk-gzip` | gzip | один раздувшийся чанк при нормальной сумме |
| `critical-total-gzip` | gzip | суммарный вес того, без чего не открыть |
| `lazy-pdf-gzip` | gzip | внезапный рост тяжёлого отложенного чанка |
| `lazy-xlsx-gzip` | gzip | зависимость, въехавшую в свой код |
| `total-build-raw` | raw | забытый в пакете файл |

**Сжатое и несжатое не смешиваются.** Шесть метрик в gzip — это то, что
идёт по сети; седьмая в raw — то, что лежит на хостинге. Сравнивать их
между собой нельзя, и в одной строке они не стоят.

## Initial Load

Что браузер обязан получить, чтобы приложение открылось и заработало:

| Ресурс | raw | gzip |
| --- | --- | --- |
| `index.html` | 3.8 КБ | 1.6 КБ |
| `assets/index-*.js` — главный чанк | 645.1 КБ | **193.6 КБ** |
| `assets/index-*.js` — точка входа | 2.6 КБ | 1.2 КБ |
| `assets/index-*.css` | 45.2 КБ | 8.3 КБ |
| **Итого критического** | | **204.7 КБ** |

Сюда НЕ входят: значки (не блокируют отрисовку), шрифт для PDF (нужен
только экспорту), service worker (регистрируется после загрузки).

**Весь каталог сборки — это не размер первой загрузки.** 2267 КБ пакета
и 205 КБ критического — разные величины, и путать их значит мерить не то.

## Lazy Features

Что вынесено из первой загрузки и почему.

| Чанк | gzip | Когда грузится | Почему вынесено |
| --- | --- | --- | --- |
| `pdf-*.js` | 499.7 КБ | нажатие «PDF» | `pdf-lib` с встраиванием шрифтов больше всего остального приложения вместе взятого; нужен раз в сеанс |
| `xlsx-*.js` | 3.2 КБ | нажатие «XLSX» | вынесен вместе с барьером экспорта: один баррель — один рубеж |
| `memory-repository-*.js` | 0.3 КБ | приватный режим браузера | запасное хранилище, нужное меньшинству |
| `fonts/*.ttf` | 401 КБ raw | первый экспорт PDF | шрифт нужен только документу; в JS его встраивать — полмегабайта base64 всем |

### Что НЕ вынесено — и это решение, а не упущение

Трёхмерная сцена, планировщик помещения и производственный расчёт
остаются в главном чанке. Проверено по графу зависимостей, а не по
ощущению:

| Кандидат | Вынести можно? | Почему оставлен |
| --- | --- | --- |
| Трёхмерная сцена | нет | это и есть первый экран: изделие видно сразу при открытии |
| Планировщик помещения | технически да | делит с редактором и сцену, и модель, и команды; рубеж прошёл бы по середине связного кода |
| Производственный расчёт | технически да | считается при каждом изменении модели — не «по нажатию», а постоянно |
| React, zustand, immer, zod | нет | каркас приложения |

Главный чанк — 193.6 КБ gzip при бюджете 260. Оптимизация ради
оптимизации здесь дала бы не выигрыш, а разрезанный по живому код и
новый класс дефектов: «возможность не открылась, потому что чанк не
доехал».

## Budgets

| Метрика | Сейчас | Бюджет | Запас |
| --- | --- | --- | --- |
| `initial-js-gzip` | 194.8 КБ | 260 КБ | 25 % |
| `initial-css-gzip` | 8.3 КБ | 20 КБ | 59 % |
| `largest-initial-chunk-gzip` | 193.6 КБ | 260 КБ | 26 % |
| `critical-total-gzip` | 204.7 КБ | 300 КБ | 32 % |
| `lazy-pdf-gzip` | 499.7 КБ | 600 КБ | 17 % |
| `lazy-xlsx-gzip` | 3.2 КБ | 20 КБ | 84 % |
| `total-build-raw` | 2267 КБ | 3072 КБ | 26 % |

Запас выбран так, чтобы бюджет ловил **чужое**, а не мешал **своему**.
260 КБ для первой загрузки — это не «плюс тридцать процентов на всякий
случай»: `pdf-lib` весит 500 КБ gzip и в такой бюджет не помещается ни
при каких обстоятельствах. Именно это однажды и произошло — до PROMPT 30
главный чанк весил 695 КБ gzip, потому что баррель `src/export/index.ts`
реэкспортировал `pdf.ts`.

Обоснованный рост не запрещён. Запрещён рост **незамеченный**.

## CI

```
Команда:          npm run check:bundle
Задача:           verify, шаг «Размер главного чанка»
Блокирует:        ДА
Источник бюджета: performance/bundle-baseline.json
```

Отдельной сборки проверка не требует: работает по `dist/`, который уже
собран предыдущим шагом.

При превышении выводится не «проверка не прошла», а метрика, текущее
значение, бюджет, превышение в килобайтах и процентах, отклонение от
базы, три самых крупных вкладчика и объяснение, зачем этот бюджет
существует.

## Updating Baseline

Законный путь ровно один:

1. Убедиться, что рост **обоснован**: новая возможность, а не случайно
   въехавшая зависимость. Если непонятно, откуда килобайты, — это
   регрессия, а не новая база.
2. Обновить `baseline` в `performance/bundle-baseline.json`.
3. Если изменился и потолок — обновить `budget` и объяснить, почему
   новый выбран именно таким.
4. Обновить таблицы в этом документе.
5. Записать причину в `CHANGELOG.md`.

Молча поднять бюджет, чтобы прогон стал зелёным, — то же самое, что
удалить проверку. Бюджет затем и нужен, чтобы разговор состоялся.

## Limitations

Честно о том, что НЕ автоматизировано.

### Время выполнения в браузере — не автоматизировано надёжно

**Runtime performance: NOT RELIABLY AUTOMATED.**

Абсолютные пороги вроде «страница открывается за 100 мс» на общем
железе CI не измеряют продукт — они измеряют, насколько занят раннер в
эту минуту. Такой порог краснел бы случайно и приучил бы не смотреть на
проверки, а это хуже отсутствия проверки.

Что вместо этого есть и работает:

| Проверка | Где | Что даёт |
| --- | --- | --- |
| Сборка сцены растёт линейно, а не квадратично | `tests/unit/scene/performance.test.ts` | ловит алгоритмическую регрессию, а не колебания машины |
| Большой проект собирается за разумное время | там же | грубый предохранитель без ложных срабатываний |
| Попадание луча укладывается в кадр | там же | интерактивность на большом проекте |
| Геометрия крупных проектов | `tests/unit/geometry/performance.test.ts` | то же для расчёта |
| Приложение становится интерактивным | дымовая проверка по живому адресу | правка габарита доходит до сцены |

Это соотношения и факты, а не миллисекунды. Они устойчивы к нагрузке
раннера — и потому им можно верить.

### Холодная и тёплая загрузка

Дымовая проверка открывает приложение в **чистом** браузере Playwright:
кэша нет, service worker не установлен. Это холодная загрузка.

Отдельного измерения тёплой загрузки нет: кэш браузера — не оптимизация
базы, и выдавать результат с прогретым кэшем за холодный старт нельзя.
Поведение с уже установленным воркером проверяется отдельно и по
существу — сценариями работы без сети (`docs/PWA_OFFLINE.md`), а не
секундомером.

### Мобильное устройство

Мобильный критический путь проверяется на трёх ширинах эмуляцией
(`tests/e2e/mobile.spec.ts`: 375, 390, 430 px). Настоящего устройства и
настоящей мобильной сети в проверках нет — и размер сборки для десктопа
не выдаётся за доказательство хорошего мобильного опыта.
