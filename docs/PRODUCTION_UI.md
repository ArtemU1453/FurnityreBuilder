# Production UI

Производственный интерфейс: восемь разделов поверх уже существующих
расчётов.

Чертежи — `PRODUCTION_DRAWINGS.md`. Присадка — `DRILLING_UI.md`. Раскрой —
`CUTTING_UI.md`. Связи между объектами — `PRODUCTION_TRACEABILITY.md`.
Сам расчёт — `PRODUCTION_CALCULATION_PIPELINE.md`, готовность —
`PRODUCTION_READINESS.md`.

---

## 1. НОВЫХ ДВИЖКОВ НЕТ НИ ОДНОГО

```
Geometry → Production Parts → Hardware → Drilling → Cutting → BOM
                                                                ↓
                                              Production UI (этот слой)
```

Интерфейс не считает ничего. Все числа — из
`ProductionCalculationResult`: размеры, количества, координаты отверстий,
раскладка, отход, использование листа. Раздел, который считает сам, рано
или поздно расходится с документом, который он обещает.

Что здесь появилось нового: **порядок**, **отбор** и **связи**.

| Появилось          | Где                                  | Что это                                                  |
| ------------------ | ------------------------------------ | -------------------------------------------------------- |
| Разделы            | `src/app/production/sections.ts`     | восемь имён и их порядок, чистый модуль                  |
| Отбор и сортировка | `src/app/production/parts-view.ts`   | поиск, фильтр, порядок строк — над готовой спецификацией |
| Трассируемость     | `src/app/production/traceability.ts` | чтение уже существующих ссылок                           |
| Модель чертежа     | `src/export/part-drawing.ts`         | одна на экран и на PDF                                   |
| Экраны             | `src/app/screens/production/`        | React поверх всего перечисленного                        |

## 2. ОДИН РАСЧЁТ НА ВСЁ ПРИЛОЖЕНИЕ

`calculateProduction` вызывается в `App.tsx` ровно один раз за изменение
модели, и его результат читают:

- индикатор готовности в строке состояния;
- чеклист готовности;
- все восемь разделов производства;
- экспорт в PDF и XLSX.

До PROMPT 29 результат считался и **выбрасывался**: проверка готовности
брала из него только статус, а экспорт запускал конвейер заново. Восемь
разделов, каждый со своим вызовом, означали бы восемь конвейеров, и выбор
детали запускал бы их все (§43).

Кэшем это не является. Результат по-прежнему выводится из проекта и нигде
не хранится; `useMemo` только не даёт посчитать одно и то же дважды в
пределах одной и той же модели.

## 3. ВОСЕМЬ РАЗДЕЛОВ

| Раздел       | Что показывает                              | Откуда данные                           |
| ------------ | ------------------------------------------- | --------------------------------------- |
| Сводка       | готовность и количества одним экраном       | `bom`, `readiness`                      |
| Детали       | позиции деталировки, поиск, фильтр, порядок | `bom.parts`                             |
| Чертежи      | контур, отверстия, размеры выбранной детали | `part-drawing.ts`                       |
| Присадка     | операции, конфликты, правила                | `calculation.drilling`                  |
| Раскрой      | листы, размещение, отход, неразмещённые     | `calculation.cutting`                   |
| Фурнитура    | позиции и их источники                      | `calculation.hardware`                  |
| Спецификация | материалы, кромка, итог                     | `bom.cutting.stocks`, `bom.edgeBanding` |
| Документы    | PDF и XLSX                                  | `export/`                               |

Разделы живут **внутри** существующего экрана «Производство», рядом с
шагами сценария. Своей навигации верхнего уровня, своего состояния
документа и своей истории у них нет — это не приложение внутри
приложения (§2).

На телефоне разделы выбираются списком, а не восемью сегментами: восемь
целей для пальца в строку не помещаются (§40).

## 4. СОСТОЯНИЕ РАСЧЁТА, А НЕ «ПЕРЕСЧИТАТЬ»

Показывается настоящее состояние: `ProductionCalculationResult.status`
(`VALID` / `VALID_WITH_WARNINGS` / `NEEDS_CONFIRMATION` / `INVALID`) и
`ProductionReadinessResult.status` — оба уже существуют и оба выводятся
из данных.

Кнопки «Пересчитать» нет, и это не упущение. Производственные величины
производны: они выводятся из проекта в момент показа и нигде не хранятся.
Поэтому:

- «устаревшего результата» не бывает — его негде взять (§33);
- состояния «не посчитано» не существует — расчёт есть всегда, когда есть
  изделие;
- кнопка, которая гарантированно ничего не меняет, — ложное обещание,
  что бывает иначе.

Замер конвейера на изделии из 68 деталей: **2.6 мс**. Прогресса по этапам
показывать нечего — расчёт заканчивается быстрее, чем успевает
отрисоваться индикатор, и рисовать шкалу ради шкалы значило бы выдумать
процесс (§36).

## 5. ТАБЛИЦЫ, А НЕ ERP

Деталировка — это именно таблица: десять сопоставимых колонок, которые
читают сверху вниз. Ни рамок вокруг каждой ячейки, ни чередующихся полос,
ни цветовой заливки строк: строка отделена от строки волосяной линией,
числа выровнены по правому краю моноширинными цифрами.

Горизонтальная прокрутка оставлена только у таблицы деталировки и только
потому, что карточка вместо строки ломает сравнение по колонке (§31).
Прокручивается сама таблица, а не страница.

Цен, поставщиков, складских остатков и закупок здесь нет и не будет
(§48).

## 6. ДОСТУПНОСТЬ

- Таблицы — настоящие `<table>` с `<caption>`, `scope="col"` и
  `scope="row"`: скринридер сообщает колонку при переходе по строке.
- Каждый svg (чертёж, карта раскроя) несёт текстовое описание своих
  данных — не подпись «схема», а габарит, материал, кромка и каждое
  отверстие с координатами.
- Число найденных позиций объявляется через `role="status"`: результат
  поиска не только виден, но и слышен.
- Выбор строки — кнопка с `aria-pressed`, а не подсветка мышью.
- Анимаций в производственных разделах нет вовсе, поэтому
  `prefers-reduced-motion` соблюдается по построению.
