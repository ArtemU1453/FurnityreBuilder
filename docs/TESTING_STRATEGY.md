## 1. ПРИНЦИПЫ

1. **Тест проверяет свойство, а не факт вызова.** Мок, подтверждающий, что
   функция была вызвана, не доказывает, что мебель посчитана верно.
2. **Тестов ради количества не бывает.** Каждый тест здесь можно назвать
   одним предложением: что сломается, если его удалить.
3. **Геометрия покрывается до появления интерфейса.** Формула, проверенная
   глазами на экране, не проверена.
4. **Архитектурные правила проверяются тестом.** Правило, которое держится
   на дисциплине, перестаёт держаться в первый занятый день.
5. **Конфигурацию не ослабляют ради зелёного прогона.** Если тест падает —
   правят код или формулировку свойства, а не порог.

## 4. PROPERTY-ТЕСТЫ

Ключевой инструмент для геометрии: перебор примеров не находит того,
что находит перебор входов.

Проверяемые свойства:

1. **После нормализации любое конечное число лежит на сетке 0.1 мм**
   и отличается от исходного не более чем на допуск.
2. **Сумма ячеек и разделителей равна доступной длине** — для любой
   выполнимой раскладки.
3. **Невыполнимая раскладка помечается, а не выдаётся за верную**,
   и размеры ячеек не уходят в минус.
4. **Ячейки идут подряд** без наложений и разрывов.

### Что property-тест уже нашёл

Свойство 2 упало на входе `available = 100, count = 4, thickness = 33.35`.
Разбор показал две разные вещи:

- `resolveSizes` нормализовала только результат, но не вход. Ненормализованная
  толщина (например, материал 3.14 мм) давала расхождение, накапливающееся
  по числу разделителей. **Исправлено в функции**, а не в тесте.
- Сам инвариант был сформулирован слишком широко: когда одни только
  разделители не помещаются в длину, сумма сойтись не может по определению.
  Свойство разделено на два: инвариант суммы для выполнимой раскладки
  и отдельная проверка, что невыполнимая помечается флагом.

Это ровно та ошибка, которую пример-ориентированный тест не поймал бы:
все написанные вручную случаи проходили.

### Property-тесты геометрического движка (PROMPT 3)

`tests/unit/geometry/properties.test.ts` и `serialization-roundtrip.test.ts`:

1. **Недопустимый вход никогда не даёт геометрию** — для любого из четырёх
   базовых параметров, гарантированно испорченного (ноль, отрицательное
   число, NaN, ±Infinity), результат — пустой список деталей, ошибка
   в диагностике, вырожденный bounding box.
2. **Допустимый вход всегда даёт валидную геометрию** — для любых габаритов
   и любой из трёх схем стыка: детали конечны, положительны по размеру,
   неотрицательны по координате, уникальны по id, не выходят за номинальный
   габарит.
3. **Внутренний объём положителен и вложен в номинальный габарит.**
4. **Детерминизм** — одинаковый вход даёт побайтово одинаковый результат.
5. **Круговой путь через сериализацию не меняет `GeometryResult`** — для
   произвольного валидного проекта.

### Второй раз то же самое: `carcass.ts`

Свойство 2 упало на входе `panelThickness = 8.25, width = 36.5`. Толщина
материала не лежала на сетке 0.1 мм. `carcass.ts` брал её «сырой» и
округлял НЕЗАВИСИМО в двух местах: при вычислении позиции правой боковины
(`W − T`) и при вычислении её размера (`T`). Два округления разошлись
в одну сторону, и правая боковина оказалась на 0.1 мм за пределами
заявленной ширины (`36.6` вместо `36.5`).

Это тот же класс дефекта, что и в `resolveSizes` на PROMPT 2: нормализовать
нужно **вход**, а не только каждый промежуточный результат. Исправление —
одна правка в начале `carcassStage.run()`: округлить `W, H, D, T` один раз
и переиспользовать. Подробности — `docs/GEOMETRY_RULES.md` §4.1.

Два независимых подтверждения одного и того же принципа на двух разных
модулях — сильный аргумент в пользу property-тестирования как обязательного,
а не опционального инструмента для любой новой геометрической формулы.

### Третий раз: сетка (PROMPT 4) — на этот раз ничего не нашёл

`tests/unit/geometry/grid-properties.test.ts` прогнал стадию `layout` через
тысячи случайных сочетаний `rows`/`columns`/`width`/`height` (при
гарантированно достаточном для минимального размера ячейки габарите) и
проверил отсутствие NaN/Infinity, положительность размеров, неотрицательность
координат, уникальность id ячеек и деталей, принадлежность `row`/`column`
границам сетки, невыход ячеек за номинальный габарит и побайтовый
детерминизм. Ни одного дефекта не найдено — стадия `layout` переиспользует
уже property-тестированный `resolveSizes` и уже исправленную нормализацию
входа каркаса, поэтому ожидаемо унаследовала их корректность, а не привнесла
новый класс ошибок. Это не повод отказаться от property-теста в следующий
раз: два предыдущих случая нашли дефекты именно там, где интуиция
подсказывала «код очевидно верен».

### Шестой раз: неравномерные размеры (PROMPT 8) — дефект нашёлся не в коде, а в покрытии

`variable-size-properties.test.ts` генерирует массивы РАЗНЫХ размеров и
подбирает габарит под них. Все свойства прошли сразу — но подготовка к ним
вскрыла другое: до PROMPT 8 ни один тест не строил деление, состоящее
только из `fixed`-детей. Все фабрики создавали `flex`, и потому случай
«размеры заданы, но не заполняют доступное место» никогда не проверялся —
а движок в нём молча строил геометрию с невидимым зазором, не нарушая
ни одного зелёного теста.

Урок противоположен предыдущим пяти: property-тест не нашёл дефект в
формуле, зато сам вопрос «а какие входы мои тесты вообще никогда не
подавали» нашёл дыру, которую формулы не закрывали. Диагностика
`SPLIT_UNDERCONSTRAINED` появилась именно оттуда.

### Пятый раз: секции и перегородки (PROMPT 7) — дефектов нет

`partition-properties.test.ts` прогнал случайные сочетания `sectionCount`
(1–8), толщины материала (8–24 мм) и габаритов и потребовал: секций ровно
столько, сколько задано; перегородок на одну меньше; все размеры
положительны и конечны; id уникальны; каждая секция и каждая перегородка
вложены во внутренний объём; ни одна деталь не пересекает другую; и —
самое существенное — `sum(секций) + перегородки + боковины = W` ТОЧНО,
при любой толщине, а не только при 16 мм. Дефектов не найдено: раскладка
секций опирается на тот же `resolveSizes`, который уже прошёл через два
найденных property-тестами дефекта на PROMPT 2–3.

### Четвёртый раз: полки (PROMPT 6) — снова ничего не нашёл, и это ожидаемо

`tests/unit/geometry/fill-properties.test.ts` прогнал этап `fill` через
случайные сочетания числа полок и габаритов: конечность, положительность,
уникальность id, вложенность полки в свою ячейку и в габарит, детерминизм.
Дефектов нет — по той же причине, что и на PROMPT 4: размещение полок
не пишет новой формулы, а вызывает уже property-тестированный
`resolveSizes` (docs/GEOMETRY_RULES.md §14.7).

Это и есть практический аргумент за переиспользование: каждая формула,
написанная заново «потому что случай немного другой», требовала бы
собственного цикла «property-тест → найденный дефект → исправление».
Реальный дефект на этом этапе нашёлся не в коде, а в ЧЕРНОВИКЕ формулы
из документации (`ARCHITECTURE.md` §5.7 давал первую полку впритык к низу
ячейки, без промежутка под ней) — и не попал в код именно потому, что
реализация не стала его повторять.

## 5. АРХИТЕКТУРНЫЕ ТЕСТЫ

`tests/unit/architecture/boundaries.test.ts` запускает ESLint через его API
на временных файлах-пробах и проверяет, что нарушение границы **действительно
даёт ошибку**.

Зачем это, если правило уже настроено в линтере: конфигурацию легко сломать
незаметно. Достаточно опечатки в шаблоне пути — правило перестаёт находить
файлы и продолжает «проходить». Именно это здесь и ловится.

Проверяется:

## 6. КОНТРАКТНЫЕ ТЕСТЫ

`InMemoryProjectRepository` и `IndexedDbProjectRepository` проверяются
**одним и тем же набором из шести тестов**. Смысл абстракции в том, что
вызывающий код их не различает; тест это и утверждает.

IndexedDB эмулируется через `fake-indexeddb`. Перед каждым тестом хранилище
очищается через публичный API — оно живёт на весь модуль, и без очистки
тесты влияли бы друг на друга (что и произошло при первом прогоне).

## 7. ЧТО ПРОВЕРЯЕТСЯ В E2E

E2E-сценариев намеренно немного: интерфейса конструктора ещё нет.
Проверяется то, что уже должно быть верным и что дорого чинить потом.

| Сценарий | Зачем |
| --- | --- |
| Приложение запускается и показывает расчёт | сквозной путь домен → геометрия → экран работает |
| **Ни одного внешнего запроса** | автономность продукта; сильнее любой проверки исходников |
| Изменение габарита пересчитывает сразу | отсутствие debounce на пути «поле → схема» |
| Отмена возвращает состояние | история работает в реальном браузере |
| Ошибка объясняется текстом и не блокирует ввод | цвет не единственный носитель смысла; принцип Agency |
| Доступность с клавиатуры, ссылка пропуска навигации | доступность не откладывается «на потом» |
| Кнопки отключены, пока нечего отменять | состояние `disabled` соответствует модели |

Отдельный Playwright-проект `chromium-dev` (dev-сервер, а не собранный
production preview) добавлен на PROMPT 4 для debug-схемы — она существует
только при `import.meta.env.DEV` и не может быть проверена в
production-конфигурации:

| Сценарий (`tests/e2e/debug-schema.spec.ts`) | Зачем |
| --- | --- |
| Debug-схема видна в `DEV` и отсутствует в production preview | `import.meta.env.DEV`-гейтинг не сломан рефакторингом |
| Изменение строк/колонок сетки перерисовывает схему без перезагрузки | путь «поле → SetRoot → geometry → SVG» работает целиком |
| Число `rect`-элементов схемы соответствует числу деталей + ячеек | схема не теряет и не дублирует элементы при рендере |
| Полки появляются в схеме отдельными деталями и подписываются (PROMPT 6) | путь «поле → fill-этап → Part → SVG» работает целиком, полка отличима от пустого проёма |
| Изменение числа секций 1 → 3 → 1 перестраивает перегородки и подписи (PROMPT 7) | путь «поле → SetSectionCount → секции → перегородки → SVG» работает в обе стороны, лишних деталей после уменьшения не остаётся |
| Индивидуальные ширины секций применяются, несходящаяся сумма объясняется текстом, одна отмена возвращает набор (PROMPT 8) | путь «поле → SetChildSize по id → геометрия → SVG» работает; ошибка расчёта видна пользователю, а не оставляет пустую схему |
| Наполнение ячейки подписано в схеме и меняется вместе с моделью (PROMPT 9) | связь Content → Cell видна на экране: пустая ячейка отличима от ячейки с полками без чтения кода |
| Переключатель debug-информации показывает/скрывает размерные линии и id | debug-режим — явный переключатель, а не всегда включённый режим |

## 8. ЧЕГО МЫ НЕ ДЕЛАЕМ

| Практика | Почему нет |
| --- | --- |
| Снапшоты целых объектов «на всякий случай» | ломаются от любой правки и ничего не объясняют |
| Моки внутри домена | домен чист, мокать нечего |
| Тесты на приватные функции | проверяется поведение через публичную границу |
| Порог покрытия в процентах | стимулирует писать тесты на геттеры вместо инвариантов |
| `expect(fn).toHaveBeenCalled()` как основная проверка | не доказывает корректность результата |

## 9. ЗАПУСК

```bash
npm run verify      # весь набор проверок в порядке возрастания стоимости
npm run test        # unit
npm run test:watch  # unit в режиме наблюдения
npm run test:e2e    # E2E (нужен собранный проект — Playwright соберёт сам)
```

`npm run verify` выполняет: реестр предположений → lint → typecheck →
unit-тесты → сборка → проверка самостоятельности собранного артефакта.
Порядок соответствует стоимости: дешёвые проверки падают первыми.

E2E запускается отдельно, потому что требует браузера. В средах
с предустановленным Chromium путь задаётся переменной
`PLAYWRIGHT_CHROMIUM_PATH`.
