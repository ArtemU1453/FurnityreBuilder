# Стратегия тестирования

Состояние на конец этапа «Архитектурный фундамент»:
**135 unit-тестов в 15 файлах, 7 E2E-сценариев. Всё зелёное.**

---

## 1. ПРИНЦИПЫ

1. **Тест проверяет свойство, а не факт вызова.** Мок, подтверждающий, что
   функция была вызвана, не доказывает, что мебель посчитана верно.
2. **Тестов ради количества не бывает.** Каждый тест здесь можно назвать
   одним предложением: что сломается, если его удалить.
3. **Геометрия покрывается до появления интерфейса.** Формула, проверенная
   глазами на экране, не проверена.
4. **Архитектурные правила проверяются тестом.** Правило, которое держится
   на дисциплине, перестаёт держаться в первый занятый день.
5. **Конфигурацию не ослабляют ради зелёного прогона.** Если тест падает —
   правят код или формулировку свойства, а не порог.

## 4. PROPERTY-ТЕСТЫ

Ключевой инструмент для геометрии: перебор примеров не находит того,
что находит перебор входов.

Проверяемые свойства:

1. **После нормализации любое конечное число лежит на сетке 0.1 мм**
   и отличается от исходного не более чем на допуск.
2. **Сумма ячеек и разделителей равна доступной длине** — для любой
   выполнимой раскладки.
3. **Невыполнимая раскладка помечается, а не выдаётся за верную**,
   и размеры ячеек не уходят в минус.
4. **Ячейки идут подряд** без наложений и разрывов.

### Что property-тест уже нашёл

Свойство 2 упало на входе `available = 100, count = 4, thickness = 33.35`.
Разбор показал две разные вещи:

- `resolveSizes` нормализовала только результат, но не вход. Ненормализованная
  толщина (например, материал 3.14 мм) давала расхождение, накапливающееся
  по числу разделителей. **Исправлено в функции**, а не в тесте.
- Сам инвариант был сформулирован слишком широко: когда одни только
  разделители не помещаются в длину, сумма сойтись не может по определению.
  Свойство разделено на два: инвариант суммы для выполнимой раскладки
  и отдельная проверка, что невыполнимая помечается флагом.

Это ровно та ошибка, которую пример-ориентированный тест не поймал бы:
все написанные вручную случаи проходили.

## 5. АРХИТЕКТУРНЫЕ ТЕСТЫ

`tests/unit/architecture/boundaries.test.ts` запускает ESLint через его API
на временных файлах-пробах и проверяет, что нарушение границы **действительно
даёт ошибку**.

Зачем это, если правило уже настроено в линтере: конфигурацию легко сломать
незаметно. Достаточно опечатки в шаблоне пути — правило перестаёт находить
файлы и продолжает «проходить». Именно это здесь и ловится.

Проверяется:

| Проба | Ожидание |
| --- | --- |
| React в `src/geometry` | `no-restricted-imports` |
| React в `src/domain` | `no-restricted-imports` |
| `geometry` импортирует `state` | `boundaries/element-types` |
| `domain` обращается к `window` | `no-restricted-globals` |
| `validation` обращается к `localStorage` | `no-restricted-globals` |
| `geometry` импортирует `domain` | **ошибок нет** — законное направление |

Последняя проба обязательна: без неё тест проходил бы и при правиле,
запрещающем вообще всё.

## 6. КОНТРАКТНЫЕ ТЕСТЫ

`InMemoryProjectRepository` и `IndexedDbProjectRepository` проверяются
**одним и тем же набором из шести тестов**. Смысл абстракции в том, что
вызывающий код их не различает; тест это и утверждает.

IndexedDB эмулируется через `fake-indexeddb`. Перед каждым тестом хранилище
очищается через публичный API — оно живёт на весь модуль, и без очистки
тесты влияли бы друг на друга (что и произошло при первом прогоне).

## 7. ЧТО ПРОВЕРЯЕТСЯ В E2E

E2E-сценариев намеренно немного: интерфейса конструктора ещё нет.
Проверяется то, что уже должно быть верным и что дорого чинить потом.

| Сценарий | Зачем |
| --- | --- |
| Приложение запускается и показывает расчёт | сквозной путь домен → геометрия → экран работает |
| **Ни одного внешнего запроса** | автономность продукта; сильнее любой проверки исходников |
| Изменение габарита пересчитывает сразу | отсутствие debounce на пути «поле → схема» |
| Отмена возвращает состояние | история работает в реальном браузере |
| Ошибка объясняется текстом и не блокирует ввод | цвет не единственный носитель смысла; принцип Agency |
| Доступность с клавиатуры, ссылка пропуска навигации | доступность не откладывается «на потом» |
| Кнопки отключены, пока нечего отменять | состояние `disabled` соответствует модели |

---

## 8. ЧЕГО МЫ НЕ ДЕЛАЕМ

| Практика | Почему нет |
| --- | --- |
| Снапшоты целых объектов «на всякий случай» | ломаются от любой правки и ничего не объясняют |
| Моки внутри домена | домен чист, мокать нечего |
| Тесты на приватные функции | проверяется поведение через публичную границу |
| Порог покрытия в процентах | стимулирует писать тесты на геттеры вместо инвариантов |
| `expect(fn).toHaveBeenCalled()` как основная проверка | не доказывает корректность результата |

## 9. ЗАПУСК

```bash
npm run verify      # весь набор проверок в порядке возрастания стоимости
npm run test        # unit
npm run test:watch  # unit в режиме наблюдения
npm run test:e2e    # E2E (нужен собранный проект — Playwright соберёт сам)
```

`npm run verify` выполняет: реестр предположений → lint → typecheck →
unit-тесты → сборка → проверка самостоятельности собранного артефакта.
Порядок соответствует стоимости: дешёвые проверки падают первыми.

E2E запускается отдельно, потому что требует браузера. В средах
с предустановленным Chromium путь задаётся переменной
`PLAYWRIGHT_CHROMIUM_PATH`.
