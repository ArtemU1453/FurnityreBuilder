# Выпуск версии

PROMPT 43. Как продукт получает номер, тег и подтверждённое присутствие в
production — и как вернуться назад.

## Выкладка и выпуск — разные вещи

Их легко спутать, и путаница дорого стоит.

| | Непрерывная выкладка | Выпуск |
| --- | --- | --- |
| Что запускает | push в ветку по умолчанию | тег `vX.Y.Z`, поставленный руками |
| Как часто | на каждый коммит | когда есть что выпускать |
| Что получается | обновлённое приложение по боевому адресу | версия, тег, GitHub Release, заметки |
| Зачем | быстро довозить исправления | воспроизводить дефект, подтверждать откат, знать, что у человека в браузере |

**Коммит ≠ выпуск.** Оба механизма работают одновременно и не мешают друг
другу: выкладка отвечает за «свежее», выпуск — за «опознаваемое».

## Version Source

Единственное место, где объявлена версия:

```
package.json → "version"
```

Оттуда она попадает во всё остальное:

| Куда | Как |
| --- | --- |
| Сборка | `vite.config.ts`, `define: __APP_VERSION__` |
| Интерфейс | строка состояния, `v{APP_VERSION}` |
| Имя кэша service worker'а | `scripts/build-sw.mjs` |
| Тег и GitHub Release | сверяются с `package.json` в `release.yml` |

Второго объявления нет и не заводится: два места расходятся при первом же
выпуске. Подстановку сторожит `npm run check:release` — он отказывает,
если версии из `package.json` нет в главном чанке или если там осталось
запасное `0.0.0-dev`.

## Versioning Rules

Семантические версии, `MAJOR.MINOR.PATCH`.

| Часть | Когда растёт |
| --- | --- |
| `PATCH` | исправления дефектов, правки CI и выкладки, документация — ничего не ломается |
| `MINOR` | новая возможность, старые проекты открываются как прежде |
| `MAJOR` | ломающее изменение: формат проекта, поведение расчёта, удалённая возможность |

Версия отражает **выпуск**, а не количество коммитов. Десять исправлений
подряд — это по-прежнему один `PATCH`, когда их выпускают вместе.

Отдельно про формат проекта: он версионируется своей схемой
(`docs/PROJECT_PERSISTENCE.md` §6) и читается миграциями. Смена версии
приложения сама по себе проекты не ломает.

## Release Steps

Шаги настоящие, команды существуют.

```bash
# 1. Версия
npm version patch --no-git-tag-version   # или minor / major

# 2. Заметки: перенести накопленное из [Unreleased] в новый раздел
$EDITOR CHANGELOG.md

# 3. Ворота качества целиком
npm ci
npm run verify
npx playwright test --project=chromium
npx playwright test --project=chromium-dev

# 4. Коммит выпуска
git add -A
git commit -m "Выпуск 0.2.0"
git push origin claude/furniture-designer-audit-cjvvuf

# 5. Дождаться зелёного прогона CI на этом коммите.
#    Он же выложит версию на боевой адрес и проверит её дымовой проверкой.

# 6. Тег — ТОЛЬКО на проверенном коммите
git tag -a v0.2.0 -m "Furniture Builder 0.2.0"
git push origin v0.2.0
```

Шаг 6 запускает `.github/workflows/release.yml`.

## Git Tag

Формат `vMAJOR.MINOR.PATCH`, аннотированный тег. Тег указывает на один
коммит и после публикации **не меняется**.

Ошиблись — выпускается новая версия. Переставить опубликованный тег
нельзя: по нему уже могли скачать, сослаться, подтвердить откат.
`release.yml` это и охраняет: если выпуск с таким тегом уже есть, он
падает вместо перезаписи.

Запрещено, и не «нежелательно»:

- `git push --force` по тегу выпуска;
- удалить и создать заново опубликованный тег;
- поменять содержимое старой версии без нового номера.

## CI Requirements

Выпуск не делается на непроверенном дереве. `release.yml` перед созданием
выпуска выполняет:

1. **Тег совпадает с версией** — `v0.2.0` при `"version": "0.1.0"`
   невоспроизводим: в интерфейсе будет один номер, в выпуске другой.
2. **`npm run verify`** — десять ворот: реестр предположений, линтер,
   типы, тесты, сборка, самостоятельность, размер чанка, готовность
   пакета, целостность публичного входа.
3. **Раздел в CHANGELOG существует** — выпуск без заметок не создаётся.

Прогоны E2E к этому моменту уже прошли: тег ставится на коммит, который
проверил обычный CI (`docs/CI_QUALITY_GATES.md`).

## Deployment

Публикация версии происходит **не** по тегу, а по тому push, которым
коммит выпуска попал в ветку по умолчанию:

```
push  →  verify  →  build-pages  →  deploy  →  smoke
```

Тег добавляет к уже опубликованной версии опознавательные знаки, а не
выкладывает её заново. Так исключён случай «тег есть, а в production
другое».

## Production Verification

После выкладки задача `smoke` проверяет по живому адресу:

- приложение открывается, оболочка не пустая, критические файлы доехали;
- одно настоящее действие проходит;
- **в интерфейсе показана та самая версия** — сверяется с `package.json`;
- ссылка в README ведёт на фактический адрес выкладки;
- ни одной критической ошибки в консоли и сети.

Упала дымовая проверка — выпуск не подтверждён, даже если тег создан.

## Rollback

Возврат — по номеру версии, а не поиском неизвестного коммита.

```bash
# 1. Какая версия была предыдущей стабильной
git tag -l 'v*' --sort=-v:refname

# 2. Что в ней было
git show v0.1.0 --stat

# 3. Вернуть состояние этой версии
git revert <коммиты после v0.1.0>       # или
git checkout v0.1.0 -- <затронутые пути>

git commit -m "Откат к состоянию 0.1.0"
git push origin claude/furniture-designer-audit-cjvvuf
```

Дальше всё идёт само: `verify → build-pages → deploy → smoke`.

Три вещи, о которых стоит знать заранее:

1. **Откат проходит те же ворота.** Ломает проверки — публикации не
   будет, и это правильно.
2. **Проекты пользователей не затрагиваются.** Код в Cache Storage,
   проекты в IndexedDB.
3. **Номер версии после отката не уменьшается.** Возврат кода — это новый
   выпуск (`0.2.1`), а не воскрешение `0.1.0`: две разные сборки под
   одним номером не воспроизводимы. Отсюда и правило «каждая исправленная
   production-версия получает новую identity».

## Что здесь НЕ автоматизировано — и почему

**Тег ставится руками.** Автоматический тег на каждый push превратил бы
выпуск в счётчик коммитов и обесценил бы сам номер. Решение «это выпуск»
принимает человек.

**Заметки выпуска не сочиняются.** `release.yml` берёт готовый раздел из
`CHANGELOG.md` и падает, если его нет. Придуманный автоматически список
изменений хуже отсутствующего: ему верят.
