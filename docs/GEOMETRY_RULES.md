# Правила геометрии

Формулы геометрического движка: назначение, вход, формула, единицы,
результат, ограничения, пример, источник. Реализация — `src/geometry/`.
Трассируемость к спецификации и тестам — §10.

**Правило документа.** Формула без подтверждённого источника помечается
`UNKNOWN` с указанием теста, который её установит. Ни одна формула здесь
не выдумана — см. `docs/PRIVETMAKET_FUNCTIONAL_SPEC.md` §0 о недоступности
референса и `docs/UNKNOWNS.json` о статусе каждого предположения.

---

## 0. КОНТРАКТ ДВИЖКА

```ts
function buildGeometry(input: GeometryInput): GeometryResult
```

Чистая, детерминированная функция: не читает часы, не генерирует случайных
значений, не обращается к DOM. Не зависит от React. Полный контракт —
`docs/ARCHITECTURE.md` §5, типы — `src/geometry/types.ts`.

```ts
interface GeometryResult {
  parts: readonly Part[];
  cells: readonly CellBox[];
  bounds: Box3;             // заявленный габарит W×H×D
  innerVolume: Box3;        // внутренний объём корпуса
  boundingBox: BoundingBox; // измеренный охват построенных деталей — см. §6
  diagnostics: readonly Issue[];
  pendingStages: readonly string[];
}
```

Единицы — миллиметры, шаг сетки 0.1 мм. Система координат — правая тройка,
начало в левом–нижнем–заднем углу изделия целиком, `y` вверх, `z` от задней
стенки к пользователю. Полное описание — `docs/COORDINATE_SYSTEM.md`,
правила округления — `docs/UNITS_AND_PRECISION.md`.

## 1. БАЗОВЫЕ ПАРАМЕТРЫ

| Параметр | Тип | Единица | Источник |
| --- | --- | --- | --- |
| `width` (W) | `Mm` | мм | `Dimensions.width`, CONFIRMED — поле есть в референсе |
| `height` (H) | `Mm` | мм | `Dimensions.height`, CONFIRMED |
| `depth` (D) | `Mm` | мм | `Dimensions.depth`, CONFIRMED |
| `panelThickness` (T) | `Mm` | мм | `Dimensions.panelThickness`, CONFIRMED (толщина ЛДСП — типовой параметр отрасли) |

Других базовых параметров не добавлено. Ни один дополнительный размерный
параметр (свес столешницы, отступ цоколя и т. п.) не подтверждён референсом
на момент этого этапа — см. `docs/UNKNOWNS.json`. Правило PROMPT 3 §3
(«дополнительные параметры — только подтверждённые») выполняется
буквально: список параметров не расширился.

Границы значений (`DIMENSION_LIMITS` в `src/domain/furniture/defaults.ts`) —
`ASSUMPTION(T-DIM-01)`, мягкие: выход за диапазон даёт `warning`, не `error`.
Реализация — `normalize.ts`, §3 ниже.

## 2. АВАРИЙНАЯ ОСТАНОВКА

**Назначение.** Гарантировать, что недопустимый вход даёт структурированную
ошибку, а не геометрию, посчитанную поверх непригодных чисел.

**Правило.** Как только конвейер накапливает диагностику с `severity: 'error'`,
все последующие этапы пропускаются. `GeometryResult.parts` для такого входа
пуст, `bounds`/`innerVolume`/`boundingBox` вырождены в нулевую точку.

**Реализация.** `GeometryContext.hasFatalError()` (обёртка над `hasErrors()`
из `src/domain/diagnostics.ts`); проверяется в цикле `buildGeometry()`
(`src/geometry/engine.ts`) перед запуском каждого реализованного этапа.

**Почему не частичный результат.** Рассмотренная альтернатива — строить то,
что ещё можно построить (например, боковины при некорректной ширине, раз они
не зависят от неё). Отклонена: результат «две боковины без верха и низа»
не является осмысленной частью мебели, а его молчаливое появление в
`parts` создаёт риск, что вызывающий код примет частичный список за полный.
Явно пустой результат безопаснее.

**Обнаружено при реализации.** До этого этапа отрицательная ширина не
останавливала расчёт: боковина «Боковина правая» получала
`position.x = -116` при `width = -100`, и деталь с отрицательной координатой
всё равно попадала в `GeometryResult.parts` рядом с диагностикой об ошибке.
Найдено при подготовке этого этапа, до появления в проверенном коде.

**Источник.** N/A — инженерное правило продукта (PROMPT 3 §11–12), не из
референса.

**Тест.** `tests/unit/geometry/invariants.test.ts` (раздел «аварийная
остановка»), `tests/unit/geometry/edge-cases.test.ts`,
`tests/unit/geometry/properties.test.ts` (property «недопустимый вход
никогда не даёт геометрию»).

**Область действия.** Это правило — про переход МЕЖДУ этапами конвейера
(`normalize` → `carcass` → `layout`). Внутри одного этапа, при обходе
дерева секций, действует более мягкая, локальная версия того же принципа —
см. §9.8.

## 3. ВАЛИДАЦИЯ ВХОДА (`normalize`)

Реализация — `src/geometry/stages/normalize.ts`. Первый этап конвейера.

### 3.1 Финитность

**Формула.** Для каждого из `width, height, depth, panelThickness`:
`Number.isFinite(value)`.
**Результат при нарушении.** `error` с кодом `DIMENSION_NOT_FINITE`.
**Источник.** N/A — базовое требование корректности числа, не геометрии.

### 3.2 Положительность

**Формула.** `value > 0` (через `gtMm`, с допуском `MM_EPSILON = 0.05`).
**Результат при нарушении.** `error` с кодом `DIMENSION_NOT_POSITIVE`.
**Источник.** N/A.

### 3.3 Совместимость ширины с толщиной каркаса

**Формула.** `width > panelThickness × 2`.
**Обоснование.** Две боковины толщиной T занимают `2T` по ширине; если
`W ≤ 2T`, внутреннего пространства для горизонталей не остаётся.
**Результат при нарушении.** `error` с кодом `WIDTH_BELOW_CARCASS`.
**Пример.** `W = 20, T = 16` → `20 ≤ 32` → ошибка.
**Источник.** Выведено из геометрии (§4), не требует внешнего подтверждения.

### 3.4 Совместимость высоты с толщиной каркаса

**Формула.** `height > panelThickness × 2`.
**Результат при нарушении.** `error` с кодом `HEIGHT_BELOW_CARCASS`.
**Источник.** Аналогично §3.3.

### 3.5 Рекомендуемый диапазон

**Формула.** `value ∈ [min, max]` из `DIMENSION_LIMITS`:

| Параметр | min | max |
| --- | --- | --- |
| width | 100 | 6000 |
| height | 100 | 3000 |
| depth | 80 | 1200 |

**Результат при нарушении.** `warning` с кодом `DIMENSION_OUT_OF_RECOMMENDED_RANGE`
— **не блокирует расчёт** (принцип Agency, `docs/DATA_MODEL.md` §12).
**Источник.** `ASSUMPTION(T-DIM-01)` — границы референса не установлены.
**Тест.** T-DIM-01 в `docs/UNKNOWNS.json`: ввести `1` и `99999` в поле
на живом референсе, зафиксировать значение, к которому приводится ввод.

## 4. КАРКАС (`carcass`)

Реализация — `src/geometry/stages/carcass.ts`. Второй этап конвейера.
Формулы приведены для схемы **`sides-through`** (боковины сквозные,
горизонтали между ними) — значение по умолчанию проекта. Формулы для
`horizontals-through` и `mixed` — зеркальны, приведены в конце раздела.

### 4.1 Нормализация входа

**Правило.** `W`, `H`, `D`, `T` округляются до сетки 0.1 мм ОДИН раз, в
начале этапа, и переиспользуются везде далее.
**Почему это отдельное правило.** Изначальная реализация брала `T` «сырой»
и округляла независимо в двух местах: при вычислении позиции правой
боковины (`W − T`) и при вычислении её размера (`T`). Для `T`, не лежащей
на сетке 0.1 мм (например, `T = 8.25`, если проект получен из внешнего
источника без нормализации), два округления могли разойтись в одну сторону,
и правая боковина оказывалась на 0.1 мм за пределами заявленной ширины.
**Обнаружено.** Property-тестом на этом этапе — `tests/unit/geometry/properties.test.ts`,
свойство «допустимый вход всегда даёт валидную геометрию». Тот же класс
дефекта, что и в `resolveSizes` на этапе PROMPT 2 (`docs/TESTING_STRATEGY.md` §4):
нормализовать нужно вход, а не только результат.
**Источник.** N/A — численная корректность реализации.
**Тест.** `tests/unit/geometry/properties.test.ts`.

### 4.2 Боковины

**Формула.**
```
sideHeight = (topFull ? H − T : H) − (bottomFull ? T : 0)

Боковина левая:  position = (0, sideY0, z0)         size = (T, sideHeight, Dc)
Боковина правая: position = (W − T, sideY0, z0)      size = (T, sideHeight, Dc)
```
где `sideY0 = bottomFull ? T : 0`, `topFull`/`bottomFull` — идёт ли
соответствующая горизонталь поверх боковин (см. §4.4), `z0`/`Dc` — из
геометрии задней стенки (§4.5).
**Единицы.** Миллиметры.
**Ограничения.** `sideHeight > 0` (проверено §3.4); `Dc > 0` (иначе `error`
`CARCASS_DEPTH_NOT_POSITIVE`, этап останавливается).
**Пример.** `W=1000, H=2000, D=500, T=16`, накладная задняя стенка 3 мм:
левая `position=(0,0,3)`, `size=(16,2000,497)`; правая `position=(984,0,3)`,
`size=(16,2000,497)`.
**Источник.** `ASSUMPTION(T-CAR-01)` — конвенция референса не установлена
(сайт недоступен, `docs/PRIVETMAKET_FUNCTIONAL_SPEC.md` §0). Формула выбрана
как наиболее распространённая отраслевая практика для шкафов.
**Тест.** T-CAR-01. Тест на живом референсе: `W=1000 H=2000 D=500 T=16`,
сверить размер боковины и верха в деталировке с таблицей в
`docs/ARCHITECTURE.md` §5.3, определить, какая из трёх схем подтверждается.

### 4.3 Горизонтали (верх, низ)

**Формула.**
```
x0 = spansFullWidth ? 0 : T
w  = spansFullWidth ? W : (W − 2T)

Дно:    position = (x0, 0, z0)         size = (w, T, Dc)     (если hasBottom)
Крышка: position = (x0, H − T, z0)     size = (w, T, Dc)     (если hasTop)
```
**Ограничения.** `w > 0` (защитная проверка `HORIZONTAL_WIDTH_NOT_POSITIVE`;
для `sides-through` практически недостижима после §3.3 — см. примечание ниже).
**Пример.** Продолжение примера §4.2: дно `position=(16,0,3)`,
`size=(968,16,497)`; крышка `position=(16,1984,3)`, `size=(968,16,497)`.
**Источник.** `ASSUMPTION(T-CAR-01)`, как в §4.2.
**Тест.** T-CAR-01.

**Примечание о защитных проверках.** После аварийной остановки (§2) этап
`carcass` запускается только на входе, уже прошедшем §3.3/§3.4. Проверка
`w > 0` внутри `carcass.ts` формально избыточна для текущих путей отказа,
но сохранена как защита на случай, если в будущем этап станет вызываться
с параметрами, не прошедшими `normalize` напрямую (например, при
пересчёте отдельной секции). Не удалена сознательно.

### 4.4 Кто идёт «сквозь» — выбор схемы

**Формула.**
```
sides-through:        top = false, bottom = false   (боковины сквозные)
horizontals-through:  top = true,  bottom = true     (горизонтали сквозные)
mixed:                top = scheme.topOverlaysSides
                       bottom = scheme.bottomOverlaysSides
```
**Источник.** `ConstructionScheme.verticalPriority`, параметр проекта.
`ASSUMPTION(T-CAR-01)` для значения по умолчанию (`sides-through`).
**Тест.** `tests/unit/geometry/carcass.test.ts` — все три схемы, явные
проверки размеров.

### 4.5 Задняя стенка и глубина корпуса

Реализация — `resolveBackGeometry()` в `carcass.ts`.

**Формула (накладная стенка, `mount.kind = 'overlay'`).**
```
carcassDepth = tolerances.depthIncludesBackPanel ? D − Tb : D
carcassZ0    = Tb          // корпус сдвинут вперёд на толщину стенки
innerZ0      = Tb
```
где `Tb` — толщина задней стенки.
**Обоснование положения по Z.** Начало координат — задняя плоскость
изделия ЦЕЛИКОМ, включая заднюю стенку (`docs/COORDINATE_SYSTEM.md` §3).
Накладная стенка прибивается к заднему торцу корпуса и физически стоит
между `z=0` и `z=Tb`; корпус начинается с `z=Tb`.

**Формула (вкладная стенка, `mount.kind = 'inset-groove' | 'inset-flush'`).**
```
carcassDepth = D
carcassZ0    = 0
innerZ0      = mount.kind === 'inset-groove'
               ? mount.grooveOffsetFromRear + Tb
               : Tb
```

**Формула (стенки нет, `mount.kind = 'none'`).**
```
carcassDepth = D
carcassZ0    = 0
innerZ0      = 0
```

**Пример.** `D=500`, накладная стенка `Tb=3`, `depthIncludesBackPanel=true`:
`carcassDepth=497`, `carcassZ0=3`.
**Источник.** `ASSUMPTION(T-CAR-04)` — монтаж и вхождение в габарит не
подтверждены референсом.
**Тест.** T-CAR-04: сравнить габаритную глубину и глубину боковины
в деталировке референса; разница равна толщине задней стенки при накладном
монтаже. `tests/unit/geometry/engine.test.ts` — три варианта монтажа.

## 5. ВНУТРЕННИЙ ОБЪЁМ

**Назначение.** Пространство, в котором будет раскладываться дерево секций
(этап 09 плана, ещё не реализован).

**Формула.**
```
innerX0    = T
innerWidth = W − 2T
innerY0    = hasBottom ? T : 0
innerY1    = hasTop ? H − T : H
innerZ0    = carcassZ0 + max(0, innerZ0_back − carcassZ0)
innerDepth = carcassZ0 + carcassDepth − innerZ0
```
где `innerZ0_back` — значение `innerZ0` из §4.5.

**Единицы.** Миллиметры.
**Ограничения.** Каждая из трёх составляющих размера обязана быть `> 0`;
иначе `error` с кодом `INNER_VOLUME_EMPTY` (запись остаётся в диагностике,
но результат уже пуст из-за аварийной остановки — на практике это
срабатывает только при данных, прошедших §3, но давших вырожденный объём
из-за взаимодействия с толщиной задней стенки).
**Пример.** Продолжение примера §4.2–4.5: `min=(16,16,3)`,
`size=(968,1968,497)`.
**Источник.** Выведено из §4 (каркас) и §4.5 (задняя стенка), которые сами
помечены `ASSUMPTION`. Формула внутреннего объёма — не отдельное
предположение, а следствие уже принятых.
**Тест.** `tests/unit/geometry/carcass.test.ts`,
`tests/unit/geometry/snapshot.test.ts`, `tests/unit/geometry/properties.test.ts`
(«внутренний объём положителен и вложен в номинальный габарит»).

## 6. BOUNDING BOX

Реализация — `src/geometry/bounding-box.ts`, чистая функция
`computeBoundingBox(parts: readonly Part[]): BoundingBox`.

**Назначение.** Измеренный охват реально построенных деталей — нужен
рендереру (этап 07) и планировщику (этап 33) для вписывания вида
и обнаружения пересечений с другими предметами в помещении.

**Формула.**
```
minX = min(part.position.x for part in parts)
maxX = max(part.position.x + part.size.x for part in parts)
// аналогично для Y, Z

totalWidth  = maxX − minX
totalHeight = maxY − minY
totalDepth  = maxZ − minZ
```
Пустой список деталей даёт вырожденный результат: все поля равны 0
(`EMPTY_BOUNDING_BOX`).

**Отличие от `bounds`.** `GeometryResult.bounds` — заявленный габарит
`(0,0,0)`–`(W,H,D)`, известный уже на входе, до расчёта деталей.
`boundingBox` — то, что РЕАЛЬНО построено. Для одного каркаса без
выступающих элементов они совпадают (`totalDepth` меньше `D` на толщину
задней стенки, если она накладная — см. пример). Когда появится
столешница со свесом (этап 23) или фурнитура, выступающая за корпус,
значения разойдутся, и `boundingBox` покажет фактический охват.

**Единицы.** Миллиметры, округление до сетки 0.1 мм на выходе.
**Пример.** Для примера §4.2–4.5: `{minX:0, maxX:1000, minY:0, maxY:2000,
minZ:3, maxZ:500, totalWidth:1000, totalHeight:2000, totalDepth:497}`.
**Источник.** N/A — геометрическое агрегирование, не зависит от
конвенций референса.
**Тест.** `tests/unit/geometry/bounding-box.test.ts`.

## 7. ИНВАРИАНТЫ РЕЗУЛЬТАТА

Реализация — `GeometryContext.finish()` (`src/geometry/context.ts`).
Применяются к КАЖДОЙ детали, независимо от того, какой этап её произвёл —
это касается и будущих этапов (наполнение, фасады, фурнитура), которые
добавляют детали через тот же `addPart()`.

| Инвариант | Формула | Код при нарушении | Действие |
| --- | --- | --- | --- |
| Финитность позиции и размера | `Number.isFinite` на всех 6 компонентах | `PART_NOT_FINITE` | деталь отбрасывается (проверяется в `addPart`, до попадания в список) |
| Уникальность идентификатора | нет повтора `part.id` среди уже принятых | `PART_ID_DUPLICATE` | вторая и последующие с тем же id отбрасываются |
| Положительность размера | `size.x > 0 ∧ size.y > 0 ∧ size.z > 0` | `PART_SIZE_NOT_POSITIVE` | деталь отбрасывается |
| Неотрицательность координаты | `position.x ≥ 0 ∧ position.y ≥ 0 ∧ position.z ≥ 0` | `PART_POSITION_NEGATIVE` | деталь отбрасывается |

**Обоснование неотрицательности координаты.** Начало координат — левый–
нижний–задний угол изделия целиком (`docs/COORDINATE_SYSTEM.md` §1).
Легитимная деталь никогда не может иметь отрицательную координату в этой
системе; отрицательное значение — всегда следствие ошибки формулы, а не
допустимое положение (например, столешница со свесом растёт в `+z`,
за номинальную глубину, но никогда в `−z`).

**Гарантия для потребителей результата.** Если деталь присутствует
в `GeometryResult.parts`, она прошла все четыре проверки. Диагностика
о нарушении остаётся в `diagnostics` даже для отброшенной детали —
причина видна, а не молчаливо теряется.

**Источник.** N/A — инженерные инварианты продукта.
**Тест.** `tests/unit/geometry/invariants.test.ts` (все четыре инварианта,
включая случай «исправная деталь рядом с некорректной проходит
независимо»).

## 8. РАЗМЕРЫ РАСКРОЯ И КРОМКА

Реализация — `src/geometry/parts.ts`, функции `rawCutSize()` и
`applyEdgeSizing()`.

### 8.1 Сырые размеры раскроя

**Формула.** Зависит от `orientation` детали:
```
vertical-yz:    length = size.y,  width = size.z,  thickness = size.x
horizontal-xz:  length = size.x,  width = size.z,  thickness = size.y
frontal-xy:     length = size.y,  width = size.x,  thickness = size.z
```
**Обоснование.** В локальной системе детали `length` идёт слева направо,
`width` — от заднего торца к переднему; см. `docs/COORDINATE_SYSTEM.md` §5.
**Источник.** N/A — геометрическое преобразование системы координат,
не зависит от референса.
**Тест.** `tests/unit/geometry/engine.test.ts` («размеры раскроя»).

### 8.2 Кромка

**Формула.**
```
subtractFromPartSize = false:
    length = raw.length,  width = raw.width           (кромка «сверху»)
subtractFromPartSize = true:
    length = raw.length − edge.left − edge.right
    width  = raw.width  − edge.back − edge.front
```
**Единицы.** Миллиметры; толщина кромки — одно из `{0, 0.4, 1, 2}`.
**Значение по умолчанию.** `subtractFromPartSize = false`
(`DEFAULT_EDGE_SIZING_POLICY`).
**Источник.** `UNKNOWN (T-EDG-03)` — какой размер показывает карта раскроя
референса (до оклейки или после), не установлено. Обе ветки реализованы
и покрыты тестами — политика вынесена в настройки проекта, а не зашита.
**Тест.** T-EDG-03. `tests/unit/geometry/engine.test.ts`
(«вычитает кромку только при включённой политике»).

## 9. РАСКЛАДКА ДЕРЕВА СЕКЦИЙ (`layout`)

Реализация — `src/geometry/stages/layout.ts`. Третий этап конвейера.
Превращает `Furniture.root` (дерево `SplitNode`/`LeafNode`,
docs/DATA_MODEL.md §5) в ячейки (`CellBox[]`) и детали перегородок
(`Part[]`). Объединяет два этапа исходного плана — `layout` и `dividers` —
в один: обоснование в §9.7.

### 9.1 Ячейка листа

**Формула.** Для листа на пути `path` от корня, при родительском объёме
`box` (для корня — `innerVolume`, иначе — объём, переданный от родителя):
```
cell.box = box                     // объём уже вырезан на уровне родителя
cell.row, cell.column               см. §9.3
cell.sectionId                      см. §9.4
cell.fill = LeafNode.fill            без изменений — что в дереве, то и в ячейке
```
**Источник.** N/A — прямое отражение уже существующей доменной модели,
без новой геометрии.
**Тест.** `tests/unit/geometry/layout.test.ts` (Test 1).

### 9.2 Раскладка одного деления

**Формула.** Для узла `SplitNode` с осью `axis`, детьми `children` и объёмом
`box`, доступным вдоль `axis`:
```
available = extentAlong(box, axis)
{spans, overconstrained} = resolveSizes(children.map(c => c.size), available, divider.thickness)
childBox[i] = sliceAlong(box, axis, spans[i].offset, spans[i].length)
```
`resolveSizes` — не новая формула этого этапа, а уже реализованная и трижды
проверенная (PROMPT 2, свойство «сумма ячеек + разделители = доступная
длина») функция `src/domain/furniture/layout.ts`. Этап `layout` — её первое
реальное применение внутри геометрического движка.
**Единицы.** Миллиметры.
**Источник.** N/A — прямое применение уже подтверждённой формулы.
**Тест.** `tests/unit/geometry/layout.test.ts` (Test 3–9),
`tests/unit/geometry/grid-properties.test.ts`.

### 9.3 Индекс строки и колонки

**Формула.** При спуске по дереву от корня к листу:
```
row    = 0
column = 0
для каждого узла SplitNode на пути:
    если node.axis === 'y': row    = индекс_ребёнка_на_этом_уровне
    если node.axis === 'x': column = индекс_ребёнка_на_этом_уровне
```
То есть `row`/`column` — индекс листа среди соседей по БЛИЖАЙШЕМУ предку
соответствующей оси, а не глобальная координата прямоугольной сетки:
дерево не обязано быть равномерной сеткой целиком.
**Пример.** Сетка 2×3 (`createUniformGrid(ids, 2, 3, …)`, §9.6): корень —
деление по Y (2 строки), каждая строка — деление по X (3 колонки). Лист
на пути `[1, 2]` получает `row = 1, column = 2`.
**Источник.** N/A — определено этим проектом, не референсом (в дереве нет
понятия «глобальные координаты сетки», см. docs/DATA_MODEL.md §5.1).
**Тест.** `tests/unit/geometry/layout.test.ts` (Test 5, Test 6).

### 9.4 Идентификатор секции

**Формула.**
```
sectionId(корень) = корень.axis === 'x' ? child.id : корень.id
sectionId(глубже) = sectionId родителя (не пересчитывается)
```
То есть «секция» — это ребёнок ПЕРВОГО (и только первого) деления по оси X,
если дерево с него начинается; если корень делится по Y или является
листом, всё изделие — одна секция с `sectionId = root.id`.
**Важное следствие.** Дерево из одного деления по X с N листьями
структурно НЕОТЛИЧИМО от «N секций» и от «1 секции с N колонками, без
единственной строки» — потому что деление с единственным ребёнком
запрещено (`SplitNode.children.length ≥ 2`, docs/DATA_MODEL.md §15), и
обернуть единственную строку ещё одним делением невозможно. Это не
недостаток модели, а честное отражение того, что эти два понятия в данном
случае совпадают буквально везде, кроме названия. Проверено явно:
`tests/unit/geometry/layout.test.ts`, Test 5.
**Источник.** N/A — определено этим проектом.
**Тест.** `tests/unit/geometry/layout.test.ts` (Test 3, Test 4, Test 5).

### 9.5 Перегородки

**Формула.** Для `SplitNode` с `divider.material === 'panel'` и N детьми —
N−1 перегородок, по одной на границу между соседями `i` и `i+1`:
```
offset = dividerOffset(spans, i)                 // из resolveSizes, §9.2

ось X (вертикальная перегородка, стойка):
    position = (box.min.x + offset, box.min.y, box.min.z)
    size     = (divider.thickness, box.size.y, box.size.z)
    orientation = 'vertical-yz'

ось Y (горизонтальный разделитель):
    position = (box.min.x, box.min.y + offset, box.min.z)
    size     = (box.size.x, divider.thickness, box.size.z)
    orientation = 'horizontal-xz'
```
Перегородка спans ПОЛНОЕ поперечное сечение объёма ТЕКУЩЕГО уровня
рекурсии (`box`), а не всего изделия: вертикальная стойка внутри одной
строки сетки 2×3 занимает высоту этой строки, а не всего корпуса.

**Роль детали.**
```
axis === 'x'                        → role = 'partition'
axis === 'y', mounting === 'fixed'      → role = 'shelf-fixed'
axis === 'y', mounting === 'adjustable' → role = 'shelf-adjustable'
```
**Обоснование роли.** Вертикальная перегородка — всегда конструктивный,
несъёмный элемент в этой модели (в отрасли не встречается «переставляемая»
несущая стойка). Горизонтальный разделитель, структурно создающий два
разных поддерева, физически является полкой; `DividerSpec.mounting`
(«на конфирматах» или «на полкодержателях») определяет, какая именно —
поэтому роль различается по этому же полю, без нового флага.
**materialId/edge.** `divider.materialId`/`divider.edge`, если заданы;
иначе — материал по роли из библиотеки (тот же механизм, что у каркаса,
§4.2), с тем же предупреждением `MATERIAL_NOT_ASSIGNED` при отсутствии
назначения.
**Идентификатор.** `buildPartId({furnitureId, role, index: i, nodeId: splitNode.id})`
— стабилен, потому что `splitNode.id` уникален в пределах изделия
(инвариант домена) и не меняется при пересчёте геометрии.
**Источник.** N/A — геометрическое следствие уже принятых решений
(конструкция дерева, `resolveSizes`), не отдельное предположение о
референсе.
**Тест.** `tests/unit/geometry/layout.test.ts` (Test 3–9),
`tests/unit/geometry/grid-properties.test.ts`.

### 9.6 Равномерная сетка — построение дерева

Реализация — `src/domain/furniture/sections.ts`,
`createSections()`/`createUniformGrid()`. Не формула движка, а фабрика
домена: строит дерево, которое ЗАТЕМ раскладывает `layout` по правилам
§9.1–9.5. Формула построения:
```
createSections(N)            → SplitNode(x, N равных flex-детей-листьев)

createUniformGrid(rows, cols):
    rows ≤ 1 и cols ≤ 1  → лист (без единого деления)
    rows ≤ 1             → SplitNode(x, cols равных детей-листьев)
    cols ≤ 1              → SplitNode(y, rows равных детей-листьев)
    иначе                  → SplitNode(y, rows детей), каждый —
                             SplitNode(x, cols равных детей-листьев)
```
Вырожденные случаи не создают лишний уровень дерева: сетка `1×N` — чистое
деление по X без обёртывающего Y-деления, и наоборот.
**Единицы.** N/A (структура, не геометрия).
**Ограничения.** `SplitNode.children.length ≥ 2` — вызывающая сторона
обязана передавать `count ≥ 2` в `createSections`.
**Источник.** N/A — равномерная сетка выбрана как область этого этапа
согласно заданию (PROMPT 4 §10), не как подтверждённое правило референса.
**Тест.** `tests/unit/domain/sections.test.ts`.

### 9.7 Почему `layout` и `dividers` — один этап

Исходный план (docs/ARCHITECTURE.md §5.2, редакция PROMPT 1–3) описывал их
раздельно. При реализации выяснилось: оба вычисляются из ОДНОГО вызова
`resolveSizes()` на каждом делении — `spans` дают одновременно и границы
ячеек (§9.1), и позиции перегородок (§9.5, через `dividerOffset`). Считать
их в двух отдельных проходах значило бы либо дважды решать одну и ту же
задачу раскладки, либо протаскивать промежуточный результат первого
прохода во второй окольным путём (через ещё одно поле контекста). Оба
пути хуже одного прохода, честно объединяющего связанные вычисления.
`docs/ARCHITECTURE.md` §5.2 и `docs/IMPLEMENTATION_PLAN.md` обновлены
вслед за этим решением.

### 9.8 Аварийная остановка внутри `layout`: локальная, а не глобальная

**Правило.** Если деление `SplitNode` переопределено
(`resolveSizes().overconstrained`) ИЛИ у любого ребёнка получился
неположительный размер (`span.length ≤ 0`) — ошибка репортится для ЭТОГО
узла, и его поддерево (дети и перегородки) не строится. Но обход дерева
ПРОДОЛЖАЕТСЯ для соседних, независимых веток.

**Отличие от §2.** Между ЭТАПАМИ конвейера (normalize → carcass → layout)
действует жёсткая политика: одна ошибка останавливает всё, что не успело
посчитаться. ВНУТРИ этапа `layout`, при обходе ОДНОГО дерева — политика
мягче: одна испорченная ветка (например, секция с числом колонок, для
которого не хватает ширины) не должна прятать от пользователя остальные,
корректные секции того же изделия, и не должна прятать уже построенный
каркас. Пользователь должен увидеть, ЧТО именно сломано, а не получить
пустой экран.

**Почему это не противоречит принципу PROMPT 3 «недопустимый вход не
должен дать геометрию».** Тот принцип касается ФУНДАМЕНТАЛЬНО непригодного
входа — габаритов, из которых в принципе нельзя построить каркас. Здесь
случай другой: каркас валиден, а одна из МНОГИХ независимых веток дерева
секций — нет. Это ближе к «опечатка в одном поле формы», чем к
«отрицательная ширина изделия»: показать форму с одной подсвеченной
ошибкой полезнее, чем показать пустой экран.
**Источник.** N/A — инженерное решение, взвешивающее два принципа
проекта (PROMPT 3 «нет мусорной геометрии» и PROMPT 1 Agency «пользователь
не должен терять контроль из-за чужой ошибки в другом месте»).
**Тест.** `tests/unit/geometry/layout.test.ts` (Test 11).

### 9.9 Минимальный размер ячейки

**Формула.** После успешной раскладки листа: если
`cell.box.size.x < MIN_CELL_SIZE` или `cell.box.size.y < MIN_CELL_SIZE`
(`MIN_CELL_SIZE = 50` мм, `src/domain/furniture/defaults.ts`) — `warning`
с кодом `CELL_BELOW_MIN_SIZE`. **Не блокирует** ни расчёт, ни экспорт сам
по себе (принцип Agency) — но это единственное предупреждение из этого
этапа, не единственная ошибка; отличать от §9.8, где деление отклоняется
целиком.
**Глубина не проверяется** этим правилом: `MIN_CELL_SIZE` — про
практичность ширины/высоты полки, а не про глубину, которая почти всегда
наследуется от корпуса целиком, не являясь на этом этапе изменяемым
параметром отдельной ячейки.
**Источник.** `docs/DATA_MODEL.md` §5.3 (значение по умолчанию 50 мм
установлено на PROMPT 1 как инженерная эвристика, не как факт о
референсе).
**Тест.** `tests/unit/geometry/layout.test.ts`
(«минимальный размер ячейки: предупреждение, не блокировка»).

## 13. CARCASS CALCULATION RULES — СВОДНАЯ ТАБЛИЦА (аудит PROMPT 5)

### 13.2 AMBIGUOUS: `sectionWidth` при вложенном делении по X внутри секции

**Найдено при ревизии.** `sectionId` присваивается ОДИН раз — на первом
делении по оси X от корня — и затем передаётся вглубь дерева БЕЗ пересчёта
(`sectionIdFor()` в `layout.ts`, §9.4), независимо от того, какие деления
встречаются глубже. Если бы дерево содержало ВТОРОЕ деление по X глубже
внутри поддерева одной секции (например, «секция 1» дополнительно поделена
на 2 подколонки), то узлы с ОДНИМ `sectionId` получили бы РАЗНЫЙ
`box.size.x` — и одно число «ширина секции» перестало бы существовать.

**Почему это не исправлено, а зафиксировано как AMBIGUOUS.** Обе доступные
сейчас фабрики (`createSections`, `createUniformGrid`,
`src/domain/furniture/sections.ts`) физически не могут построить такое
дерево: `createSections` не создаёт вложенности, `createUniformGrid`
чередует Y (строки) → X (колонки) РОВНО один раз на каждую ветку. Общая
модель `SplitNode` это не запрещает — интерфейс ручного редактирования
дерева (этап 10, интерактивная половина, ещё не реализована) в будущем
сможет породить такой случай. Придумывать сейчас, что должно означать
«ширина секции» в этом гипотетическом дереве — значит выдумывать
конструктивное правило без источника, что PROMPT 5 §26 прямо запрещает.

**NEEDS_CONFIRMATION.** Когда появится ручное редактирование дерева (этап
10) или необходимость показать «ширину секции» в интерфейсе как единое
число — этот случай нужно решить явно (например: секция без единственного
`sectionId`-инварианта запрещена на уровне команд; либо «ширина секции»
определяется как объединяющий bounding box всех её ячеек, а не как общее
число). Не решается сейчас, потому что ни один этап плана до сих пор этого
не требует.

### 13.3 Boковины — обязательный элемент, а не параметр

**Найдено при ревизии, подтверждено, не было явно записано отдельной
строкой ни в одном документе.** В отличие от `hasTop`/`hasBottom`
(`CarcassSpec`, оба — булевы поля, можно отключить), в модели НЕТ полей
`hasLeftSide`/`hasRightSide`: боковины строятся в `carcass.ts` безусловно,
на каждом прогоне. Поэтому формула `internalWidth = W − 2T` не имеет
скрытого условия «если боковины есть» — они есть всегда. Статус:
CONFIRMED (инженерное решение продукта, не референса — `N/A`, не
`ASSUMPTION`, так как это структурное свойство модели, а не догадка о
конструкции мебели).

### 13.4 Разделение overall / internal / cell — уже было, подтверждено

PROMPT 5 §19 требует не смешивать габарит, внутреннее пространство и
ячейку в одном поле. Ревизия подтвердила: `GeometryResult.bounds`
(overall), `GeometryResult.innerVolume` (internal) и `CellBox.box` (cell)
— три разных структуры, ни одна не переиспользуется для другого смысла.
Статус: CONFIRMED, без изменений.

### 13.5 Отсутствие magic numbers — проверено

Поиск по `src/geometry/` не нашёл ни одного нечисленного вычитания вида
`width − 36` без источника: единственные числовые литералы в формулах —
`× 2` (две боковины/два разделителя — самоочевидное количество, не
константа с скрытым смыслом) и именованные константы (`MIN_CELL_SIZE`,
`DIMENSION_LIMITS`, `MM_PRECISION`, `MM_EPSILON` — все в
`domain/furniture/defaults.ts` / `domain/units.ts`, с обоснованием
в комментарии на месте объявления). Статус: CONFIRMED.

## 14. SHELF CALCULATION RULES (PROMPT 6)

Реализация — `src/geometry/stages/fill.ts`, четвёртый этап конвейера.
Строит физические полки внутри уже посчитанных ячеек.

### 14.1 Cell — пространство, Shelf — деталь

Ключевое разделение этапа (PROMPT 6 §5): **полка не создаёт и не изменяет
ни одной ячейки**. `fill` вызывает только `ctx.addPart()` и никогда
`ctx.addCell()` — множество ячеек остаётся ровно таким, каким его построил
`layout` (§9). Промежутки между полками внутри одной ячейки НЕ становятся
самостоятельными ячейками: ячейка — это открытый проём, а полки в нём —
детали, стоящие внутри.

Из этого следует практическое отличие от структурного деления по оси Y
(§9.5), которое ВЫГЛЯДИТ похоже, но означает другое:

| | Горизонтальный разделитель (`SplitNode`, `axis: 'y'`) | Полка (`LeafFill.shelves`) |
| --- | --- | --- |
| Что порождает | новую пару ячеек с независимым наполнением | только деталь |
| Число ячеек | растёт | не меняется |
| Роль детали | `shelf-fixed` / `shelf-adjustable` | те же роли |
| Когда применять | зоны с РАЗНЫМ наполнением (штанга сверху, ящики снизу) | одинаковые полки в одном проёме |

Физически это одна и та же деталь — доска поперёк проёма
(§9.5: «горизонтальный разделитель физически является полкой»), поэтому
роль `PartRole` у них общая, и debug-рендерер красит их одинаково.
Различие только в том, делится ли при этом дерево.

### 14.2 Модель полки: почему не плоская структура из задания

Задание (§3) предлагает `Shelf { id, sectionId, row, x, y, z, width,
height, depth, thickness, materialId, edge, removable }`. В коде
используется уже существующий с PROMPT 1 тип `Shelf`
(`src/domain/furniture/types.ts`, `docs/DATA_MODEL.md` §6.1), потому что
в нём НЕТ вычисляемых полей — и это то же правило, по которому в модели
нет `Cell.width` и `Section.width` (§13.1, `DATA_MODEL.md` §5.6):

| Поле задания | Где оно на самом деле | Почему не хранится |
| --- | --- | --- |
| `x`, `y`, `z`, `width`, `height`, `depth` | `Part.position` / `Part.size` в `GeometryResult` | производные от ячейки и `placement`; хранить — значит завести второй источник истины и рассинхрон при первом же изменении габарита |
| `sectionId`, `row` | `Part.origin.nodeId` → ячейка в `GeometryResult.cells` → её `sectionId`/`row` | у ячейки они уже есть (§9.3–9.4); дублировать на детали нечего |
| `thickness` | `Shelf.thickness ?? Dimensions.panelThickness` | второй независимый параметр толщины не заводится (PROMPT 6 §9) |
| `removable` | `Shelf.mounting === 'adjustable'` | «съёмная» и «на полкодержателях» — одно и то же свойство под двумя именами; хранить оба — тот же рассинхрон |
| `id` | `Shelf.id` (`NodeId`) | уже есть, стабилен |
| `materialId`, `edge` | `Shelf.materialId` / `Shelf.edge`, иначе материал по роли | общая система материалов (PROMPT 6 §24) |

Тип полки (§4 задания, FIXED/REMOVABLE) — это `PartRole` результата:
`shelf-fixed` или `shelf-adjustable`. Новые виды полок добавляются новым
значением роли и одной строкой в `shelfRole()`, без переписывания движка.

### 14.3 Количество полок

**Формула.** `count = LeafFill.shelves.length` — прямо из модели.

**Почему не `rowCount − 1`** (PROMPT 6 §12): в этой архитектуре у ячейки
нет собственного `rowCount`. Число рядов — свойство ДЕРЕВА (число детей
`SplitNode` с `axis: 'y'`), и оно уже даёт свои детали по правилу §9.5
(N детей → N−1 разделителей). Полки же перечислены поштучно, поэтому
никакого вывода количества из чего-то другого не требуется и не делается.

**Источник.** N/A — следствие модели, не предположение о референсе.
**Тест.** `tests/unit/geometry/fill.test.ts` (Test 2–4, 8).

### 14.4 Ширина полки

**Формула.** `shelf.size.x = cell.box.size.x`, `shelf.position.x = cell.box.min.x`.

Ячейка уже посчитана net: боковины, вертикальные перегородки и толщины
разделителей вычтены на этапе `layout` (§9.2). Поэтому полка по построению
не может пересечь боковину или стойку — никакого повторного вычитания
толщин здесь нет (PROMPT 6 §16 про двойное вычитание).

**Технологический зазор не вводится.** `ASSUMPTION(T-SHF-01)`: реестр
`docs/UNKNOWNS.json` фиксирует допущение «полка встаёт впритык к стенкам
проёма». Если тест на референсе покажет зазор, он появится ОТДЕЛЬНЫМ
именованным параметром модели, а не константой в формуле.

**Тест.** `fill.test.ts` (Test 2, 6, 10), `fill-properties.test.ts`.

### 14.5 Глубина полки

**Формула.**
```
frontSetback = Shelf.frontSetback ?? 0
shelf.size.z     = cell.box.size.z − frontSetback
shelf.position.z = cell.box.min.z
```
Полка стоит вплотную к задней плоскости ячейки, а `frontSetback`
укорачивает её СПЕРЕДИ (ось Z растёт к пользователю,
`docs/COORDINATE_SYSTEM.md` §1).

`cell.box.size.z` — это `internalDepth` (§13.1), то есть глубина уже
учитывает монтаж задней стенки. Именно поэтому `shelf.depth ≠ D`
(PROMPT 6 §8): для `D = 500` с накладной стенкой 3 мм полка получает
497 мм, а не 500.

**Ограничение.** `size.z > 0`, иначе `error` `SHELF_DEPTH_NOT_POSITIVE`
и эта полка не строится.
**Источник.** `ASSUMPTION(T-SHF-01)` — отступ от фасада не подтверждён;
значение по умолчанию 0, как и у `createDividerSpec`.
**Тест.** `fill.test.ts` (Test 7).

### 14.6 Толщина полки

**Формула.** `thickness = Shelf.thickness ?? Dimensions.panelThickness`,
откладывается по оси Y: `shelf.size.y = thickness`.

Второго параметра толщины не заводится (PROMPT 6 §9): `Shelf.thickness`
существовал в модели с PROMPT 1 как ПЕРЕОПРЕДЕЛЕНИЕ, и остаётся им.
**Тест.** `fill.test.ts` (Test 5, 6 — толщина не меняется при изменении H и W).

### 14.7 Положение по высоте: равномерное размещение

**Формула (`placement.mode === 'auto'`).** `count` полок делят высоту
ячейки на `count + 1` равных промежутка:
```
spans = resolveSizes(count + 1 равных flex-детей, cell.box.size.y, thickness)
shelf[i].y = cell.box.min.y + dividerOffset(spans, i)
```
Это ТОТ ЖЕ вызов, которым `layout` раскладывает структурные ряды (§9.2):
N полок между N+1 промежутками — ровно та задача, которую `resolveSizes`
уже решает и которая уже покрыта property-тестом с PROMPT 2. Никакой
второй формулы равномерного размещения не написано.

**Исправлено при реализации.** Черновик формулы в `ARCHITECTURE.md` §5.7
(редакция PROMPT 1) давал
`y = cell.y0 + (cell.h − count·T)·index/(count+1) + T·index`, то есть
первая полка вставала ВПРИТЫК к низу ячейки, без промежутка под ней:
не хватало одного слагаемого `gap`. Черновик был помечен как рабочий
и не проверялся тестом; реализация использует `resolveSizes`, где
промежуток снизу равен промежутку сверху по построению. Проверено
явно: `fill.test.ts`, «полки равномерно делят внутреннюю высоту
на 4 промежутка».

**Формула (`placement.mode === 'manual'`).**
`shelf.y = cell.box.min.y + placement.offsetFromBottom`.

**Ограничения.**
- `offsetFromBottom ≥ 0` и `offsetFromBottom + thickness ≤ cell.box.size.y`,
  иначе `error` `SHELF_OUT_OF_CELL_BOUNDS`, полка не строится;
- равномерная группа, которая не помещается (`resolveSizes` вернул
  `overconstrained` или неположительный промежуток) → `error`
  `SHELF_AUTO_OVERCONSTRAINED`, вся группа этой ячейки не строится;
- у всех полок одной auto-группы `placement.count` обязан совпадать
  с фактическим размером группы, а `placement.index` — быть
  перестановкой `0…count−1`, иначе `error`
  `SHELF_AUTO_PLACEMENT_INCONSISTENT` и группа не строится.

**Одна толщина на равномерную группу.** `resolveSizes` принимает ОДНУ
толщину разделителя на всё деление. Поэтому шаг размещения auto-группы
считается по толщине первой полки группы (или толщине корпуса). Полки
разной толщины внутри ОДНОЙ равномерной группы противоречили бы самому
смыслу «равномерно» и как отдельный случай не поддерживаются; полке
с индивидуальной толщиной место в `manual`.

**Область ошибки — ячейка, а не изделие.** Как и в §9.8: сломанная
группа полок гасит только себя, соседние ячейки, каркас и остальная
раскладка остаются построенными и видимыми.

**Источник.** N/A — применение уже подтверждённой формулы `resolveSizes`.
**Тест.** `fill.test.ts` (Test 2, 5, 8 и блок «коллизии и валидация»).

### 14.8 Высота ячейки и полки: двойного вычитания нет

PROMPT 6 §10 требует проверить связь `Cell.height` и `Shelf.thickness`.
В этой архитектуре её нет по построению: `cell.box.size.y` вычисляется
`layout`-этапом ДО того, как `fill` узнаёт о полках, и полки её не
меняют. Толщина полки вычитается ровно один раз — внутри `resolveSizes`
при расчёте промежутков (§14.7), и только из высоты промежутков, а не
из высоты ячейки.

Проверяемое равенство для ячейки с `count` равномерными полками:
```
sum(промежутки) + count · thickness = cell.box.size.y
```
что является тем же инвариантом `resolveSizes`, который property-тест
проверяет с PROMPT 2.

### 14.9 Пересечения

**Что гарантировано формулой.** Полка не пересекает боковины,
вертикальные перегородки, верх и низ — потому что лежит внутри ячейки
(§14.4), а ячейка уже не пересекает их (§9, проверено с PROMPT 4).
Полки одной auto-группы не пересекаются между собой — гарантия
`resolveSizes`.

**Что проверяется явно.** Комбинации `manual + manual` и
`manual + auto` формулой не гарантированы: пользователь может задать два
произвольных `offsetFromBottom`. Такие пары ищутся попарным сравнением
интервалов `[y, y + thickness]` внутри одной ячейки; при пересечении —
`error` `SHELF_OVERLAP`.

**Почему обе полки остаются в результате.** Каждая из них по отдельности
корректна (конечна, положительна, внутри ячейки) — исключить одну
означало бы выбрать за пользователя, какая «лишняя». Показать обе
и подсветить конфликт полезнее; это то же решение, что и в §9.8
(«показать, ЧТО сломано, вместо пустого экрана»).
**Тест.** `fill.test.ts`, блок «коллизии и валидация».

### 14.10 Идентификатор полки

**Формула.** `part:{furnitureId}/{cellNodeId}/{role}/{Shelf.id}`.

В отличие от перегородок (§9.5), где последний сегмент — порядковый номер
границы, у полки уже есть собственный стабильный `NodeId` из дерева
модели, и он используется напрямую (для этого `buildPartId` принимает
`number | string`). Следствие, которого требует PROMPT 6 §14: добавление
или удаление СОСЕДНЕЙ полки не меняет id остальных, потому что id не
выведен из позиции в массиве.

**Тест.** `fill.test.ts` (Test 14): тот же вход даёт те же id; изменение
высоты корпуса меняет `Y` полок, но не их id.

### 14.11 Bounding box

Полка лежит внутри ячейки, ячейка — внутри корпуса, поэтому добавление
полок НЕ меняет внешний габарит. Это не рассуждение, а проверка:
`fill.test.ts` (Test 11) сравнивает `boundingBox` изделия с полками
и без них — все три размера совпадают.

## 15. VERTICAL PARTITION RULES И СЕКЦИЯ КАК ОБЛАСТЬ (PROMPT 7)

Реализация — `src/geometry/stages/layout.ts` (та же, что и раскладка §9).
Отдельного этапа конвейера у перегородок нет и не заводится: перегородка —
прямое следствие деления дерева, а не самостоятельный расчёт.

### 15.1 Что уже было и осталось без изменений

Вертикальные перегородки стали настоящими деталями `Part` ещё на PROMPT 4
(§9.5): роль `partition`, ориентация `vertical-yz`, детерминированный id,
материал по роли, кромка. Ревизия PROMPT 7 §2 подтвердила, что модель
удовлетворяет требованиям задания §3–4, и НЕ переписывала её:

| Требование задания §3 | Где это уже есть |
| --- | --- |
| `id` | `Part.id` = `part:{furnitureId}/{splitNodeId}/partition/{index}` |
| `type` | `Part.role = 'partition'` (горизонтальные разделители — другие роли, §9.5) |
| `sectionId` / `parentId` | `Part.origin.nodeId` — узел деления, породивший перегородку |
| `x`, `y`, `z`, `width`, `height`, `depth` | `Part.position` / `Part.size` |
| `thickness` | `size.x` перегородки, он же `DividerSpec.thickness` |
| `materialId` | `Part.materialId` |

Плоскую структуру из задания в модель не переносили по тому же правилу,
что и для полки (§14.2) и ячейки (`docs/DATA_MODEL.md` §5.6): координаты и
размеры — производные, у них уже есть одно место жительства.

### 15.2 Количество перегородок

**Формула.** Для деления по оси X с `N` детьми — `N − 1` перегородка,
по одной на границу между соседями (§9.5).

Отсюда для верхнего уровня:
```
sectionCount   = число детей верхнего деления по X (1, если деления нет)
partitionCount = sectionCount − 1
```

`partitionCount = sectionCount − 1` выполняется здесь не как принятое
соглашение, а как СЛЕДСТВИЕ конструкции: перегородка ставится на границу
между двумя соседними секциями, границ между `N` соседями ровно `N − 1`,
а внешние границы крайних секций — это боковины, которые строит `carcass`
и которые перегородками не являются (задание §8).

**Источник.** N/A — геометрическое следствие уже принятых решений.
**Тест.** `tests/unit/geometry/partitions.test.ts` (Test 1–4 и уравнение
§18), `partition-properties.test.ts` (для случайного `sectionCount`).

### 15.3 Геометрия перегородки

**Формула** (перегородка `i` в делении по X с объёмом `box`):
```
offset      = dividerOffset(spans, i)                  // из resolveSizes, §9.2
position    = (box.min.x + offset, box.min.y, box.min.z)
size        = (divider.thickness, box.size.y, box.size.z)
orientation = 'vertical-yz'
```
Координата НЕ задаётся вручную (задание §6): `offset` приходит из той же
раскладки, что определяет ширины секций, поэтому «положение перегородки»
и «ширина секции» физически не могут разойтись — это одно вычисление.

Перегородка занимает полное поперечное сечение объёма ТОГО уровня, на
котором стоит: перегородка верхнего уровня — всю внутреннюю высоту и
глубину корпуса, перегородка внутри строки — только высоту этой строки.

**Зависит от.** `W`, `T` (через `innerVolume`, §13.1), `H`, `D`,
`sectionCount`, `DividerSpec.thickness`.
**Ограничения.** `divider.material === 'panel'` — иначе деление логическое
и детали не порождает (`DividerSpec`, `docs/DATA_MODEL.md` §5.4).
**Тест.** `partitions.test.ts` (Test 14).

### 15.4 Секция как геометрическая область

**Формула.**
```
корень — деление по X:  на каждого ребёнка i → section = { nodeId: child.id,
                                                            index: i,
                                                            box: childBox }
иначе (лист или деление по Y): одна секция { nodeId: root.id, index: 0,
                                              box: innerVolume }
```
Секции выпускаются ровно там, где решается принадлежность ячейки секции
(`sectionIdFor`, §9.4) — поэтому «где граница секции» определено в одном
месте, а не в двух.

**Границы (задание §9).** `box` и есть шесть границ:

| Граница | Значение | Чем является физически |
| --- | --- | --- |
| `leftBoundary` | `box.min.x` | боковина (для крайней левой секции) или перегородка |
| `rightBoundary` | `box.min.x + box.size.x` | перегородка или правая боковина |
| `bottomBoundary` | `box.min.y` | дно (или низ корпуса, если дна нет) |
| `topBoundary` | `box.min.y + box.size.y` | крышка (или верх корпуса) |
| `backBoundary` | `box.min.z` | передняя грань задней стенки (§4.5) |
| `frontBoundary` | `box.min.z + box.size.z` | передняя плоскость корпуса |

Отдельной детали ни для одной границы не создаётся (прямое требование
задания §9): границей служит либо уже существующая деталь, либо плоскость
внутреннего объёма.

**`section.width` не хранится** (задание §10) — это `box.size.x`,
производная от положения границ.

**Тест.** `partitions.test.ts` (Test 1–4, 11–13), `debug-view.test.ts`.

### 15.5 Зависимости пересчёта

```
Furniture (W, H, D, T)
  → Carcass        боковины, верх, низ, innerVolume        (§4–5)
  → Sections       области между боковинами и перегородками (§15.4)
  → Partitions     детали на границах секций                (§15.3)
  → Rows/Cells     деление внутри секции                    (§9)
  → Shelves        детали внутри ячейки                     (§14)
```
Стрелка означает «вычисляется из», а не «хранит ссылку на». Ни одно звено
не хранит результат предыдущего: изменение `W` или `sectionCount` проходит
всю цепочку за один пересчёт, потому что промежуточных копий нет.

**Тест.** `partitions.test.ts` (Test 5–10).

### 15.6 Политика идентичности

Полностью описана в `docs/DATA_MODEL.md` §5.7. Со стороны движка важно
одно: `GeometryResult` не назначает идентичность, он её ОТРАЖАЕТ.
`section.nodeId`, `cell.nodeId` и `nodeId` в `Part.origin` — это id узлов
дерева модели; пересчёт геометрии не может их изменить, потому что не
трогает дерево. Поэтому «id не меняются при пересчёте» — не правило,
которое нужно соблюдать, а свойство, которое невозможно нарушить, не
изменив модель.

**Тест.** `partitions.test.ts` (Test 15, 16), `document-store.test.ts`
(раздел «SetSectionCount и идентичность секций»).

### 15.7 Пересечения деталей

**Правило.** Никакие две детали не занимают один объём. Касание гранями
(полка вплотную к перегородке, дно к боковине, перегородка к крышке) —
законный конструктивный контакт и пересечением не считается.

**Реализация.** Предикат `overlaps()` в `src/domain/coordinates.ts`
сравнивает перекрытие по каждой оси с общим допуском `MM_EPSILON`, поэтому
слой тоньше половины шага сетки (след округления) не принимается за
пересечение. `findPartOverlaps()` (`src/geometry/overlaps.ts`) применяет
предикат ко всем парам деталей.

**Почему не этап конвейера.** Проверка квадратична по числу деталей, а
конвейер запускается на каждое нажатие в поле габарита. Инвариант при
этом держится по построению (ячейка не пересекает перегородку, потому что
перегородка вычтена из ячейки той же раскладкой). Поэтому проверка живёт
как чистая функция: сейчас её вызывают тесты на всех конфигурациях, а
постоянное место у неё уже назначено планом — `VAL-05` «Пересечение
деталей» в слое валидации (`docs/FEATURE_MATRIX.md`).

**Тест.** `partitions.test.ts` (§19), `partition-properties.test.ts`,
`coordinates.test.ts` («пересечение против касания»).

## 16. VARIABLE SECTION / ROW / COLUMN RULES (PROMPT 8)

Индивидуальные размеры секций, рядов и колонок. Реализация — та же
`resolveSizes` (`src/domain/furniture/layout.ts`) и та же стадия `layout`:
нового механизма размеров не заводилось.

### 16.1 Источник истины

| Параметр (задаёт пользователь) | Где хранится |
| --- | --- |
| `W`, `H`, `D`, `T` | `Furniture.dimensions` |
| размер секции / ряда / колонки | `SectionChild.size` — `SizeSpec` на ребёнке деления |
| число секций / рядов / колонок | длина `SplitNode.children` |
| ось деления (секции или ряды) | `SplitNode.axis` |

| Производное (считает движок) | Где появляется |
| --- | --- |
| `section.box` (X, ширина, все шесть границ) | `GeometryResult.sections` |
| `partition.x` | `Part.position` детали с ролью `partition` |
| `cell.box` (X, Y, ширина, высота) | `GeometryResult.cells` |
| `shelf.y` и размеры полки | `Part` с ролью `shelf-*` |
| `boundingBox` | `GeometryResult.boundingBox` |

Ни одна производная величина не хранится рядом с параметром: изменение
размера меняет ТОЛЬКО `SizeSpec`, всё остальное пересчитывается
(PROMPT 8 §2).

### 16.2 Модель размера: `fixed` и `flex`

```ts
type SizeSpec =
  | { mode: 'fixed'; value: Mm }    // держит абсолютный размер
  | { mode: 'flex';  weight: number } // забирает остаток пропорционально весу
```

Режимы EQUAL и FIXED из задания (§5–§6) — не отдельное поле-переключатель,
а следствие содержимого этого же типа:

| Режим задания | Как выражается |
| --- | --- |
| EQUAL | все дети `flex` с одинаковым весом (что и делает `createSections`) |
| FIXED | все дети `fixed` с заданными значениями |
| смешанный | часть `fixed`, часть `flex` — режим, которого в задании нет, но который нужен на практике: «эта секция ровно 300, остальные делят остаток» |

Отдельного `sectionSizingMode` не заводится: он был бы вторым источником
истины о том, что уже однозначно записано в размерах детей, и мог бы с
ними разойтись.

### 16.3 Формулы

Одни и те же для обеих осей — секции и колонки по `x`, ряды по `y`:

```
available = размер родительского объёма вдоль оси
usable    = available − divider.thickness × (N − 1)
fixedSum  = Σ value по детям с mode = 'fixed'
rest      = usable − fixedSum
flex[i]   = rest × weight[i] / Σ weight        (последний получает остаток)

child[0].offset = 0
child[i].offset = child[i−1].offset + child[i−1].length + divider.thickness
```

Отсюда прямо следует формула §8 задания:
```
section[0].x = внутренняя левая граница корпуса
section[i].x = section[i−1].x + section[i−1].width + partitionThickness
```
Позиция каждой секции вычисляется из предыдущих, вручную X не задаётся
нигде и никем.

**Ширина секции — это ПРОЁМ**, а не доля габарита. Поэтому габарит связан
с размерами так:
```
W = Σ section.width + (N − 1) · T + 2 · T
H = Σ row.height    + (M − 1) · T + 2 · T   (при наличии дна и крышки)
```
Задание пишет «1200 → [300, 500, 400]», деля отвлечённый отрезок; те же
три секции физически требуют `W = 1264`.

### 16.4 Валидация суммы

| Случай | Диагностика | Что делает движок |
| --- | --- | --- |
| `Σ fixed` больше доступного (`rest < 0`) | `SPLIT_OVERCONSTRAINED` (error) | поддерево не строится |
| `Σ fixed` меньше доступного и НЕТ `flex`-ребёнка, который забрал бы остаток | `SPLIT_UNDERCONSTRAINED` (error) | поддерево не строится |
| размер ребёнка ≤ 0 после раскладки | `CELL_SPAN_NOT_POSITIVE` (error) | поддерево не строится |
| размер не число (NaN/±∞) | `DIMENSION_NOT_FINITE` / отсев в `addPart`/`addCell` | значение не попадает в результат |

**`SPLIT_UNDERCONSTRAINED` добавлен на PROMPT 8.** До него такой вход
проходил молча: `resolveSizes` возвращала положительный `rest`, никто его
не проверял, и геометрия строилась с невидимым зазором у дальнего края —
а инвариант «сумма ячеек и разделителей равна доступной длине» переставал
выполняться, оставаясь при этом зелёным в тестах, потому что все тесты
использовали `flex`-детей. Найдено при подготовке этого этапа.

Сравнение остатка с нулём — через `gtMm`, то есть с общим допуском
`MM_EPSILON` (PROMPT 8 §21): остаток тоньше половины шага сетки — след
округления, а не зазор.

**Область ошибки — деление, а не изделие.** Как и раньше (§9.8): каркас
и соседние ветки остаются построенными, пользователь видит, ЧТО именно
не сходится.

### 16.5 Ячейка при индивидуальных размерах

`cell.width` и `cell.height` НЕ вычисляются как `section.width / columnCount`
(прямой запрет §13–14 задания) — и не могли бы: раскладка не знает такого
выражения вообще. Размер ячейки всегда приходит из `resolveSizes` того
деления, которому ячейка принадлежит, поэтому при колонках `[150, 250]`
получаются ячейки 150 и 250, а не две по 200.

### 16.6 Колонки

Колонка — ребёнок деления по `x`, не являющегося верхним. Механизм тот же,
что у секций, включая индивидуальные размеры: `createSizedSplit(ids, 'x', …)`
внутри секции даёт колонки заданной ширины. Отдельной системы размеров для
колонок не заводится (§9 задания). Проверено тестом: секция с колонками
`[150, 250]` даёт две ячейки именно такой ширины, обе внутри своей секции.

### 16.7 Идентичность при изменении размера

Изменение размера не создаёт и не удаляет ни одного узла дерева, поэтому
не может изменить ни один id — ни секции, ни ячейки, ни полки, ни детали
(`docs/DATA_MODEL.md` §5.7). Команда `SetChildSize` адресует ребёнка по
`childId`, а не по позиции в массиве: позиция сдвигается при добавлении
соседа, id — нет.

Проверено тестом: изменение ширины секции с полками не меняет ни одного
идентификатора, при этом геометрия действительно другая.

### 16.8 Изменение общего габарита при изменении секции (§17 задания)

Задание требует выбрать между `FIXED_TOTAL` (габарит держится, соседи
перераспределяют остаток) и `FREE_TOTAL` (габарит растёт вслед за суммой)
и не выбирать самостоятельно, если правило неизвестно.

**Что реализовано:** поведение `FIXED_TOTAL`, причём выраженное не режимом,
а составом размеров. Габарит `W` — независимый параметр, и команда
изменения размера секции его не трогает. Что произойдёт с соседями,
определяет пользователь заранее:

- есть `flex`-соседи → они поглощают разницу, сумма продолжает сходиться;
- все соседи `fixed` → сумма перестаёт сходиться, и движок сообщает об
  этом ошибкой вместо того, чтобы молча подогнать чужие размеры.

**Что НЕ решено:** `FREE_TOTAL` — увеличивать ли `W` автоматически вслед
за суммой секций. Это меняло бы габарит изделия в ответ на правку
внутренней структуры, то есть трогало бы параметр, который пользователь
задал сам. Правило не подтверждено ни спецификацией, ни референсом:
`NEEDS_CONFIRMATION`, см. `docs/UNKNOWNS.json` (T-DIM-05).

## 17. CELL / CONTENT / PART (PROMPT 9)

Три сущности, которые в мебельном редакторе легче всего перепутать, и
правило, по которому они различаются.

### 17.1 Определения

| Сущность | Что это | Где живёт | Есть ли у неё материал и размер раскроя |
| --- | --- | --- | --- |
| `Part` | ФИЗИЧЕСКАЯ деталь: боковина, перегородка, дно, крышка, полка, будущая дверь | `GeometryResult.parts` | да |
| `Cell` | ПРОСТРАНСТВЕННАЯ область — проём между деталями | `GeometryResult.cells` | нет: пространство не пилят и не кромят |
| `Content` | ЛОГИЧЕСКОЕ наполнение ячейки: пусто, полки, ящики, штанга | `LeafNode.fill` (`LeafFill`) | нет: наполнение порождает детали, но само деталью не является |

Цепочка расчёта:
```
Project → Carcass → Sections → Cells → Contents → Geometry Engine → Parts
```
Каждая стрелка — «вычисляется из». Наполнение стоит МЕЖДУ ячейкой и
деталями: ячейка даёт ему объём, оно говорит, что в этом объёме должно
появиться, а детали строит движок.

### 17.2 Наполнение не дублирует геометрию ячейки

У наполнения нет ни `cellId`, ни собственных координат, ни ширины —
и это не упущение. Наполнение ЛЕЖИТ внутри ячейки (`LeafNode.fill`),
поэтому:

- ссылка на ячейку не может испортиться — её нет, есть вложенность;
- наполнение не может осиротеть — удаление ячейки удаляет узел вместе
  со всем, что в нём лежит;
- наполнение не может «переехать» в другую ячейку при пересчёте —
  пересчёт не трогает дерево;
- размер наполнения не может разойтись с размером ячейки — он из неё
  и берётся.

Всё это — свойства по построению, а не правила, которые нужно соблюдать.
Именно поэтому второй тип `Content { id, cellId, … }` рядом с `LeafFill`
не заводится: он превратил бы четыре гарантии в четыре обязанности.

**Идентичность наполнения — это идентичность ячейки** (`LeafNode.id`),
потому что наполнение у ячейки ровно одно. Элементы ВНУТРИ наполнения —
полки, ящики, штанга — имеют собственные стабильные `NodeId`.

### 17.3 Одно наполнение на ячейку

**Правило.** У ячейки ровно одно наполнение. Смешанные случаи выражаются
делением ячейки, а не списком наполнений: полки сверху и ящики снизу —
это две ячейки, разделённые по оси Y.

Так у каждой зоны есть собственные границы, собственный id и собственный
размер, а у движка — одно правило вместо разбора комбинаций. Правило
зафиксировано с PROMPT 1 (`docs/DATA_MODEL.md` §5.5) и на PROMPT 9
подтверждено, а не пересмотрено.

**Единственное исключение** — `rod+shelf`: штанга с полкой над ней. Это
одна типовая конструкция, а не два независимых наполнения; делить её на
две ячейки значило бы навязать разделитель, которого в изделии нет.

### 17.4 Дверь — не наполнение ячейки

`DOOR` из задания в этой модели не `LeafFill`. Фасад может закрывать
НЕСКОЛЬКО ячеек сразу, поэтому живёт отдельно: `Furniture.facades:
FacadeGroup[]` с полем `covers`, указывающим на узел дерева или на корпус
целиком (`docs/DATA_MODEL.md` §7). Добавить `door` в `LeafFill` значило бы
завести второй способ описать ту же дверь.

Геометрия фасадов — этап 22 плана, здесь не реализуется.

### 17.5 Контракт резолвера

Реализация — `src/geometry/content.ts`:
```ts
resolveContentGeometry(fill: LeafFill, cellId: NodeId): ContentResolution
```
Чистая функция: не читает часы, не обращается к DOM, не зависит от React,
одинаковый вход даёт одинаковый результат. Геометрических формул не
содержит — отвечает только на вопрос «что означает это наполнение».
Координаты полок и фасадов ящиков по-прежнему считают `stages/fill.ts`
(полки) и `src/geometry/drawers.ts` (фасады ящиков, PROMPT 11) из объёма
ячейки.

| `status` | Когда | Что делает движок |
| --- | --- | --- |
| `empty` | наполнения нет или оно пусто | не создаёт ни одной детали |
| `built` | геометрия вида реализована (полки — PROMPT 6; фасады ящиков — PROMPT 11, короб при этом остаётся `not-implemented` на уровне `stages/fill.ts`, §19.2) | строит детали |
| `not-implemented` | вид есть в модели, геометрии для него ещё нет (штанга) | детали не строит, сообщает `CONTENT_NOT_IMPLEMENTED` (severity `info`) с указанием, чего не хватает |

**`not-implemented` — явный статус, а не тихий пропуск.** До PROMPT 9
`fill` молча игнорировал ящики и штангу: наполнение в модели было, деталей
не появлялось, и «ящики пока не строятся» ничем не отличалось от «ячейка
пуста» — ни в результате, ни в диагностике, ни на экране. Диагностика
выдаётся один раз на вид наполнения, а не на каждую ячейку.

### 17.6 Как добавить новый вид наполнения

Точка расширения — само объединение `LeafFill`. Порядок:

1. добавить вариант в `LeafFill` (`src/domain/furniture/types.ts`) и в
   Zod-схему (`src/persistence/schema.ts`) — иначе сериализация его
   отвергнет, что и требуется до появления схемы;
2. добавить ветку в `resolveContentGeometry` — TypeScript не даст этого
   забыть: `switch` по дискриминанту без ветки перестаёт компилироваться;
3. пока геометрии нет — вернуть `not-implemented` с описанием, чего не
   хватает; когда появится — `built` и правила в этом документе.

Ветки для `drawers` и `rod` уже проходят этим путём, поэтому точка
расширения не гипотетическая: она рабочая и покрыта тестами.

### 17.7 Что НЕ реализовано

| Вид наполнения | Состояние | Плановый этап |
| --- | --- | --- |
| `empty` | реализовано | — |
| `shelves` | реализовано (PROMPT 6) | — |
| `drawers` (фасад) | реализовано (PROMPT 11) | — |
| `drawers` (короб) | модель есть, геометрии нет — `not-implemented` | 21 (продолжение) |
| `rod`, `rod+shelf` (штанга) | модель есть, геометрии нет — `not-implemented` | 23 |
| дверь (`FacadeGroup`, распашная, 1 ячейка) | реализовано (PROMPT 10) | — |
| дверь (купе/складная/подъёмная, несколько ячеек) | модель есть, геометрии нет — `not-implemented` | 22 (продолжение) |
| обувной модуль | модели нет: конфигурация не подтверждена, `NEEDS_CONFIRMATION` (T-FILL-01) | не назначен |

## 18. ДВЕРИ И ФАСАДЫ ЯЧЕЕК (PROMPT 10)

### 18.1 Почему `FacadeGroup`, а не `DoorContent`

Формулировка задания просила типизированный `DoorContent`, привязанный
к ячейке — тот же приём, каким PROMPT 9 ввёл `Content` для полок/ящиков/
штанги. Здесь он не подходит: `FacadeGroup` существует в модели с ранних
этапов (`docs/DATA_MODEL.md` §7) и намеренно живёт ВНЕ ячейки, потому что
один фасад может закрывать несколько ячеек сразу. Завести рядом
`DoorContent { cellId, … }` означало бы второй способ описать ту же дверь
и два расходящихся источника истины — ровно то, чего проект избегает
с PROMPT 1 (`docs/DATA_MODEL.md` §15, «источник истины один»). Поэтому
PROMPT 10 реализует резолвер и этап конвейера для уже существующей модели,
а не параллельную. Обоснование продублировано в коде —
`src/geometry/doors.ts`, header-комментарий.

Базовый случай (§18.2–18.6) сознательно ограничен `covers.kind === 'node'`,
указывающим на ОДИН лист дерева. Покрытие нескольких ячеек (`covers.kind
=== 'carcass'` или узел-разделение) архитектурно предусмотрено полем
`covers`, но вычисление общего прямоугольника нескольких ячеек — отдельная
задача, не входящая в этот этап; `stages/facades.ts` сообщает об этом
диагностикой `DOOR_COVERAGE_NOT_IMPLEMENTED` (severity `info`) и не строит
деталей — тот же принцип явного статуса, каким PROMPT 9 пометил ящики
и штангу.

### 18.2 Конвейер: Cell → FacadeGroup → resolveDoorGeometry → Part

1. `stages/facades.ts` перебирает `Furniture.facades`;
2. для каждого `FacadeGroup` с `covers.kind === 'node'`, указывающим на
   лист дерева, находит соответствующий `CellBox` среди уже построенных
   `layout`-этапом ячеек (`ctx.getCells()`) — тем же способом, каким
   `fill.ts` находит `LeafNode` для ячейки (`docs/GEOMETRY_RULES.md` §9.7);
3. вызывает чистую функцию `resolveDoorGeometry(facade, cell,
   panelThickness)` (`src/geometry/doors.ts`) — она решает «что означает
   этот фасад» и не строит `Part` сама, тем же разделением обязанностей,
   каким `content.ts` отделён от `fill.ts`;
4. этап создаёт `Part` (роль `facade`, уже существующая роль, не новая)
   для каждой створки, которую резолвер вернул.

Источник истины — `Furniture.facades` и дерево секций, как и у остального
наполнения: дверь не хранит своих X/Y/Z как отдельное состояние — они
выводятся заново из `cell.box` на каждом пересчёте, поэтому изменение
W/H/D/ширины секции/высоты ряда/числа секций автоматически пересчитывает
дверь без специального кода на этот случай (тот же механизм, что и у
полок, §17.5).

### 18.3 Формулы (базовый случай: 1–2 створки на одну ячейку)

Все зазоры — `OverlaySpec` (`docs/DATA_MODEL.md` §7), значения по
умолчанию — `DEFAULT_OVERLAY` (`ASSUMPTION(T-DOOR-02)`: накладные,
зазор между створками 3 мм, по периметру 2 мм).

```
available = cell.box.size.x − 2·gapSide
height    = cell.box.size.y − gapTop − gapBottom
```

Ширины створок делит `resolveSizes(leaves.map(l => l.size), available,
gapBetweenLeaves)` — ТОТ ЖЕ алгоритм, что уже делит секции, ряды и колонки
(§9.2), а зазор между створками играет ту же роль, что и толщина
разделителя в этих делениях. Формула не изобретена заново: `FacadeLeaf.size:
SizeSpec` существовала в модели именно для этого случая ещё до PROMPT 10.

Для одной створки (`leaves.length === 1`) `resolveSizes` вырождается
корректно: `available` целиком, `gapBetweenLeaves` не участвует (делить
нечего).

```
thickness = leaf.thickness ?? panelThickness
```
Тот же приоритет, что у `Shelf.thickness` (§14): своя толщина
переопределяет общую, отдельного умолчания у двери нет.

**Позиция.** `x`, `y` — из `available`/`height` и смещения створки
(`spans[i].offset` из `resolveSizes`, плюс `gapSide`/`gapBottom`).
`z` — передняя грань ячейки: `cell.box.min.z + cell.box.size.z`. В системе
координат этого проекта Z растёт от задней стенки к фасаду
(`stages/carcass.ts`: `carcassZ0`/`carcassDepth` — корпус кончается на
БОЛЬШЕЙ Z, а не на нуле), поэтому дверь начинается на передней грани
ячейки и уходит дальше вперёд на свою толщину, а не внутрь объёма ячейки.

**Почему это исключает пересечения по построению (§14 задания).** Любая
деталь наполнения (полка, перегородка) лежит СТРОГО внутри `cell.box`, то
есть заканчивается по Z не дальше `cell.box.max.z`. Дверь начинается
РОВНО на этой границе и идёт только вперёд — соприкосновение возможно,
пересечение (в смысле `overlaps()`, §15.2, эпсилон-корректное) — нет.
Единственная коллизия, которую стоит проверять отдельно, — две РАЗНЫЕ
двери на одной и той же ячейке (`DOOR_CELL_ALREADY_COVERED`, error); она
и проверяется, набором уже покрытых `nodeId`, без пересчёта пересечений
парами (`findPartOverlaps`, §15.5, остаётся тестовым инструментом, не
частью основного конвейера, тем же обоснованием, что и в PROMPT 7).

### 18.4 Различие overlay/inset (NEEDS_CONFIRMATION)

`OverlaySpec.mode` хранится и передаётся дальше, но в этой версии НЕ
меняет численно ширину/высоту двери: обе меры считаются от `cell.box`
(уже вычисленного проёма). Физический смысл overlay — дверь ШИРЕ проёма,
перекрывает торец соседней панели — не реализован, потому что величина
перекрытия не подтверждена (`NEEDS_CONFIRMATION T-DOOR-06`,
`docs/UNKNOWNS.json`), а не потому что о разнице забыли.

### 18.5 Нереализованные виды (явный статус, не тихий пропуск)

| Случай | Статус резолвера | Диагностика |
| --- | --- | --- |
| `type: 'sliding' \| 'folding' \| 'lift'` | `not-implemented` | `DOOR_COVERAGE_NOT_IMPLEMENTED`, info |
| `covers.kind === 'carcass'` | не доходит до резолвера | `DOOR_COVERAGE_NOT_IMPLEMENTED`, info |
| `covers` указывает на узел-разделение (не лист) | не доходит до резолвера | `DOOR_COVERAGE_NOT_IMPLEMENTED`, info |
| `leaves.length === 0` или `> 2` | `invalid`/`not-implemented` | `DOOR_GEOMETRY_INVALID` (error) / `DOOR_COVERAGE_NOT_IMPLEMENTED` (info) |
| зазоры не оставляют места в ячейке | `invalid` | `DOOR_GEOMETRY_INVALID`, error |
| две двери на одну ячейку | вторая не строится | `DOOR_CELL_ALREADY_COVERED`, error |

Разделение `error`/`info` — то же, что и везде в движке: «геометрия не
помещается при уже заданных пользователем числах» — ошибка пользовательских
данных (как `SHELF_OUT_OF_CELL_BOUNDS`, `HORIZONTAL_WIDTH_NOT_POSITIVE`,
§14), «этот вид фасада ещё не реализован» — ожидаемое информационное
сообщение (как `CONTENT_NOT_IMPLEMENTED`, §17.5).

### 18.6 Команды

`AddFacade`/`RemoveFacade`/`UpdateFacadeLeaf` (`src/state/commands.ts`) —
имена, уже существовавшие в `PLANNED_COMMANDS` с более ранних этапов:
архитектура держала для них место до PROMPT 10, поэтому задание
`addDoorToCell`/`removeDoorFromCell`/`updateDoorConfig` реализовано под
уже принятыми именами, а не под второй парой для того же действия.
`AddFacade` проверяет базовое правило («не более одной двери на ячейку»)
на уровне команды, а не только валидацией — чтобы в истории неоткуда было
взяться двум дверям одной ячейки. Все три — обычные Immer-команды: history,
undo/redo и сериализация работают тем же механизмом, что и у остальных
команд, без специального кода на этот случай.

## 19. ЯЩИКИ И ФАСАДЫ ЯЩИКОВ (PROMPT 11)

### 19.1 Почему `Drawer[]` внутри `LeafFill`, а не `DrawerContent`

В отличие от двери (§18.1), ящик НЕ нуждался в отдельной модели вне
ячейки: `LeafFill.kind === 'drawers'` существовал с PROMPT 1
(`docs/DATA_MODEL.md` §5.5) — один ящик физически не может обслуживать
несколько ячеек сразу, поэтому структурная вложенность (наполнение лежит
ВНУТРИ ячейки) здесь корректна с самого начала. Заводить
`DrawerContent { cellId, … }` рядом с уже существующим `Drawer` значило
бы завести второй способ описать то же самое — тот же довод, которым
PROMPT 9 отклонил отдельный тип `Content` для полок (`docs/DATA_MODEL.md`
§5.5). PROMPT 11 реализует резолвер для УЖЕ существующей модели
(`src/geometry/drawers.ts`), а не параллельную.

### 19.2 Фасад — да, короб — нет

Реализована только геометрия ФАСАДА ящика. Сборка короба (боковины, дно,
передняя и задняя стенки короба) требует схемы, которую референс не
подтвердил (`T-DRW-02`: тип направляющих, материал и монтаж дна —
`unknown`). Строить пять деталей короба наугад значило бы придумать
конструкцию — PROMPT 11 §7 явно это запрещает. Короб остаётся
`not-implemented`: `stages/fill.ts` сообщает об этом диагностикой
`DRAWER_BOX_NOT_IMPLEMENTED` (`info`) один раз на сборку, тем же явным
статусом, каким PROMPT 9 пометил ящики и штангу до появления этого файла.

`PartRole` уже содержит `drawer-front`/`drawer-side`/`drawer-back`/
`drawer-bottom` — они существовали в модели заранее и остаются
незанятыми до тех пор, пока схема сборки короба не будет подтверждена;
заводить для них геометрию сейчас означало бы то же самое додумывание.

### 19.3 Формулы (фасад)

Зазоры — `Drawer.facade.overlay` ПЕРВОГО ящика стопки, если задан, иначе
`DEFAULT_OVERLAY` (`ASSUMPTION T-DRW-04`: второй тип зазоров для ящиков
не заводится, переиспользован тот же `OverlaySpec`, что и у дверей, §18.3).

```
facadeWidth = cell.box.size.x − 2·gapSide
available   = cell.box.size.y − gapTop − gapBottom
```

Высоты фасадов делит `resolveSizes(drawers.map(d => d.size), available,
gapBetween)` — ТОТ ЖЕ алгоритм, что уже делит секции, ряды, колонки и
створки двери (§9.2, §18.3), только вдоль оси Y (ящики стоят один над
другим), а не X. `facadeWidth` — одна ширина на все фасады стопки:
вертикальный ряд не делится по X.

```
thickness = drawer.facade.thickness ?? panelThickness
```
Тот же приоритет, что у `FacadeLeaf.thickness` (§18.3).

**Позиция.** `x = cell.box.min.x + gapSide`; `y` — из офсета
`resolveSizes` (порядок массива — БЕЗ переворота: `drawers[0]` получает
наименьший Y, то есть нижний ящик, та же конвенция, что уже действует
для `Shelf.placement.index` в `planAutoShelves`, §14); `z = cell.box.min.z
+ cell.box.size.z` — передняя грань ячейки, та же формула и то же
обоснование отсутствия пересечений с наполнением, что у двери (§18.3):
фасад ящика начинается ровно на границе `cell.box` и уходит только
вперёд, поэтому не может пересечься ни с чем внутри ячейки по построению.

Количество ящиков в ячейке НЕ ограничено искусственно (`ASSUMPTION
T-DRW-05` — реального верхнего порога референс не подтвердил): единственная
граница — помещаются ли фасады по высоте, и её уже проверяет `resolveSizes`
(`overconstrained`/`underconstrained`), тем же способом, что и у секций,
рядов и колонок.

### 19.4 Диагностика

| Случай | Статус резолвера | Диагностика |
| --- | --- | --- |
| `drawers.length === 0` | `built`, `facades: []` | нет (симметрично `shelves: []`) |
| зазоры не оставляют места в ячейке | `invalid` | `DRAWER_GEOMETRY_INVALID`, error |
| фасады не помещаются по высоте (`resolveSizes`) | `invalid` | `DRAWER_GEOMETRY_INVALID`, error |
| ящики есть, короб не строится | `built` (фасад), короб — нет | `DRAWER_BOX_NOT_IMPLEMENTED`, info |
| дверь назначена на ячейку с ящиками | дверь не строится | `DOOR_CELL_HAS_DRAWERS`, error |

Та же граница error/info, что и у двери (§18.5): «зазоры не оставляют
места при уже заданных пользователем числах» — ошибка пользовательских
данных, «короб ещё не реализован» — ожидаемое информационное сообщение.

### 19.5 Дверь и ящик несовместимы в одной ячейке

`stages/facades.ts` проверяет `node.fill.kind === 'drawers' &&
node.fill.drawers.length > 0` перед тем, как построить дверь для ячейки,
и отказывает с `DOOR_CELL_HAS_DRAWERS` (error), если условие истинно.
Правило явное (PROMPT 11 §14), а не догадка: у ячейки одно наполнение
(§17.3), и когда это `drawers`, фасады ящиков уже занимают переднюю
плоскость ячейки — второй, конкурирующий фасад (дверь) на той же
плоскости не имеет физического смысла. `Drawer ↔ Shelf` коллизии
архитектурно невозможны той же причиной: `LeafFill` — размеченное
объединение, ячейка не может одновременно иметь `shelves` и `drawers`.

### 19.6 Команды

Отдельные `addDrawerToCell`/`removeDrawerFromCell`/`updateDrawerConfig`
НЕ заведены: ящик — уже существующий `LeafFill.kind === 'drawers'`,
поэтому та же команда `SetFill`, что уже обслуживает полки с PROMPT 6/9,
обслуживает и его. Второй командный слой для того же действия означал бы
вторую систему состояния (PROMPT 11 §17, §28) — то же решение, каким
PROMPT 6/9 обошлись без отдельных `addShelf`/`removeShelf`.

## 20. РУЧКИ, PUSH-TO-OPEN И МЕХАНИЗМЫ ОТКРЫВАНИЯ (PROMPT 12)

```
Cabinet → Cell → Content → Facade → Opening System → Hardware Parts
```

### 20.1 Почему `OpeningSystem` вложен в фасад, а не отдельная сущность

Ручка или push-to-open физически не существуют без фасада, который они
открывают — тот же класс структурной корректности, что PROMPT 9 применил
к `Content` (лежит в ячейке) и PROMPT 11 — к фасаду ящика (лежит в
`Drawer`). `OpeningSystem` лежит на `FacadeLeaf.opening` (дверь) и
`DrawerFacadeSpec.opening` (ящик), а не в отдельном списке со ссылкой
`targetFacadeId`/`targetContentId`, которые буквально просит PROMPT 12 §3:
ссылаться по id было бы вторым способом выразить то, что уже выражено
вложенностью, и вернуло бы проблему битой ссылки, которую вложенность
устраняет по построению (осиротевшей ручки не бывает структурно, §20.5).

Это заменяет прежнее поле `handle?: HandleSpec | null` (существовало с
ранних этапов, геометрией никогда не читалось): `null` неявно значил
push-to-open — тот самый `hasHandle`-подобный магический флаг, которого
PROMPT 12 §2 прямо просит избегать. `OpeningSystem.kind` делает три
состояния (`none`/`handle`/`push-to-open`) явными без спецзначений.

### 20.2 Почему ручка — `Part`, а не отдельный список

`GeometryContext.addPart`/`finish()` (`src/geometry/context.ts`) несёт
комментарий, написанный ещё на PROMPT 7, до появления самих ручек:
«наполнение, фасады и фурнитура (этапы 11+) шлют детали через тот же
`addPart` и получают эту защиту бесплатно». PROMPT 12 реализует ровно это
— `Part.role` расширен значениями `'handle'`/`'push-to-open'`, и обе роли
идут в `GeometryResult.parts` наравне с фасадом/полкой/перегородкой:
второй список в `GeometryResult`, вторая проверка инвариантов и второй
Geometry Engine не заводятся (PROMPT 12 §25).

Материал ручки — тот же `MaterialId`/`MaterialLibrary`, что и у панелей
(`resolveMaterial(materials, 'handle')`/`resolveMaterial(materials,
'push-to-open')`, тот же fallback-с-предупреждением, что и у остальных
ролей): вторая Material System не заводится. Расчёт количества
петель/направляющих/крепежа под конкретную ручку остаётся задачей будущего
Hardware Engine (`src/domain/hardware/types.ts`, уже существующий каталог
`HardwareKind`/`HardwareItem`, не расширяется геометрией на этом этапе) —
Opening System определяет СПОСОБ открывания, Hardware посчитает, что для
него нужно, позже (PROMPT 12 §12).

### 20.3 Резолвер не знает про сторону петель

`resolveOpeningSystemGeometry(opening, facade)` (`src/geometry/
opening-system.ts`) — чистая функция от `OpeningSystem` и уже построенного
объёма фасада (`{x,y,z,width,height,thickness}` — тот же формат, что уже
возвращают `resolveDoorGeometry`/`resolveDrawerFacadeGeometry` для одной
створки/фасада ящика). Она не получает `hingeSide` и не решает, какая
сторона фасада «дальняя от петель» — это решение принимает фабрика по
умолчанию (`createHandleOpeningSystem`/`createPushToOpenSystem`,
`src/domain/furniture/defaults.ts`) ОДИН раз, при создании конфигурации,
и записывает его как обычное число (`HandlePlacement.side`). Резолвер
пересчитывает геометрию из уже готового `HandlePlacement` на каждом
вызове — доменная логика выбора стороны не дублируется в двух местах.

### 20.4 Формулы

```
HandlePlacement:
  anchor: 'top' | 'bottom' | 'center'   — откуда считать offsetY
  side:   'left' | 'right' | 'center'   — откуда считать offsetX
  offsetX, offsetY: Mm
  offsetZ: Mm                            — вынос ручки от плоскости фасада
  orientation: 'horizontal' | 'vertical'
```

Позиция левого-нижнего угла ручки:
```
x = side === 'right' ? facade.x + facade.width  − offsetX − footprint.width
  : side === 'left'  ? facade.x + offsetX
  :                     facade.x + facade.width/2 − footprint.width/2 + offsetX

y = anchor === 'top'    ? facade.y + facade.height − offsetY − footprint.height
  : anchor === 'bottom' ? facade.y + offsetY
  :                        facade.y + facade.height/2 − footprint.height/2 + offsetY

z = facade.z + facade.thickness   — передняя грань фасада, та же формула
                                     и то же обоснование отсутствия
                                     пересечений с наполнением, что у
                                     самого фасада (§18.3/§19.3): ручка
                                     начинается ровно на границе фасада
                                     и уходит только вперёд.
```

`footprint` (габарит ручки в плоскости фасада), `ASSUMPTION(T-HW-06)`:
```
bar:                width = HandleSpec.lengthMm ?? 128, height = 14   (orientation: horizontal)
                     width = 14, height = HandleSpec.lengthMm ?? 128  (orientation: vertical)
knob/profile/recessed: width = height = 32
```
`thickness` детали (вынос вперёд) = `placement.offsetZ` для ручки; для
push-to-open — `pushToOpen.clearance` (footprint 20×20 мм,
`ASSUMPTION T-HW-07`), НЕ `placement.offsetZ`: клиренс механизма — своя
физическая величина, отдельная от произвольного выноса ручки.

Умолчания по умолчанию (`createHandleOpeningSystem`/
`createPushToOpenSystem`): дверь — вертикальная штанга у края,
противоположного `hingeSide`, вертикальный центр фасада, вынос 25 мм;
ящик (`hingeSide` не передан) — горизонтальная штанга по центру ширины,
30 мм от верхнего края; push-to-open — верхний угол со стороны,
противоположной петлям (дверь), либо центр верхнего края (ящик), отступ
40 мм, clearance 3 мм. Ни одно значение не подтверждено референсом —
`T-DOOR-04` (docs/PRIVETMAKET_FUNCTIONAL_SPEC.md) лишь фиксирует, что
координаты ручки МОГУТ быть в присадке, не какие именно.

### 20.5 Валидация и границы фасада

| Случай | Статус резолвера | Диагностика |
| --- | --- | --- |
| `opening.kind === 'none'` | `none`, `items: []` | нет |
| размеры ручки не положительны | `invalid` | `OPENING_GEOMETRY_INVALID`, error |
| ручка/push-to-open выходит за X/Y границы фасада | `invalid` | `OPENING_GEOMETRY_INVALID`, error |
| вынос ручки (`offsetZ`) не положителен | `invalid` | `OPENING_GEOMETRY_INVALID`, error |
| зазор `clearance` push-to-open не положителен | `invalid` | `OPENING_GEOMETRY_INVALID`, error |

Граница X/Y проверяется по формуле фасада (не по Z: вынос вперёд —
ожидаемое поведение самой ручки, не выход за пределы). Та же граница
error, что и у `DOOR_GEOMETRY_INVALID`/`DRAWER_GEOMETRY_INVALID` (§18.5,
§19.4): недопустимая геометрия при уже заданных пользователем числах —
ошибка данных, не «функция не реализована».

**Orphan-ручка невозможна структурно.** `opening` не хранится отдельно от
своей створки/ящика — удаление `FacadeGroup` (`RemoveFacade`) или замена
`drawers` без данного ящика (`SetFill`) убирает `opening` вместе с
владельцем, тем же путём, каким PROMPT 9 гарантировал отсутствие
осиротевшего `Content`. Отдельной проверки «удалить ручку при удалении
фасада» не требуется — нечему остаться.

**Дверь и ящик не получают случайный `OpeningSystem`.** Фабрики
(`createHingedFacade`, `createDrawer`) НЕ задают `opening` вовсе — поле
остаётся `undefined`, резолвер трактует это как `none`. Пересборка сетки
(`SetRoot`/`SetSectionCount`) создаёт новые листья теми же фабриками —
дверь/ящик после пересборки либо не существуют вовсе (структура
изменилась), либо явно заданы пользователем; заведённого по умолчанию
`opening` взяться неоткуда.

### 20.6 Команды

Ни одна из `setOpeningSystem`/`removeOpeningSystem`/`addHandle`/
`removeHandle`/`updateHandleConfig` (PROMPT 12 §15) не заведена отдельно:

- **дверь** — поле `patch.opening?: OpeningSystem` в уже существующей
  `UpdateFacadeLeaf` (PROMPT 10 §18.6). Установка/смена/снятие ручки —
  одна команда с разным значением `opening`, тот же приём, каким уже
  патчатся `hingeSide`/`materialId`/`thickness`/`size`;
- **ящик** — уже существующий `SetFill` (PROMPT 11 §19.6), заменяющий
  весь `drawers[]`; `opening` — поле внутри `facade` заменяемого ящика.

Второй командный слой для того же действия означал бы вторую систему
состояния (PROMPT 12 §25) — то же решение, каким PROMPT 10/11 обошлись
без отдельных команд для фасада/ящика.

## 21. ЭФФЕКТИВНАЯ ТОЛЩИНА И МАТЕРИАЛ ДЕТАЛИ (PROMPT 13)

Реализация — `resolveEffectiveMaterial()` в `src/geometry/parts.ts`,
единственная точка, где деталь узнаёт свой материал и свою толщину.
Вызывают её `stages/fill.ts` (полки, фасады ящиков), `stages/layout.ts`
(перегородки и разделители) и `stages/facades.ts` (дверные створки).

### 21.1 Что было не так до PROMPT 13

`Material.thickness` и фактическая толщина детали были ДВУМЯ
независимыми числами. Геометрия считала `Shelf.thickness ?? panelThickness`
и `Material.thickness` не читала вообще, поэтому полка с назначенным
материалом «стекло 4 мм» получала толщину детали 16 мм — толщину корпуса.
Материал был декорацией: он попадал в `Part.materialId` и в
`quantityGroupKey`, но на геометрию не влиял. PROMPT 13 сводит оба числа
к одному правилу.

### 21.2 Приоритет эффективной толщины

**Формула.**
```
effectiveThickness(part) =
    1. explicit override поля детали      (Shelf.thickness, FacadeLeaf.thickness,
                                           DrawerFacadeSpec.thickness, DividerSpec.thickness)
 ?? 2. Material.thickness назначенного материала
 ?? 3. Dimensions.panelThickness          (только если материал не определён совсем)
```
**Единицы.** Миллиметры, округление `roundMm` (сетка 0.1 мм) — один раз,
в `resolveEffectiveMaterial`, а не на каждом месте использования.
**Обоснование.** Уровень 1 не менялся: `Shelf.thickness ?? …` работал так
с PROMPT 6. Менялось то, что раньше было безусловным «низом» приоритета:
между «своя толщина детали» и «толщина корпуса» встал материал детали.
Уровень 3 остаётся только аварийным: он достижим лишь при пустой
библиотеке материалов, когда никакого `Material` для детали нет.
**Источник.** `ASSUMPTION (T-MAT-03)` — точный порядок референсом не
подтверждён; выбран единственный, не противоречащий уже реализованному
поведению уровня 1.
**Тест.** `tests/unit/geometry/materials.test.ts` («единый приоритет
эффективной толщины», «стеклянная полка не получает толщину корпуса
молча»), `tests/unit/geometry/materials-properties.test.ts`.

### 21.3 Перегородка — исключение, и почему

Толщина перегородки/разделителя (`DividerSpec.thickness`) материалом НЕ
подменяется. Поле обязательное, то есть по факту всегда уровень 1
приоритета, и именно по нему `resolveSizes()` уже поделил ячейки
(§9.2): подставить сюда толщину материала значило бы, что деталь
перегородки перестала совпадать с промежутком, который она разделяет.
Материал перегородки при этом полноценно участвует в назначении
`materialId`/`edge` детали и проверяется на битую ссылку.

### 21.4 Толщина корпуса и материал корпуса — разные числа

`Dimensions.panelThickness` остаётся собственным параметром корпуса:
боковины, крышка, дно и внутренний объём считаются по нему (§4, §5), а
не по толщине корпусного материала. Это сознательно НЕ сведено к одному
числу на этом этапе: правило «толщина корпуса всегда равна толщине
назначенного корпусного материала» референсом не подтверждено, а
подтверждённые формулы каркаса (§13) переписывать без такого
подтверждения нельзя. Расхождение видно пользователю: панель
«Материалы» показывает толщину материала рядом с полем «Толщина»
габаритов, а debug-схема — толщину каждой детали.

### 21.5 Кромка не меняет размер детали (по умолчанию)

Кромление НЕ меняет геометрические размеры детали (`Part.size`) ни при
какой политике: `applyEdgeSizing()` (§8.2) влияет только на размеры
РАСКРОЯ (`Part.cut`), и только при `subtractFromPartSize = true`. При
значении по умолчанию (`false`) кромка не меняет и их. Толщина детали
(`cut.thickness`) кромкой не меняется никогда — кромка клеится на торец,
а не на пласть.
**Источник.** `UNKNOWN (T-EDG-03)` — какой размер показывает карта
раскроя референса. Обе ветки реализованы и покрыты тестами.

### 21.6 Диагностика материалов

| Код | Severity | Когда |
|---|---|---|
| `MATERIAL_NOT_ASSIGNED` | warning | роли не назначен материал, взят первый из библиотеки |
| `MATERIAL_REFERENCE_BROKEN` | error | `materialId` детали или её кромки отсутствует в библиотеке |
| `GLASS_MIRROR_STRUCTURAL_ROLE` | warning | стекло/зеркало назначено несущей роли (`T-MAT-04`) |

`MATERIAL_REFERENCE_BROKEN` — именно ошибка, а не тихая подстановка:
деталь всё равно строится на материале роли (иначе одна битая ссылка в
старом файле остановила бы весь расчёт), но пользователь видит, какая
именно деталь ссылается в пустоту. Тот же код использует и валидация
проекта (`src/validation/rules/references.ts`) для назначений по ролям,
задней стенки и материала проекта — один словарь кодов на оба слоя.

**Тест.** `tests/unit/geometry/materials.test.ts` («битая ссылка полки —
error-диагностика движка», «стекло на перегородке — предупреждение»).
