# Правила раскроя

Документ описывает раскладку производственных деталей на листах
(PROMPT 17). Переход `Part → ProductionPart` — в
`docs/PRODUCTION_PARTS.md`.

Форма описания та же:
**Спецификация → Доменное правило → Реализация → Тест**.
Неподтверждённые величины помечены `NEEDS_CONFIRMATION`.

---

## 1. Группировка

**Спецификация (§11, §13).** Детали группируются по совместимым
параметрам; ЛДСП 16 мм и МДФ 18 мм не объединяются.

**Доменное правило.** Ключ группы — `materialId` И толщина. Толщина
детали может быть переопределена явно (PROMPT 13), и деталь 18 мм
невозможно выпилить из листа 16 мм, сколько бы они ни делили материал.
Направление текстуры в ключ не входит: оно определяется материалом, то
есть уже содержится в первой части ключа.

**Реализация.** `groupKeyOf`, `groupForCutting` — `src/production/grouping.ts`.

**Тест.** `parts.test.ts` Test 13–15: корпус 16 мм и задняя стенка 3 мм
дают ровно две группы.

## 2. Заготовка

**Спецификация (§12).** Модель `CuttingStock` с размерами, пропилом и
обрезной кромкой; архитектура под стандартный, пользовательский и
несколько размеров листа; UI выбора листа не делать.

**Доменное правило.** Заготовка собирается из трёх источников, каждый
отвечает за своё:

| Величина | Источник |
| --- | --- |
| размер листа | `Material.sheet: SheetFormat` (реестр материалов, PROMPT 1) |
| обрезная кромка | `CuttingSettings.trim`, иначе равномерно из `sheet.trim` |
| ширина пропила | `CuttingSettings.kerf` (настройки проекта) |
| материал и толщина | группа раскроя |

Второго справочника листов не заведено: у материала стал бы второй
формат, расходящийся с первым при первом же редактировании. Несколько
размеров листа поддержаны архитектурно — формат принадлежит материалу,
поэтому разные материалы уже дают разные листы; выбор из нескольких
форматов одного материала потребует расширить `Material.sheet` до списка,
и это единственное место, которое придётся изменить.

**Материал без формата листа** — не ошибка расчёта, а неполные данные:
детали такой группы уходят в `unplaced` с причиной `INVALID_STOCK`, а не
раскладываются на выдуманном листе.

**Реализация.** `resolveStock`, `src/production/stock.ts`.

**Тест.** `parts.test.ts` Test 22 — ни один экземпляр не теряется.

## 3. Ширина пропила — `NEEDS_CONFIRMATION`

**Спецификация (§16).** Не придумывать значение, не зашивать в алгоритм,
хранить централизованно.

**Доменное правило.** `CuttingSettings.kerf` в настройках проекта,
меняется командой `SetCuttingSettings`. Значение по умолчанию —
`DEFAULT_KERF = 4` мм, и это ВРЕМЕННОЕ техническое значение, а не
производственный норматив: реальная ширина зависит от пилы конкретного
цеха (обычно 3–4.4 мм). Ровно поэтому оно вынесено одной константой —
чтобы его нельзя было встретить зашитым в раскладке.

**Реализация.** `src/domain/cutting/types.ts`; алгоритм читает
`stock.kerf` и нигде не содержит числовых литералов пропила.

**Тест.** `layout.test.ts` Test 26 (три случая), `cutting-commands.test.ts`.

**Статус:** `NEEDS_CONFIRMATION (T-CUT-01)`.

## 4. Обрезная кромка и рабочая область

**Спецификация (§17).** Деталь не должна попадать в область trim.

**Доменное правило.**

```
usableStockArea = {
  x:      trimLeft,
  y:      trimBottom,
  length: stockLength − trimLeft − trimRight,
  width:  stockWidth  − trimTop  − trimBottom,
}
```

Раскладка работает ТОЛЬКО внутри этого прямоугольника: начальный свободный
прямоугольник листа — это рабочая область, а не лист.

**Реализация.** `usableAreaOf`, `src/production/stock.ts`.

**Тест.** `layout.test.ts` Test 27 (четыре случая) и property-тест
«все размещения внутри рабочей области».

**Статус:** ширина кромки — `NEEDS_CONFIRMATION (T-CUT-03)`; по умолчанию
одно значение `SheetFormat.trim` применяется ко всем четырём сторонам,
архитектура допускает четыре разных.

## 5. Алгоритм раскладки

**Спецификация (§15).** Первый детерминированный 2D-nesting;
прямоугольные детали и листы; поворот 90° при разрешении; пропил; trim;
никаких пересечений и выходов за границы; тяжёлую библиотеку не
подключать.

**Доменное правило.** Гильотинный раскрой с деревом свободных
прямоугольников, детали перебираются по убыванию площади (best-fit
decreasing). Алгоритм не выбирался заново: ровно он записан в
`docs/ARCHITECTURE.md` §9.1 как решение проекта, и причина там же —
гильотинный рез соответствует реальному форматно-раскроечному станку,
который режет лист только насквозь. Раскладка, которую невозможно
распилить, не стоит ничего, какой бы процент использования она ни
показывала.

Шаги:

1. Каждый экземпляр позиции разворачивается в отдельную единицу
   размещения (§22).
2. Единицы сортируются по убыванию площади; при равенстве — по
   идентификатору позиции и номеру экземпляра, иначе одинаковый вход давал
   бы разную раскладку.
3. Для каждой единицы ищется свободный прямоугольник с МИНИМАЛЬНЫМ
   остатком площади среди всех уже начатых листов. Рассматриваются оба
   положения — 0° и 90°, второе только если поворот разрешён.
4. Если не нашлось — открывается новый лист. Если единица не помещается и
   в чистый лист, она уходит в `unplaced` с причиной `TOO_LARGE`.
5. Занятый прямоугольник заменяется двумя остатками: горизонтальный рез
   через весь прямоугольник над деталью и вертикальный в нижней полосе
   справа от неё. Пропил вычитается один раз на каждый рез — деталь
   остаётся своего размера, материал теряется между деталями.

Пересечений не может возникнуть по построению: размещение ЗАБИРАЕТ
свободный прямоугольник и заменяет его двумя непересекающимися остатками.
Проверка (§19) всё равно выполняется — она ловит ошибку в самом
алгоритме, а не в данных.

Оптимальность не гарантируется и не заявляется: задача NP-трудная.

**Реализация.** `layoutGroup`, `src/production/layout.ts`.

**Тест.** `layout.test.ts` Test 23–32 и все семь property-тестов.

## 6. Поворот

**Спецификация (§18).** Алгоритм не должен нарушать запрет ради
эффективности.

**Доменное правило.** Вариант с поворотом добавляется в перебор ТОЛЬКО
при `rotationAllowed` (правило — в `docs/PRODUCTION_PARTS.md` §7). Деталь,
не влезающая без поворота и не имеющая права поворачиваться, уходит в
`unplaced`, а не поворачивается «на этот раз».

**Тест.** `layout.test.ts` Test 25 (три случая), property-тест 4.

## 7. Неразмещённые детали

**Спецификация (§20).** Деталь не удаляется молча.

**Доменное правило.**

| Причина | Когда |
| --- | --- |
| `TOO_LARGE` | не помещается даже в чистый лист |
| `NO_SPACE` | зарезервирована: сейчас недостаток места всегда решается новым листом |
| `INVALID_STOCK` | у материала нет формата листа либо рабочая область непригодна |
| `INVALID_DIMENSIONS` | размер заготовки не положителен |

**Реализация.** `CuttingResult.unplaced`; каждый элемент несёт позицию,
номер экземпляра, физическую деталь-источник и текстовое пояснение.

**Тест.** `layout.test.ts` Test 28, property-тест 3 («размещённые +
неразмещённые = требуемое количество»).

## 8. Отход и процент использования — `NEEDS_CONFIRMATION`

**Спецификация (§21).** Формулы документированы; не путать
геометрический остаток, технологический отход, trim и kerf.

**Доменное правило.**

```
usedArea    = Σ (width × height) размещённых деталей
stockArea   = stockLength × stockWidth                    // полный лист
usableArea  = usable.length × usable.width                // после trim
wasteArea   = stockArea − usedArea
utilization = usedArea / stockArea
```

Что во что входит, буквально:

| Величина | Входит в `wasteArea` |
| --- | --- |
| обрезная кромка (trim) | да |
| пропил между деталями (kerf) | да |
| неиспользованные остатки листа | да |
| площадь самих деталей | нет |

`usedArea` считается по РАЗМЕРУ ДЕТАЛИ, а не по занятому месту с
пропилом: пропил — это потеря, и приписывать её детали значило бы завысить
полезное использование.

**Статус.** База процента (полный лист против рабочей области) референсом
не подтверждена: `NEEDS_CONFIRMATION (T-CUT-02)`. Обе площади считаются и
хранятся в `CuttingLayout`, поэтому смена базы не потребует правки
алгоритма.

**Тест.** `layout.test.ts` Test 31 (две проверки, включая раздельный учёт
рабочей области).

## 9. Трассируемость

**Спецификация (§24).** Цепочка от размещения до ячейки.

**Доменное правило.**

```
CuttingPlacement.sourcePartId
 → Part (геометрия)
 → Part.origin.nodeId
 → Cell / Shelf / Drawer / FacadeLeaf
```

Размещение хранит `sourcePartId` КОНКРЕТНОГО экземпляра, а не позиции: без
этого четыре из пяти одинаковых полок потеряли бы связь со своей ячейкой.

**Реализация.** `expandInstances` раздаёт `sourcePartIds[i]` каждому
экземпляру; `CuttingPlacement` несёт его дальше.

**Тест.** `parts.test.ts` Test 20, property-тест 6.

## 10. Инвалидация

**Спецификация (§29).** Изменение любого влияющего параметра
инвалидирует раскрой.

**Доменное правило.** Отдельного механизма инвалидации нет и не нужно:
раскрой — производная величина, он не хранится, а пересчитывается из
проекта. Изменение габарита, материала, толщины, ширины секций, высоты
рядов, полок, дверей, ящиков, задней стенки, цоколя, столешницы, свесов,
антресоли или фальшпанелей меняет геометрию, а вместе с ней и раскрой.
Хранимый раскрой пришлось бы помечать устаревшим — несуществующему
устареть нечем.

В интерфейсе пересчёт — мемоизация по ссылке на проект, ровно как у
геометрии и фурнитуры: Immer даёт структурное разделение, поэтому ссылка
меняется только при реальном изменении модели.

**Тест.** property-тест 7 (сериализация не меняет расчёт),
`persistence.test.ts` Test 33–34.

## 11. Хранение

Раскрой не сохраняется (§28). В файле проекта лежат только ПАРАМЕТРЫ
раскроя — пропил, обрезная кромка, политика поворота: их задаёт человек.
Карта, координаты размещений и заготовки не сериализуются.

Старый файл без поля `settings.cutting` читается и получает умолчания
(`z.default` в схеме) — без новой версии документа и без миграции,
потому что отсутствие поля здесь однозначно.

**Тест.** `persistence.test.ts` Test 33–34.

## 12. Команды

`SetCuttingSettings` — одна patch-команда на весь `CuttingSettings`
(`kerf`, `trim`, `rotationPolicy`). Три отдельные команды писали бы в один
объект тремя путями.

Команд ручного перемещения деталей по листу нет намеренно (§26, §36):
интерактивного редактора раскроя на этом этапе не существует, а
координата, записанная пользователем в производную раскладку, потерялась
бы при первом же пересчёте.

## 13. Чего здесь нет

Интерактивного редактора раскроя, перетаскивания деталей, присадки, ЧПУ,
PDF, XLS, закупок, цен, склада, производства, заказов, планировщика,
регистрации, бэкенда и внешних сервисов расчёта. Раскрой считается
локально, в браузере пользователя.
