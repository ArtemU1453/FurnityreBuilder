# Архитектура хранения

Реализация: `src/persistence/`. Проверки: `tests/unit/persistence/`.

---

## 1. ЗАДАЧА

Приложение работает без регистрации и без сервера. Значит проект существует
только на устройстве пользователя, и потеря работы — худший из возможных
исходов. Хранение здесь не вспомогательная подсистема, а часть основного
обещания продукта.

---

## 2. ВЫБОР ХРАНИЛИЩА

| Вариант | Решение | Обоснование |
| --- | --- | --- |
| `localStorage` | **только настройки интерфейса** | Синхронный: сериализация крупного проекта блокирует поток и роняет кадр. Лимит около 5 МБ. Хранит только строки |
| **IndexedDB** | **основное хранилище проектов** | Асинхронный, вмещает на порядки больше, поддерживает транзакции, индексы и бинарные значения (превью в будущем) |
| JSON-файл | **обмен и резервная копия** | Пользователь физически владеет своими данными; файл открывается текстовым редактором |

Реализация IndexedDB — через `idb`: тонкая обёртка, дающая промисы вместо
событий. Собственная обёртка над сырым IndexedDB заняла бы столько же кода
и была бы менее проверенной.

## 3. АБСТРАКЦИЯ `ProjectRepository`

```
UI → Application layer → ProjectRepository → Storage
```

Интерфейс запрещает интерфейсу приложения обращаться к хранилищу напрямую:

```ts
interface ProjectRepository {
  list(): Promise<ProjectSummary[]>;
  load(id: ProjectId): Promise<ProjectDocument | undefined>;
  /** Возвращает записанное: `updatedAt` ставится здесь и больше нигде. */
  save(project: Project): Promise<Project>;
  delete(id: ProjectId): Promise<void>;
  // Добавлено на PROMPT 25 — к этому же интерфейсу, а не рядом с ним.
  has(id: ProjectId): Promise<boolean>;
  create(project: Project): Promise<Project>;
  duplicate(id: ProjectId, ids: IdFactory, name?: string): Promise<Project | undefined>;
  rename(id: ProjectId, name: string): Promise<Project | undefined>;
  isPersistent(): boolean;
}
```

Операции библиотеки выражаются через `load` и `save` целиком и потому
написаны один раз — в `BaseProjectRepository`, от которого наследуются
обе реализации. Правило «что такое переименовать проект» при этом живёт
в домене (`renameProject`, `duplicateProject`), а не в хранилище:
хранилище умеет положить и достать, а ЧТО оно кладёт — решает домен.

Что это даёт на практике:

1. **тесты идут в памяти** — без эмуляции браузера и без асинхронных гонок;
2. **приватный режим деградирует корректно** — при недоступном IndexedDB
   `createProjectRepository()` возвращает реализацию в памяти, и ни одна
   строка UI не меняется;
3. **смена движка хранения не затрагивает ничего выше**.

Запрет на прямой доступ к `localStorage`, `sessionStorage` и `indexedDB`
в слоях выше персистентности проверяется линтером (`no-restricted-globals`)
и тестом `tests/unit/architecture/boundaries.test.ts`.

### Две реализации, один контракт

`InMemoryProjectRepository` — не отладочная заглушка, а рабочий режим.
Обе реализации проверяются **одним и тем же набором тестов**: смысл
абстракции в том, что вызывающий код их не различает.

`isPersistent()` существует, чтобы интерфейс мог честно сказать:
«изменения не сохраняются автоматически, выгрузите проект в файл».
Молча работать в памяти, делая вид, что всё сохранено, — худшее поведение
из возможных.

## 4. ФОРМАТ ДАННЫХ

```ts
interface ProjectDocument {
  schemaVersion: number;
  project: Project;
}
```

Версия лежит **снаружи** проекта: читатель обязан узнать версию до того,
как начнёт разбирать содержимое.

Формат хранения и формат обмена — один и тот же обычный JSON. Никаких
бинарных контейнеров: пользователь без аккаунта должен иметь возможность
забрать свой проект файлом и открыть его чем угодно.

### Схема БД

```
db: 'furniture-builder', version 1
├── projects   keyPath 'id', index 'updatedAt'
└── settings   произвольные ключи
```

Сводные поля (`name`, `createdAt`, `updatedAt`) продублированы рядом
с документом, чтобы список проектов строился без разбора каждого проекта
целиком.

## 5. ВЕРСИОНИРОВАНИЕ И МИГРАЦИИ

```ts
export const SCHEMA_VERSION = 1;
```

Порядок чтения (`deserializeDocument`):

```
1. проверить, что это объект
2. прочитать schemaVersion (versionProbeSchema)
3. применить миграции от версии документа к текущей
4. проверить результат полной схемой (Zod)
5. вернуть типизированный документ
```

Проверка схемой обязательна, потому что импортируемый файл — **недоверенный
вход**. Пользователь может подсунуть чужой JSON, обрезанный файл или
документ будущей версии; ни один из этих случаев не должен приводить
приложение в сломанное состояние. Разбор идёт до попадания данных в стор.

### Правила миграций

- каждая миграция — чистая функция от неизвестной формы к неизвестной форме;
  промежуточные версии типизировать нельзя, их типы уже удалены из кода;
  гарантию даёт схема, применяемая после миграции;
- **документ новее поддерживаемой версии отклоняется целиком**.
  Частично применённый импорт хуже отказа: пользователь решит, что файл
  открылся, и продолжит работу с искажённым проектом;
- отсутствующая миграция — явная ошибка `MigrationError`, а не пропуск шага;
- реестр `MIGRATIONS` сейчас пуст. Заглушки «1 → 1» в нём нет: это было бы
  враньём о наличии миграций.

Проверено тестами: круговой путь домен → JSON → домен не теряет данных;
мусор, испорченная структура и будущая версия отклоняются.

## 7. ПРИВАТНОСТЬ

Данные не покидают браузер. Сервера нет, сетевых запросов приложение не
выполняет — это проверяется E2E-тестом «приложение не выполняет ни одного
внешнего запроса». Экспорт будет реализован как `Blob` и локальная ссылка,
без загрузки куда-либо.
