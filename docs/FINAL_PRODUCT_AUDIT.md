## 7. Инвалидация (§7)

Инвалидации в приложении нет, и это не упущение, а следствие §6:
результат, которого нигде нет, не может устареть.

| Изменённый параметр   | Что пересчитывается                                            |
| --------------------- | -------------------------------------------------------------- |
| Габарит               | геометрия → детали → фурнитура → присадка → раскрой → спецификация |
| Толщина плиты         | то же                                                            |
| Число секций / ширины | то же                                                            |
| Наполнение ячейки     | то же                                                            |
| Фасад, открывание     | то же                                                            |
| Материал, кромка      | детали и далее по цепочке                                        |
| Настройки раскроя     | раскрой и спецификация                                           |
| Перемещение по комнате | ничего из производства                                          |

Последняя строка — единственная нетривиальная: перестановка мебели в
помещении меняет документ, но не меняет ни одной детали, поэтому
производственный расчёт на неё намеренно не подписан. Кнопки
«Пересчитать» нет и быть не может: она обещала бы, что без неё данные
неверны.

Условие двойное намеренно: «не сохранено» само по себе верно и для

истории есть хотя бы одна команда» — отличает «есть что терять» от
«ничего не делали». Откат всех правок через Ctrl+Z снова опустошает
историю, и предупреждение исчезает: на экране опять то, с чего начали.

Автосохранения по-прежнему нет намеренно — см. `PERSISTENCE.md`.

## 10. Пограничные случаи (§10)

Обход 1 → 2 → 3 → 4 → 3 → 2 → 1 через настоящую команду
`SetSectionCount`, а не через сборку дерева вручную. На каждом шаге:
число секций совпадает с заказанным, идентификаторы не повторяются, ни
одна деталь не ссылается на исчезнувший узел, ни одна ячейка не ссылается
на исчезнувший узел, возврат к одной секции даёт ровно исходную
структуру и не оставляет вырожденного деления с единственным ребёнком.

До этого этапа проверялось только движение «вперёд» — а опасно именно
сокращение (D-009).

## 11. Точность (§11)

Найдено два места, сравнивавших миллиметры собственным `1e-6`

`1e-8`, `1e-9` в коде живут в лучевой геометрии, камере и шейдерах, то
есть в нормализованных и радианных величинах, а не в миллиметрах; там
доменный допуск неприменим по смыслу.

## 20. Обработка ошибок (§20)

| Слой               | Как отвечает на ошибку                                          |
| ------------------ | --------------------------------------------------------------- |
| Домен              | Не бросает: некорректное состояние выражается диагностикой       |
| Геометрия          | `Issue` в `diagnostics`, а не исключение; сцена не остаётся пустой без объяснения |
| Валидация          | `Issue` со статусом `PASS`/`WARNING`/`ERROR`/`NEEDS_CONFIRMATION` |
| Расчёты            | Ошибки и предупреждения в результате                             |
| Хранилище          | `RepositoryError`; приватный режим объявляется отдельно          |
| Разбор файла       | `DeserializationError`, `MigrationError` → текст пользователю    |
| Экспорт            | Текст ошибки, кнопка остаётся рабочей                            |
| Интерфейс          | 4 `ErrorBoundary` вокруг рискованных экранов; «Проект не потерян» и кнопка «Попробовать снова» |

Ни в одном месте ошибка не показывается стеком: пользователю нужен
ответ «что делать», а не место в коде. Телеметрии нет — `ErrorBoundary`
пишет только в консоль.

## 26. Сравнение с предыдущим состоянием (§26)

| Состояние                     | Оценка |
| ----------------------------- | ------ |
| Предыдущее (PROMPT 30, `7c63840`) | 85 |

Откуда взялись четыре балла:

- **+2 к надёжности и функциональности** — D-001 был потерей работы при
  обычном действии: восстановленный проект схлопывался нажатием кнопки,
  показывавшей неверное число. Такой дефект в выпуске стоил бы дороже
  всего остального списка вместе.
- **+1 к UX** — D-002 и D-005: два поля перестали выглядеть одинаково,
  кнопка перестала делать то, чего не обещала.
- **+1 к надёжности** — D-003, D-004 и D-009: работа больше не исчезает
  молча при закрытии вкладки, сообщение о несохранённых изменениях снова
  что-то значит, а сокращение числа секций проверено в обе стороны.

Что оценку не подняло и почему: присадка как была пустой, так и осталась
— выдумывать координаты отверстий вместо подтверждённых правил хуже, чем
честно показать пустой раздел; `App.tsx` как был большим, так и остался —
разбирать его на финальном этапе значило бы внести риск ради стройности.
