# Формат .b3d: что удалось восстановить

PROMPT 66 §2. Минимальное достоверное подмножество формата — ровно
столько, сколько нужно для `PM-18` и `PM-17`. Полное описание формата не
ставилось целью и не получено.

Базовый коммит `584d2b3`. Продуктовый код не менялся.

Воспроизводится: `node scripts/research/b3d-parse.mjs <файл> [out.json]`.

---

## FACT — контейнер

| Что | Значение |
| --- | --- |
| Размер файла | 21 761 байт |
| Заголовок | `42 5A 38 35 01 00 00 FF` (`BZ85`…) |
| Сжатие | **zlib**, поток найден сканированием сигнатуры `78 01\|5E\|9C\|DA` |
| Смещение потока | **531** (не жёстко задано: парсер берёт самый большой успешно распакованный поток) |
| Распакованный размер | **381 367 байт** |
| Хвост после потока | 64 байта, не разбирались |

## FACT — таблица имён

```
u32 count            = 583
u32 0
count × ( u32 len + ASCII[len] )
```

Имена ключей — **ASCII, по байту на символ**. Значения-строки — **UTF-16LE**.
Две разные кодировки в одном файле.

Таблица заканчивается на смещении 8116; дальше идёт поток записей.

## FACT — поток записей

```
u32 key    — индекс в таблице имён (1-based) либо идентификатор узла
u32 tag    — 0 у поля; ненулевой у структурного маркера
u8  type   — код типа
value      — по коду типа
```

### Коды типов, встреченные в файле

| Код | Значение | Как установлено |
| --- | --- | --- |
| `0x00` | нет значения | у структурных маркеров |
| `0x01` | `u8` | |
| `0x02` | **нет значения** | см. ниже |
| `0x03` | `u8` (флаг/перечисление) | |
| `0x04` | `i32` | |
| `0x05` | `f64` | кватернионы читаются как ±0.7071067811865476 |
| `0x06` | строка: `u32` длина **в символах** + UTF-16LE | |
| `0x07` | двоичный блок: `u32` длина **в байтах** + байты | не разбирается |
| `0x08` | нет значения | |
| `0x09` | завершитель потока | один раз, за 17 байт до конца |

### Как определена длина `0x02`

Не угадыванием. Перебором: для каждой длины от 0 до 12 поток разбирался
до отказа. Результат:

| Длина `0x02` | Записей до отказа |
| --- | --- |
| 0 | **20 780, до конца файла** |
| 9 | 20 603, отказ на смещении 381 179 |
| остальные | 1…4 |

Только длина **0** доводит разбор до завершителя. Проверяемо: скрипт
перебора воспроизводится тем же парсером.

## FACT — структура объекта

```
{Type, Name, ID}                    заголовок объекта
{X, Y, Z, Rx, Ry, Rz, Rw}           мировое положение + кватернион
{Mat, Thick, Contour}               только у деталей
{X,Y,Z,DirX,DirY,DirZ,Radius,Depth} отверстия, ЛОКАЛЬНЫЕ координаты
```

| `Type` | Что это | Сколько в файле |
| --- | --- | --- |
| `4002` | деталь (панель) | **46** |
| `3001` | экземпляр фурнитуры | **513** |

Отверстия идут **перед** описанием фурнитуры, к которой относятся
(проверено на минификсе и рафиксе), поэтому парсер накапливает их в
буфер и приписывает следующему описанию.

## UNKNOWN — что НЕ разобрано

| Что | Почему не потребовалось |
| --- | --- |
| `Contour` (блок `0x07`, 46 штук) | контуры деталей; размеры взяты из деталировки, которая их уже даёт |
| `Operations`, `Butts`, `Clip` | для расстановки крепежа не нужны |
| Хвост 64 байта после zlib-потока | вне полезной нагрузки |
| Смысл `tag` (1, 2, 3, 4, 7, 8, 9, 12, 13) | группировка объектов восстановлена по полям, не по тегам |

## Оговорка о проприетарности

Разобранный файл — проектный файл заказчика из сервиса-референса. **В
репозиторий он не кладётся** (`BRAND_INDEPENDENCE_AUDIT.md`). Тесты
проверяют формат на файле, собранном по этому описанию здесь же; факты
из настоящего файла проверяются только при заданном `B3D_FIXTURE` и без
него **пропускаются**, а не «проходят».
