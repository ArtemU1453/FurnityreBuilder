# Отчёт о проверке production-выкладки

PROMPT 36 §18. Что именно проверено, на чём проверено и что осталось
непроверенным. Отчёт описывает **факты прогона**, а не намерения.

Дата проверки: 2026-09-10. Версия: `0.1.0`. Идентификатор сборки:
`furniture-builder-v0.1.0-f610a30a718b` (имя кэша service worker'а —
единственное место, где версия видна во время работы).

## Вердикт

**DEPLOYMENT VERIFIED — RELEASE CANDIDATE.**

Не «READY» и не «BLOCKED», и оба слова выбраны, а не смягчены.

Выкладка проверена по-настоящему: сборка развёрнута на обычном
статическом сервере и проверена тем же набором сценариев, что и сам
продукт, — 35 сценариев на развёрнутом приложении, офлайн целиком,
обновление версии двумя настоящими сборками, ноль внешних запросов.
Дефектов, из-за которых приложение не заработало бы у пользователя, не
найдено. Поэтому не BLOCKED.

Но два утверждения этот прогон сделать не может, и делать их не станет:
приложение не выложено на настоящий домен по HTTPS и выпуск не
опубликован. «Проверено на статическом сервере» и «работает на боевой
площадке» — разные утверждения, и второе требует площадки, которой у
проекта нет. Поэтому не READY.

Что переводит в READY: выложить `dist/` в корень HTTPS-домена, пройти
`docs/PRODUCTION_DEPLOYMENT_CHECKLIST.md` на этом адресе и опубликовать
выпуск.

## Release

| | |
| --- | --- |
| Версия в `package.json` | `0.1.0` |
| Ветка | `claude/furniture-designer-audit-cjvvuf` (она же ветка по умолчанию) |
| Git-тег | **не создан** |
| GitHub Release | **не опубликован** |

**RELEASE PUBLICATION NOT EXECUTED.**

Причина названа честно, а не спрятана за «не поддерживается». Тег и
выпуск — действие наружу и почти необратимое: тег появляется у всех, кто
клонирует репозиторий, а выпуск — публичная запись. Указания выкладывать
выпуск не поступало, а работы у прогона ровно одна — проверить, что
сборка выкладывается верно. Всё, что для выпуска нужно, подготовлено;
недостаёт только решения владельца:

```bash
git tag -a v0.1.0 -m "Furniture Builder 0.1.0"
git push origin v0.1.0
```

Площадки размещения у проекта тоже нет: ни конфигурации хостинга, ни
учётных данных в репозитории не заведено, и заводить их этот прогон не
стал бы — это означало бы выбрать за владельца, где живёт его продукт.
Поэтому «развёрнутое приложение» ниже — это настоящий статический сервер
с настоящей сборкой, а не `vite preview`: отличие принципиальное, потому
что предпросмотр Vite подставляет свои заголовки и свой fallback, и
проверять на нём выкладку значит проверять не то.

## Deployment

| | |
| --- | --- |
| Тип | статический сайт, ничего кроме файлов |
| Backend | нет и не планируется |
| Переменные окружения | нет ни одной |
| Учётные записи, оплата, реклама, аналитика | нет |
| Внешние сервисы | нет |
| Проверочная площадка | `node scratchpad/serve.mjs dist 4300` — обычный HTTP-сервер поверх `dist/` |
| Заголовки площадки | `/assets/*` → `public, max-age=31536000, immutable`; остальное → `no-cache` |
| SPA-fallback | проверены оба режима: rewrite на `index.html` и отдача `404.html` |

**Найдено и исправлено в этом прогоне:** требование размещать приложение
**в корне домена** нигде не было записано. Сборка ссылается на файлы от
корня (`/assets/…`), `start_url` и `scope` манифеста — `/`, область
действия воркера — тоже корень. Выложи такую сборку в подкаталог — и
получишь **белый экран без единого сообщения**: браузер запросит
`/assets/index-….js`, хостинг ответит 404, приложение не запустится.
Ошибка молчаливая, а значит самая дорогая.

Записано в `DEPLOYMENT.md` §2 и, что важнее, поставлено под автоматику:
`npm run check:release` теперь отказывает, если ссылки в разметке,
`start_url` и `scope` перестанут указывать на один и тот же корень.
Документация без проверки живёт до первой правки.

## Deep Links

Проверено обращением к серверу, а не чтением конфигурации: у приложения
один адрес, отдельных маршрутов у экранов нет (`DEPLOYMENT.md` §7), и
вопрос только в том, что отдаст хостинг на неизвестный путь.

| Путь | Хостинг с rewrite | Хостинг без rewrite (GitHub Pages) |
| --- | --- | --- |
| `/` | 200, приложение | 200, приложение |
| `/library` | 200, приложение | 404, приложение |
| `/editor` | 200, приложение | 404, приложение |
| `/production` | 200, приложение | 404, приложение |
| `/room` | 200, приложение | 404, приложение |
| `/нет-такого` | 200, приложение | 404, приложение |
| `/a/b/c` | 200, приложение | 404, приложение |

В обоих случаях пользователь видит приложение, а не страницу ошибки
хостинга. Разница только в коде ответа: без rewrite отдаётся `404.html`,
а он у нас копия входной страницы. Это ожидаемая форма для GitHub Pages
и подобных площадок и записана как таковая.

Чего **нет**: ссылка на конкретный экран или конкретный проект. Адрес не
адресует ничего, кроме приложения целиком. Ограничение архитектурное,
записано в `DEPLOYMENT.md` §7 и `FINAL_DEFECT_LIST.md`.

## Production Pipeline

На развёрнутом приложении (FLOW B, FLOW E): деталировка, раскрой,
фурнитура и присадка открываются, отвечают об одном и том же изделии,

не молчит. Подробности — `docs/PRODUCT_CAPABILITY_TRUTH.md`.
