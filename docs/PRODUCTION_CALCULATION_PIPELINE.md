# Конвейер производственного расчёта

Документ описывает единую цепочку от проекта до производственной
спецификации (PROMPT 19 §20). Сами правила — в `docs/PRODUCTION_PARTS.md`,
`docs/CUTTING_RULES.md`, `docs/HARDWARE_RULES.md`,
`docs/DRILLING_RULES.md`; структура спецификации — в
`docs/PRODUCTION_BOM.md`.

---

## 1. Цепочка

```
Project
  ↓ normalize + carcass + layout + fill + back + base + countertop + facades
Geometry                     buildGeometry()          src/geometry/
  ↓ роль → пилят или покупают; группировка одинаковых
Production Parts             toProductionParts()      src/production/
  ↓ правила количества фурнитуры
Hardware BOM                 calculateHardware()      src/hardware/
  ↓ правила присадки: фурнитура + деталь → операции
Drilling Plan                calculateDrilling()      src/drilling/
  ↓ группы «материал + толщина» → листы → гильотинная раскладка
Cutting Result               calculateCutting()       src/production/
  ↓ агрегация деталей, кромки и сводок
Production BOM               buildProductionBOM       src/bom/
  ↓ статус по ошибкам, предупреждениям и подтверждениям
ProductionCalculationResult  calculateProduction()    src/bom/
```

Единственная точка входа — `calculateProduction(project, options?)`.
Она чистая, детерминированная и не знает ни о React, ни о DOM, ни об
экране (§24); граница проверена архитектурным тестом.

## 2. Каждый шаг считается один раз

**Спецификация.** Один прогон конвейера не должен строить одни и те же
детали дважды.

**Доменное правило.** Геометрия строится один раз на изделие и передаётся
дальше явным параметром. Производственные детали и спецификация фурнитуры
передаются в расчёт присадки; раскрой получает ту же геометрию.
Спецификация проекта — слияние спецификаций изделий
(`mergeHardwareBoms`), а не ещё один полный прогон правил.

**Реализация.** `src/bom/engine.ts`. До PROMPT 19 `calculateDrilling` сам
строил детали и фурнитуру — теперь он принимает их через
`CalculateDrillingOptions`, а при отсутствии считает сам, как и раньше:
результат от этого не зависит.

**Тест.** `tests/unit/bom/bom-properties.test.ts` property 4 (детерминизм),
`tests/unit/drilling/*` (расчёт без переданных входов не изменился).

## 3. Аварийная остановка

**Спецификация.** Расчёт не должен строить производные данные поверх
геометрии, признанной непригодной.

**Доменное правило.** Изделие, геометрия которого содержит ошибку, не
даёт ни деталей, ни фурнитуры, ни присадки, ни раскроя. Диагностика при
этом сохраняется и попадает в результат: пустая спецификация с внятной
причиной честнее, чем спецификация из случайных чисел. То же правило
действует на всех четырёх слоях по отдельности.

**Тест.** «изделие с ошибкой геометрии не даёт спецификации».

## 4. Статус результата

| Статус | Когда |
| --- | --- |
| `INVALID` | есть хотя бы одна ошибка |
| `NEEDS_CONFIRMATION` | ошибок нет, но есть неподтверждённые правила |
| `VALID_WITH_WARNINGS` | ошибок и неподтверждённых правил нет, есть предупреждения |
| `VALID` | ничего из перечисленного |

Порядок проверок — порядок серьёзности: проект с критической ошибкой не
может быть `VALID` ни при каких обстоятельствах (§19).

**Сегодня любой проект получает `NEEDS_CONFIRMATION`**: список
неподтверждённых правил не пуст и не будет пуст, пока не подтверждены
пропил, кромка, петли, направляющие, полкодержатели и крепёж. Это не
дефект расчёта, а его честный итог.

## 5. Инвалидация

Отдельного механизма нет и не нужно (§22): результат не хранится, а
пересчитывается из проекта. Меняется что угодно из перечисленного —
габариты, материалы, толщина, секции, полки, двери, ящики, ручки, задняя
стенка, цоколь, столешница, свесы, антресоль, фальшпанели, параметры
раскроя, параметры присадки — меняется вход, а с ним и результат.
Устаревшей спецификации не бывает, потому что хранимой спецификации не
существует.

В интерфейсе пересчёт — мемоизация по ссылке на проект, как у геометрии,
фурнитуры, раскроя и присадки: Immer даёт структурное разделение, поэтому
ссылка меняется только при реальном изменении модели.

## 6. Готовность к экспорту

`ProductionCalculationResult` содержит и агрегат, и все промежуточные
результаты: экспортёру PDF или XLSX нужна спецификация, а карте раскроя и
карте присадки — их собственные полные данные. Пересчитывать что-либо
заново генератору не придётся (§26).

Сами генераторы на этом этапе не создаются.
