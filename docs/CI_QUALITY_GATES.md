# Ворота качества и CI

PROMPT 39. Что проверяется автоматически, какой командой и что случится,
если проверка не пройдёт.

## Главное, что выяснилось при настройке

CI существовал с самого начала — и **не был зелёным ни разу**. Все
тридцать девять прогонов, от PROMPT 11 до PROMPT 38, завершались
падением. Причина одна и та же во всех:

```
Error: Timed out waiting 180000ms from config.webServer.
```

Восемь проверок из десяти при этом честно проходили: реестр
предположений, линтер, типы, тесты, сборка, самостоятельность, размер
чанка, готовность пакета. Падал шаг E2E — и падал не по существу, а
потому что тестовый сервер поднимался не по тому адресу, по которому его
ждали.

`vite preview` слушал `localhost`, а Playwright опрашивал `127.0.0.1`.
`localhost` — имя, а не адрес, и Node с версии 17 не ставит IPv4 первым:
на машине с двойным стеком имя разрешается в `::1`, сервер поднимается
только там, а по `127.0.0.1` не отвечает никто. В контейнере
разработчика `localhost` — это IPv4, поэтому локально всё работало, и
расхождение не замечалось.

Исправлено буквально: сервер и опрашиваемый адрес теперь одна и та же
строка `127.0.0.1` (`playwright.config.ts`). Гадать больше не о чем.

**Вывод, который стоит запомнить: наличие workflow — не то же самое, что
работающие ворота.** Файл лежал, шаги выполнялись, красный значок висел
рядом с каждым коммитом, и никто в него не смотрел. Поэтому в этом
документе у каждых ворот стоит не «настроено», а фактический результат.

## Конвейер

```
Trigger
  ↓
Install (npm ci, из lock-файла)
  ↓
Assumptions registry
  ↓
Lint
  ↓
Typecheck
  ↓
Tests (unit + property + integration, один прогон vitest)
  ↓
Production build
  ↓
Build output check
  ↓
Brand independence
  ↓
Bundle size
  ↓
Release package
  ↓
E2E (chromium)
  ↓
E2E (chromium-dev)
```

Порядок не случаен: дешёвое впереди. Линтер отвечает за секунды, E2E — за
минуты; узнавать об опечатке после четырёх минут прогона незачем.

## Ворота

Все обязательные. Ни у одного нет `continue-on-error`, ни одного `|| true`.

| Ворота | Команда | Задача CI | Блокирует |
| --- | --- | --- | --- |
| Реестр предположений | `npm run check:assumptions` | `verify` | ДА |
| Линтер и границы слоёв | `npm run lint` | `verify` | ДА |
| Типы | `npm run typecheck` | `verify` | ДА |
| Тесты: модульные + property + интеграционные | `npm run test` | `verify` | ДА |
| Production-сборка | `npm run build` | `verify` | ДА |
| Состав артефакта | `test -f dist/…` | `verify` | ДА |
| Самостоятельность продукта | `npm run check:brand` | `verify` | ДА |
| Размер главного чанка | `npm run check:bundle` | `verify` | ДА |
| Готовность пакета | `npm run check:release` | `verify` | ДА |
| Целостность публичного входа | `npm run check:public` | `verify` | ДА |
| E2E: продукт | `npx playwright test --project=chromium` | `verify` | ДА |
| E2E: технический режим | `npx playwright test --project=chromium-dev` | `verify` | ДА |

### Про property- и интеграционные тесты

Оба вида **существуют** и **запускаются**, но своей команды у них нет — и
заводить её не за чем:

| Вид | Где лежит | Чем запускается |
| --- | --- | --- |
| Модульные | `tests/unit/**` | `npm run test` |
| Property | те же каталоги, 20 файлов на `fast-check` | `npm run test` |
| Интеграционные | `tests/unit/integration/` — 9 файлов | `npm run test` |

Vitest берёт `tests/unit/**/*.test.ts` целиком. Разделять их тремя
запусками значило бы трижды поднимать один и тот же процесс ради трёх
строк в журнале. Если понадобится прогнать отдельно — фильтром по пути:

```bash
npx vitest run tests/unit/integration
```

### Про два проекта E2E

Запускаются по отдельности и оба обязательны. Вместе они поднимают два
сервера и мешают друг другу.

- `chromium` — продукт на **production-сборке**. На ней же проверяются
  PWA, работа без сети и чистота консоли.
- `chromium-dev` — технический debug-режим, которого в production-сборке
  нет вовсе (`import.meta.env.DEV`), поэтому ему нужен dev-сервер.

## Что ловит каждая проверка

Перенесено из прежнего `CI.md` — единственное, ради чего он существовал.

| Шаг | Что ловит |
| --- | --- |
| `check:assumptions` | правило, придуманное без записи в `UNKNOWNS.json` |
| `lint` | импорт через границу слоя, React в чистом слое |
| `typecheck` | всё, чего не видит vitest: он выполняет тесты, не типизируя их |
| `test` | инварианты, отмену, детерминированность, регрессию количеств |
| `build` | то, что ломается только в production: мёртвые ветки, чанки |
| состав артефакта | сборка «прошла», но входной страницы или воркера в ней нет |
| `check:brand` | внешний запрос или упоминание референса |
| `check:bundle` | библиотека, въехавшая в загрузку по умолчанию |
| `check:release` | лишний файл в пакете, разошедшийся базовый путь, отладочный вывод |
| `check:public` | битая ссылка входа, localhost, заглушка, README, разошедшийся с адресом публикации |
| E2E | связки между разделами и поведение в настоящем браузере |

`typecheck` стоит отдельным шагом не для порядка: vitest выполняет тесты
без проверки типов, и тест с неверной формой команды проходит зелёным.
На PROMPT 30 этот шаг поймал четыре ошибки в новых тестах.

## Чего в CI нет намеренно

| Чего нет | Почему |
| --- | --- |
| Отчёт о покрытии | процент не отличает проверенный инвариант от просто вызванной строки |
| Визуальные снимки | расхождение в один пиксель красит CI чаще, чем находит дефект |
| Матрица браузеров | приложению нужны WebGL 2 и Pointer Events; вторая среда даёт вторую причину ложных падений, но не второй класс дефектов |
| Внешние сервисы | каждый добавленный сервис — новая причина красного CI, не связанная с кодом |

Артефакты выгружаются, но только при падении и только диагностические
(см. ниже). Это не «публикация»: они живут семь дней и нужны тому, кто
разбирает конкретный упавший прогон.

## Триггеры

| Событие | Что запускает |
| --- | --- |
| `push` в ветку по умолчанию | полный прогон |
| `pull_request` | полный прогон |
| `workflow_dispatch` | полный прогон вручную |

Push проверяется только на ветке по умолчанию — она же рабочая. Прочие
ветки проверяются через pull request, иначе один и тот же коммит
проверялся бы дважды.

Новый push в ту же ветку отменяет предыдущий прогон (`concurrency`):
держать очередь проверок устаревшего кода незачем.

## Установка и кэш

`npm ci` — строго из `package-lock.json`, одно и то же дерево
зависимостей при каждом прогоне. `npm install` не используется: он вправе
подтянуть другие версии и сделать прогон невоспроизводимым.

Кэшируется только загрузка пакетов (`actions/setup-node` с `cache: npm`).
Кэш ускоряет установку, но не подменяет её: `npm ci` всё равно удаляет
`node_modules` и ставит заново. Собранный `dist/` не кэшируется никогда —
источником истины он быть не может.

## Диагностика падения

Каждая проверка — отдельный шаг со своим именем. Упавшие ворота видно в
списке шагов, а не поиском по журналу.

При падении E2E выгружается артефакт `playwright-diagnostics`:

- `playwright-report/` — отчёт с шагами каждого сценария;
- `test-results/` — трассы и снимки экрана упавших сценариев.

Хранятся 7 дней. Ни данных пользователя, ни секретов в них нет:
сценарии работают в пустом браузере, а проекты живут только в его
IndexedDB.

**Повторов нет.** `retries: 0` и в CI, и локально. Повтор допустим только
против подтверждённой нестабильности инфраструктуры; такой здесь не
подтверждено, а «упал с первого раза, прошёл со второго» — это не
зелёный прогон, это невыясненная причина. Трасса снимается при падении
(`retain-on-failure`), а не «при первом повторе»: повторов нет, и старая
настройка не дала бы ни одной трассы.

## Права и безопасность

```yaml
permissions:
  contents: read
```

Workflow только читает репозиторий: ничего не комментирует, не помечает,
не публикует. Секретов он не использует вовсе — у продукта нет ни
переменных окружения, ни ключей, ни внешних сервисов, поэтому и выводить
в журнал нечего.

Внешние действия закреплены мажорными версиями: `actions/checkout@v4`,
`actions/setup-node@v4`, `actions/upload-artifact@v4`.

## CI и выкладка

Один workflow, три задачи по цепочке:

```
verify  ─→  build-pages  ─→  deploy  ─→  smoke
```

Последняя задача проверяет уже ОПУБЛИКОВАННОЕ приложение по адресу,
который отдала выкладка: успешная публикация не доказывает, что
приложение работает (`docs/PRODUCTION_SMOKE_TESTING.md`).

`needs` не запускает задачу, пока предыдущая не завершилась успехом.
Значит любая красная проверка из `verify` останавливает публикацию, не
доводя до неё. Ворота и выкладка при этом не смешаны: `verify` ничего не
публикует и прав на это не имеет, а `build-pages` и `deploy` не проверяют
качество заново.

`build-pages` и `deploy` идут только на push в ветку по умолчанию. Pull
request проходит ворота, но production не подменяет.

Права выданы по задачам, а не всему workflow: `verify` — только чтение;
`build-pages` и `deploy` — плюс `pages: write` и `id-token: write`.
`contents: write` не выдаётся никому.

**До PROMPT 40 связи не было вовсе.** Публикация жила отдельным workflow
и запускалась по тому же push, что и CI, — параллельно. Коммит с красными
воротами попал бы в production, и ничто бы этому не помешало.

Подробно: `docs/GITHUB_PAGES_DEPLOYMENT.md`.

## Как проверить то же самое локально

```bash
npm ci                 # из lock-файла
npm run verify         # реестр → линтер → типы → тесты → сборка →
                       # самостоятельность → размер → готовность пакета
npx playwright test --project=chromium
npx playwright test --project=chromium-dev
```

`npm run verify` закрывает девять из одиннадцати ворот одной командой и
останавливается на первом упавшем. Два прогона E2E запускаются отдельно —
по той же причине, по которой они разделены в CI.
