# Производственные детали

Документ описывает переход от физической геометрии к списку деталей для
изготовления (PROMPT 17). Правила раскроя — в `docs/CUTTING_RULES.md`.

Каждое правило описано по одной форме:
**Спецификация → Доменное правило → Реализация → Тест**.
Неподтверждённые правила помечены `NEEDS_CONFIRMATION`.

---

## 1. Две разные сущности

`Part` описывает ОДИН физический объект в изделии: у него есть положение,
ориентация пласти и происхождение. Он нужен, чтобы нарисовать шкаф и
проверить, что детали не пересекаются.

`ProductionPart` описывает ПОЗИЦИЮ, которую надо изготовить: материал,
размер заготовки, кромка, количество. Пять одинаковых полок — одна позиция
количеством 5, а не пять позиций.

```
Furniture → Geometry → Physical Parts → Production Parts
          → Material Groups → Cutting Stock → Cutting Layout
```

Зависимость односторонняя (§25): раскрой читает геометрию, но не пишет в
неё. Проверено тестом «расчёт не изменяет проект» и архитектурным тестом
границ (`production` не видит `state`).

### Что НЕ заведено заново

Аудит показал, что половина требуемых полей уже существует с PROMPT 1:

| Требование PROMPT 17 | Что уже было | Решение |
| --- | --- | --- |
| `length`/`width`/`thickness` | `Part.cut: CutSize` — размеры раскроя с уже применённой `EdgeSizingPolicy` | переиспользовано |
| `edgeBanding` | `Part.edge: EdgeSpec` (4 стороны в локальных координатах детали) | переиспользовано |
| `grainDirection` | `Material.grain: 'none' \| 'along-length' \| 'along-width'` | переиспользовано |
| `rotationAllowed` | `Part.grainLocked` | переиспользовано как ЗАПРЕТ от геометрии |
| группировка одинаковых | `Part.quantityGroupKey` | переиспользован как ключ позиции |
| формат листа | `Material.sheet: SheetFormat {width, height, trim}` | переиспользован |
| имя детали | `Part.label` («Боковина левая», «Полка 2») | переиспользовано |

Второй справочник ролей, второй формат листа и вторая система имён не
заводились: у каждой величины остаётся один источник.

## 2. Какие детали попадают в производство

**Спецификация (§4–§5).** В раскрой попадают только физические
производимые детали; ячейки, наполнение, фурнитура и служебные объекты —
нет.

**Доменное правило.** Статус объекта выводится из `PartRole` одной
функцией `classifyPart`. Отдельного поля `PHYSICAL/VIRTUAL/DERIVED` в
`Part` не заведено: роль уже отвечает на этот вопрос однозначно, а второе
поле пришлось бы синхронизировать с первым.

| Роль | Статус | Тип позиции |
| --- | --- | --- |
| `side` | physical | `side` |
| `top` | physical | `top` |
| `bottom` | physical | `bottom` |
| `partition` | physical | `partition` |
| `shelf-fixed`, `shelf-adjustable` | physical | `shelf` |
| `back` | physical | `back` |
| `plinth` | physical | `plinth` |
| `countertop` | physical | `countertop` |
| `facade` (двери и фасады ящиков) | physical | `facade` |
| `drawer-front`, `drawer-side`, `drawer-back`, `drawer-bottom` | physical | `drawer-box` |
| `filler` (фальшпанель) | physical | `false-panel` |
| `handle`, `push-to-open` | hardware | — |
| `other` | hardware | — |

**Реализация.** `src/production/parts.ts`, `classifyPart` — исчерпывающий
`switch`: добавление новой роли в `PartRole` не скомпилируется, пока автор
не решит, пилят её из листа или покупают. Молчаливое «по умолчанию в
раскрой» — способ получить в спецификации ручку размером 14×128.

**Тест.** `tests/unit/production/parts.test.ts` Test 1–8, «ручки и
механизмы деталями раскроя не считаются».

## 3. Детали ящиков — `NEEDS_CONFIRMATION`

**Спецификация (§6).** Если ящик состоит из физических деталей, у каждой
должна быть своя позиция.

**Доменное правило.** Модель короба (`DrawerBoxSpec {sideHeight, bottom}`)
в проекте есть с PROMPT 11, но геометрия её не читает: конструкция короба
референсом не подтверждена (`T-DRW-02`). Поэтому деталей `drawer-*` не
существует ни в геометрии, ни в раскрое.

**Реализация.** Архитектура готова: роли заведены, `productionTypeOf`
отображает их в тип `drawer-box`. Фиктивных размеров нет — придумать
высоту боковины короба значило бы выдать догадку за расчёт.

**Тест.** Test 9 — фиксирует именно отсутствие деталей короба и наличие
готового отображения роли.

**Статус:** `NEEDS_CONFIRMATION (T-DRW-02)`.

## 4. Количество и идентичность

**Спецификация (§22).** `quantity = 5` не обязано порождать пять позиций,
но каждый физический экземпляр должен быть размещён.

**Доменное правило.** Позиция объединяет детали с одинаковым
`quantityGroupKey` (роль, материал, размеры раскроя, кромка).
`sourcePartIds[i]` — деталь i-го экземпляра, отсортированные по
идентификатору; `quantity === sourcePartIds.length` проверяется валидацией.

Одинаковыми считаются только по-настоящему одинаковые детали. Три фасада
ящиков высотой 652.7/652.7/652.6 мм — это ДВЕ позиции, а не одна: по
объединённой спецификации распилили бы деталь не того размера.

**Реализация.** `toProductionParts`, `src/production/parts.ts`.

**Тест.** Test 2, Test 5, Test 7.

## 5. Материал и толщина

**Спецификация (§8).** У каждой позиции — свой материал и своя
эффективная толщина; `16` как универсальная толщина запрещена.

**Доменное правило.** Толщина берётся из `Part.cut.thickness`, которую
геометрия уже посчитала через `resolveEffectiveMaterial` (PROMPT 13:
явное переопределение → толщина материала → толщина корпуса). Раскрой
толщину не пересчитывает.

**Реализация.** `toProductionParts`; материал, которого нет в реестре, даёт
ошибку `PRODUCTION_MATERIAL_NOT_FOUND`, а не подстановку «чего-нибудь».

**Тест.** Test 10–11 (корпус 16 мм, задняя стенка 3 мм в одном изделии).

## 6. Кромка

**Спецификация (§9).** Кромка не теряется на пути
`Part → ProductionPart → CuttingLayout` и привязана к конкретной стороне
детали.

**Доменное правило.** Переносится `EdgeSpec` целиком. Стороны —
`front/back/left/right` в ЛОКАЛЬНЫХ координатах детали; соответствие осям
изделия задаёт `Part.orientation` (`docs/DATA_MODEL.md`). Своей системы
сторон раскрой не заводит.

**Реализация.** `ProductionPart.edgeBanding = part.edge`.

**Тест.** Test 12 — боковина с кромкой 2 мм спереди, задняя стенка без
кромки вовсе.

## 7. Направление текстуры и поворот

**Спецификация (§10, §18).** Поворот на 90° недопустим, если его
запрещает текстура или производственное правило; алгоритм не имеет права
нарушить запрет ради эффективности.

**Доменное правило.**

```
rotationAllowed = !part.grainLocked
                && policy !== 'never'
                && material.grain === 'none'
```

Три источника запрета и ни одного источника разрешения вопреки текстуре:
варианта «поворачивать всегда» в `RotationPolicy` нет намеренно — он
позволил бы положить деталь поперёк декора, то есть изготовить брак.

**Реализация.** `rotationAllowedFor`, `src/production/parts.ts`.

**Тест.** Test 16–18 и property-тест «поворот никогда не нарушает запрет».

## 8. Имена

**Спецификация (§23).** Детерминированные имена из типа, секции и
индекса, хранящиеся в одном месте.

**Доменное правило.** Используется существующее `Part.label`, которое
геометрия строит из роли и индекса. Если позиция объединила детали с
разными именами («Полка 1» и «Полка 2»), берётся имя типа («Полка»):
называть пять полок «Полка 1» было бы неправдой.

**Реализация.** `nameFor`, `src/production/parts.ts`.

**Тест.** Test 7 (объединённые фасады получают имя «Фасад»).

## 9. Валидация

| Код | Что ловит |
| --- | --- |
| `PRODUCTION_LENGTH_NOT_POSITIVE` | длина ≤ 0 |
| `PRODUCTION_WIDTH_NOT_POSITIVE` | ширина ≤ 0 |
| `PRODUCTION_THICKNESS_NOT_POSITIVE` | толщина ≤ 0 |
| `PRODUCTION_MATERIAL_NOT_FOUND` | материал отсутствует в реестре |
| `PRODUCTION_QUANTITY_INVALID` | количество < 1 |
| `PRODUCTION_QUANTITY_MISMATCH` | количество не равно числу деталей-источников |
| `PRODUCTION_SOURCE_NOT_FOUND` | ссылка на несуществующую физическую деталь |

**Реализация.** `src/production/validate.ts`. Проверяется собственный
результат движка: ошибка здесь означает ошибку алгоритма, а не ввода.
