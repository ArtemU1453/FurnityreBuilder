# Целостность публичного входа

PROMPT 42. Что охраняет путь пользователя к приложению и что делать,
когда охрана срабатывает.

## Public Entry Point

Единственный путь пользователя к продукту:

```
репозиторий  →  README  →  «Открыть приложение»  →  рабочее приложение
```

Ссылка живёт в разделе `## Открыть приложение` — вторым заголовком
README, сразу после описания продукта. Не в конце, не в документации, не
в описании репозитория: посетитель не должен её искать.

## Production URL Source

**Адрес не записан в проекте константой.** Он определяется устройством
самой площадки:

```
https://<владелец>.github.io/<репозиторий>/
```

Поэтому проверка его **вычисляет** — из `GITHUB_REPOSITORY` в CI, из
адреса `origin` локально. Второго источника истины нет и не заводится:
две записи одного адреса расходятся молча, и разошедшуюся правильную
замечают позже, чем битую.

Фактический адрес сегодня: **https://artemu1453.github.io/FurnityreBuilder/**

Он же приходит из вывода выкладки (`deploy.outputs.url`) и туда же
направляется дымовая проверка.

## README Validation

`npm run check:public`, он же шаг «Целостность публичного входа» в CI.
Сети не трогает — обязан проходить на каждом pull request, даже когда
площадка недоступна.

| Проверка | Что ловит |
| --- | --- |
| Раздел «Открыть приложение» существует | вход убрали или переименовали |
| В разделе есть ссылка | заголовок остался, ссылка исчезла |
| Не локальный адрес | `localhost`, `127.0.0.1`, `0.0.0.0`, `[::1]` после отладки |
| Не заглушка | `example.org`, `YOUR_URL`, `TODO`, `PLACEHOLDER`, `<…>` |
| HTTPS | без него нет ни офлайна, ни установки |
| Совпадает с вычисленным адресом | репозиторий переименовали, ссылку поправили мимо |
| Ни один документ не называет ДРУГОЙ адрес | второй источник истины |
| Собранный пакет отвечает тому же адресу | базовый путь разошёлся с публикацией |

Проверено, что ловит каждый случай:

| Подстановка в README | Результат |
| --- | --- |
| `http://localhost:5173/` | падение: «ссылка входа ведёт на локальный адрес» |
| `https://example.org/` | падение: «ссылка входа — заглушка, а не адрес» |
| `https://…github.io/OtherRepo/` | падение: «не совпадает с адресом публикации» |
| раздел удалён | падение: «пользователю негде найти приложение» |
| `http://` вместо `https://` | падение: «не по HTTPS» |

## Deployment Validation

Что проверяется уже после сборки и выкладки.

### Перед публикацией — `build-pages`

| Проверка | Что ловит |
| --- | --- |
| `check:release` | состав пакета, манифест, service worker, согласованность базового пути |
| `404.html` — копия `index.html` | заглушку «не найдено» вместо приложения |
| Артефакт пригоден | пустая или неполная сборка: нет входной страницы, чанка, стилей, меньше десяти файлов |

### После публикации — `smoke`

| Проверка | Что ловит |
| --- | --- |
| README = адрес выкладки | документация разошлась с тем, что реально опубликовано |
| Дымовая проверка по живому адресу | белый экран, битые чанки, ошибки консоли (`docs/PRODUCTION_SMOKE_TESTING.md`) |

## Consistency Rules

Совпасть обязаны три вещи:

```
ссылка в README  =  вычисленный адрес площадки  =  адрес из вывода выкладки
```

Первые две сверяет `check:public` — без сети, на каждом pull request.
Вторую с третьей сверяет шаг в задаче `smoke` — после выкладки, когда
фактический адрес известен.

Расхождение любой пары — дефект, а не мелочь: пользователь либо не
найдёт приложение, либо попадёт не туда.

## Base Path

Базовый путь защищён отдельно и раньше — в `check:release` (§6a). За
истину берётся разметка: ссылки в ней, `start_url` и `scope` манифеста,
область действия service worker'а и весь его список предзагрузки обязаны
указывать на один и тот же путь.

Разойтись они могут только молча: приложение с неверной базой не падает,
оно показывает белый экран. Поэтому проверок две — статическая здесь и
живая в дымовой проверке, которая тот же белый экран ловит уже на
опубликованном адресе.

Отложенные чанки (`pdf-*.js`, `xlsx-*.js`) статически не проверяются, и
это осознанно: Vite вычисляет их адреса относительно модуля, а не от
корня, поэтому базовый путь на них не влияет. Работоспособность
подтверждается прогоном набора E2E по подкаталожной сборке, где эти
чанки действительно загружаются.

## Routing

Отдельных адресов у экранов нет — навигация внутренняя
(`docs/DEPLOYMENT.md` §7). Значит и «сломать маршрут» нечем; единственный
вопрос к площадке — что она отдаст на неизвестный путь.

GitHub Pages отдаёт `404.html`. Он у нас копия входной страницы, и
совпадение проверяется автоматически: заглушка «не найдено» тихо отменила
бы это поведение, а состав пакета такую подмену не заметил бы.

Что при этом **не** работает и не притворяется работающим: ссылку на
конкретный экран или конкретный проект отправить нельзя. Кнопки «назад» и
«вперёд» по экранам не ходят. Перезагрузка возвращает на начальный экран,
но открытый проект восстанавливается — он в IndexedDB, а не в адресе.

## Failure Handling

**Сработала проверка входа.** Сообщение называет и найденное, и
ожидаемое. Дальше решает не скрипт:

- адрес действительно изменился (репозиторий переименовали, подключили
  домен) → обновить ссылку в README и в документах, которые её называют;
- адрес не менялся → ссылку поправили по ошибке, вернуть.

Автоматически README не переписывается никогда. Смена публичного адреса —
решение, а не опечатка, и принимать его должен человек.

**Разошлись README и выкладка.** Задача `smoke` падает после публикации.
Приложение при этом опубликовано и работает — сломан вход. Чинится
правкой ссылки и следующим прогоном.

**Маскировки нет.** Ни `continue-on-error`, ни `|| true`, ни «любой
адрес сойдёт». Проверка либо проходит, либо роняет прогон.
