# Архитектура экспорта

Документ описывает слой `src/export/` (PROMPT 20): переход от
производственного расчёта к файлам документации. Форматы описаны
отдельно: `docs/PDF_EXPORT.md`, `docs/XLSX_EXPORT.md`.

---

## 1. Цепочка

```
Project
  ↓ calculateProduction()            src/bom/    (PROMPT 19)
ProductionCalculationResult
  ↓ buildProductionExportData()      src/export/data.ts
ProductionExportData
  ↓ createProductionPdf()            src/export/pdf.ts
  ↓ createProductionXlsx()           src/export/xlsx.ts
файл
```

Экспорт **не считает ничего производственного**. Ни размера, ни
количества, ни раскладки: всё приходит готовым из
`ProductionCalculationResult`. Второго расчётного движка нет — граница
проверена архитектурным тестом (`export` не видит `state`, не знает
React и DOM).

## 2. Зачем отдельный слой данных

Генераторы документов не должны знать ни о геометрии, ни о правилах
производства: их работа — разложить готовые числа по страницам и
ячейкам. `ProductionExportData` фиксирует эту границу. Если завтра
появится третий формат, он получит те же данные, а не начнёт
«дочитывать» недостающее из модели напрямую — именно так в проектах и
заводится второй расчётный движок.

Содержимое — плоские строки таблиц: у ячейки XLSX нет способа сослаться
на объект. Значения уже отформатированы там, где это отображение, и
оставлены числами там, где это число.

| Раздел | Источник |
| --- | --- |
| `metadata`, `dimensions` | `Project`, `ProductionBOM.version`, статус расчёта |
| `parts` | `ProductionBOM.parts` |
| `drawings` | `ProductionBOM.parts` + `DrillingPlan` |
| `hardware` | `HardwareBOM.lines` |
| `drilling` | `DrillingPlan.operations` + переход в мировые координаты |
| `placements`, `sheets`, `unplaced` | `CuttingResult.layouts` / `unplaced` |
| `materials` | `ProductionBOM.parts` + `CuttingSummary.stocks` |
| `edgeBanding` | `ProductionBOM.edgeBanding` |
| `confirmations` | `ProductionBOM.confirmations` |

## 3. Единицы и округление

**Спецификация (§10).** PDF и XLSX обязаны показывать одно и то же число
одинаково; внутренняя точность расчёта не меняется.

**Доменное правило.** Все преобразования — в `src/export/format.ts`:
`mmValue` (число для ячейки), `mmText` (строка для страницы), `areaM2`,
`lengthM`, `percentValue`, `edgeText`, `sizeText`. Округление
миллиметров делает `roundMm` — та же функция, которой пользуется
геометрия (`docs/UNITS_AND_PRECISION.md`); второго правила округления не
заводится. Дополнительно снимается «минус ноль»: `-0` в ячейке выглядит
как ошибка расчёта.

**Тест.** «размеры округляются одинаково и не дают хвостов» — ни одно
значение не имеет больше одного знака после запятой.

## 4. Детерминизм

**Спецификация (§13).** Один проект — один результат.

**Доменное правило.** `buildProductionExportData` чистая: момент
генерации передаётся параметром, а не читается из часов. Дата живёт
только в `metadata.generatedAt` и не влияет ни на одну производственную
величину.

XLSX детерминирован побайтово (собственный ZIP без отметок времени).
PDF — структурно: `pdf-lib` при каждом сохранении генерирует случайные
ключи ресурсов и идентификатор файла, поэтому сравниваются страницы, их
формат и заголовок, а не байты. Требование §13 — «same PDF
structure/data» — выполняется именно в этом смысле.

**Тест.** «дата генерации — единственное, что отличается»,
«одинаковые данные дают побайтово одинаковый файл» (XLSX),
«структура документа повторяется при повторном экспорте» (PDF).

## 5. Зависимости

| Что | Зачем | Где |
| --- | --- | --- |
| `pdf-lib` + `@pdf-lib/fontkit` | сборка PDF и подмножество шрифта | зависимость приложения, загружается динамически |
| Liberation Sans | кириллица в PDF | `public/fonts/`, отдаётся своим сервером |
| `exceljs` | ЧТЕНИЕ книги в тестах | только `devDependencies` |

XLSX пишется **без библиотеки**: формат — это ZIP из нескольких XML, а
всё необходимое (контейнер без сжатия и CRC32) укладывается в полторы
сотни строк. Взамен получены побайтовый детерминизм и отсутствие
транзитивных зависимостей у приложения, которое обязано работать офлайн.

`exceljs` намеренно оставлен только тестам: проверять собственный
писатель собственным читателем — самообман, читатель повторил бы ошибку
писателя.

## 6. Загрузка файла и интерфейс

Генераторы возвращают байты и ничего не сохраняют: сохранение —
`src/app/export-actions.ts`, единственное место, знающее о `Blob`,
`document` и `URL.createObjectURL`.

Генератор PDF со шрифтовой библиотекой весит больше, чем всё остальное
приложение, поэтому загружается динамическим `import()` по нажатию, а не
при открытии страницы. Шрифт запрашивается у своего же сервера — в
JS-бандл он не встраивается: полмегабайта base64 достались бы и тем, кто
ничего не экспортирует.

Интерфейс (§19): обе кнопки блокируются на время генерации (двойной
запуск дал бы два файла и вопрос, какой актуален), состояние объявляется
через `role="status"` с `aria-live`, ошибка показывается текстом и не
запирает кнопку — экспорт обязан быть повторяемым.

## 7. Статусы и ограничения

Статус расчёта (`VALID`, `VALID_WITH_WARNINGS`, `NEEDS_CONFIRMATION`,
`INVALID`) выносится на титульный лист PDF и в первые строки листа
«Сводка».

**Экспорт не запрещается при `INVALID`.** Документ нужен ровно для того,
чтобы увидеть, ЧТО не так: список ошибок в нём и находится. Запрет
оставил бы пользователя без единственного внятного отчёта. Вместо
запрета документ помечается предварительным — крупно, на первой
странице.

Неподтверждённые правила (`ProductionBOM.confirmations`) печатаются
целиком, отдельным разделом: «часть данных предварительна» без перечня —
бесполезная оговорка.

## 8. Трассируемость

`ExportPartRow.sourcePartIds` несёт идентификаторы физических деталей
всех экземпляров позиции; `ExportPlacementRow.partId` и
`ExportDrillingRow.partId` — идентификатор производственной позиции.
Цепочка `Cell → Part → ProductionPart → PartBOMItem → строка документа`
восстанавливается по ним целиком. Ни один идентификатор экспортом не
выдумывается и не генерируется заново при каждом запуске (§12).

## 9. Чего здесь нет

Цен, себестоимости, склада, закупок, поставщиков, заказов,
производственного workflow, ЧПУ и G-code, планировщика, регистрации и
бэкенда. Экспорт формирует документы и ничего не отправляет: файл
сохраняется на диск пользователя.
