# Производственная спецификация

Документ описывает структуру `ProductionBOM` (PROMPT 19). Цепочка расчёта
— в `docs/PRODUCTION_CALCULATION_PIPELINE.md`.

Форма описания: **Спецификация → Доменное правило → Реализация → Тест**.

---

## 1. Что это и чем не является

`ProductionBOM` — АГРЕГАТ уже посчитанного, а не новый источник истины
(§2). Он ничего не вычисляет заново и не хранит второй копии данных, у
которых уже есть владелец:

| Раздел | Откуда | Новое? |
| --- | --- | --- |
| `parts` | `ProductionPart[]` | да — строка деталировки |
| `edgeBanding` | размеры деталей + `EdgeSpec` | да — сводка метража |
| `hardware` | `HardwareBOM` как есть | нет |
| `drilling` | `DrillingPlan` | нет, только сводка поверх |
| `cutting` | `CuttingResult` | нет, только сводка поверх |
| `confirmations` | статусы правил | да — сборка из существующего |

Второй спецификации фурнитуры не заводится: `bom.hardware` — это тот же
объект, что и `result.hardware` (проверено тестом на идентичность
ссылки). Второй модели отверстий тоже нет.

**Что удалено.** `HardwareLine` из `src/domain/hardware/types.ts` —
строка спецификации, заведённая на PROMPT 1 и ни разу не использованная:
её место заняла `HardwareBomLine` (PROMPT 16). Две строки спецификации
рядом — два ответа на один вопрос, и второй неизбежно отстаёт.

## 2. Строка деталировки

```ts
interface PartBOMItem {
  id: string;                        // bom:<ключ группировки>
  productionPartIds: string[];       // производственные позиции
  name, partType, category;
  materialId, materialName, materialKind, thickness;
  length, width, quantity;
  grainDirection, edgeBanding;
  sourcePartIds: PartId[];           // физические детали всех экземпляров
  sourceNodeIds: NodeId[];
}
```

Размеры, имя материала и кромка — **snapshot** (§4): спецификация
материализует их, чтобы экспорт не пересчитывал деталь заново. Источник
истины остаётся один — `productionPartIds` ведут к нему, а расхождения не
возникает, потому что снимок делается в том же прогоне конвейера.

Независимой копии каталога материалов в спецификации нет (§9): имя и
категория берутся из `MaterialLibrary` в момент расчёта.

## 3. Группировка

**Спецификация (§7).** Детерминированный ключ; детали с разными
производственными свойствами не объединяются.

**Доменное правило.** Ключ — тип, материал, толщина, длина, ширина,
направление текстуры, кромка (включая её материал):

```
partType | materialId | thickness | length | width | grain | edge
```

Роль детали в ключ **не входит**: стационарная и съёмная полка одного
размера из одного материала с одной кромкой — одна панель на распиле и
одна строка спецификации. Кромка, наоборот, входит: две детали 720×560 с
разной кромкой оклеиваются по-разному, и объединять их нельзя.

**Реализация.** `bomGroupKey`, `src/bom/parts.ts`.

**Тест.** «детали с разной кромкой не объединяются», «роль детали в ключ
группировки не входит».

## 4. Количество и отсутствие двойного счёта

**Спецификация (§8, §28).** Количество не должно удваиваться.

**Доменное правило.** Количество строки — сумма `ProductionPart.quantity`
её позиций, и оно РАВНО числу физических деталей-источников. Раскладка на
листах количество не меняет: экземпляр, не поместившийся на лист, не
исчезает из спецификации, а попадает в `unplacedParts`.

Три места, где двойной счёт был бы возможен, и почему его нет:

| Риск | Почему не возникает |
| --- | --- |
| `ProductionPart.quantity` + размещения | количество берётся ровно из одного места — из позиции |
| `HardwareBOM` + спецификация | `bom.hardware` — тот же объект, а не пересчёт |
| `DrillingPlan` → детали | операции присадки не порождают деталей вовсе |

**Тест.** Test 5–8 и property 3 («количество строки равно числу её
деталей-источников», «одна физическая деталь входит ровно в одну строку»).

## 5. Кромка

**Спецификация (§10).** Метраж не оценивается приблизительно.

**Доменное правило.** Стороны `left`/`right` лежат на концах ДЛИНЫ,
поэтому их полоса идёт вдоль ширины детали; `front`/`back` — наоборот
(`docs/COORDINATE_SYSTEM.md` §5). Это то же соответствие, по которому
кромка уменьшает размер раскроя, — второго толкования сторон нет. Каждая
сторона учитывается столько раз, сколько экземпляров у позиции.

Группировка — по толщине и материалу кромки. Материал кромки в проекте
может быть не назначен (`EdgeSpec.materialId` необязателен), и это
рабочая конфигурация: строка получает имя «Кромка N мм (материал не
назначен)».

**Реализация.** `buildEdgeSummary`, `src/bom/parts.ts`.

**Тест.** Test 11 и «кромка 0.4 мм по бокам считается по ширине детали».

## 6. Сводки присадки и раскроя

Сводка — производное представление, а не замена подробностей: и
`DrillingPlan`, и `CuttingResult` целиком остаются в
`ProductionCalculationResult` (§11).

`DrillingSummaryItem` несёт число операций, множества граней и типов
операций и сами операции. `CuttingSummary` берёт числа из раскладки:
количество листов равно числу раскладок, а не считается вторым
алгоритмом (§12–§13).

**Тест.** Test 12–14.

## 7. Производственная структура

Разделы (§16) соответствуют фактическим типам деталей проекта:

```
Product
 ├── carcass      боковины, крышка, дно, перегородки
 ├── shelves      полки (стационарные и съёмные)
 ├── doors        двери и фасады ящиков
 ├── drawers      детали короба ящика — пусто (T-DRW-02)
 ├── back-wall    задняя стенка
 ├── plinth       цоколь
 ├── countertop   столешница
 ├── false-panels фальшпанели
 └── other        типы без своего раздела
```

Раздел `drawers` существует, но пуст: геометрия не строит деталей короба,
потому что конструкция не подтверждена. Фиктивных разделов «на будущее»
не заводится.

## 8. Идентичность позиции

**Спецификация (§14).** Изменение количества не создаёт новой логической
позиции; изменение свойств, делающее деталь другой, — создаёт.

**Доменное правило.** `id` строки выведен из ключа группировки, то есть
из производственных свойств детали. Количество в ключ не входит: добавили
третью полку — та же строка, количество 3. Поменяли материал, толщину,
размер, текстуру или кромку — деталь стала другой, и это другая строка.
Та же политика, что у `Part` (`docs/DATA_MODEL.md` §5.7) и у
`ProductionPart`: идентичность выводится из сущности, а не из счётчика.

**Тест.** Test 22 («добавленная полка появляется сама», «изменение
габарита меняет размеры строк, но не их количество»).

## 9. Трассируемость

```
PartBOMItem → productionPartIds → ProductionPart → sourcePartIds → Part
                                                 → origin.nodeId → Cell / Content
PartBOMItem → sourcePartIds → Part (напрямую, без промежуточного шага)
bom.hardware.lines[].sources → HardwareItem → sourcePartId / sourceNodeId
bom.drilling.items[].operations → DrillingOperation → sourceHardwareId, sourcePartId
```

Строка спецификации хранит источники ВСЕХ экземпляров, а не одного: без
этого четыре из пяти одинаковых полок потеряли бы связь со своей ячейкой.

**Тест.** Test 19–20, property 1–2.

## 10. Ошибки, предупреждения и подтверждения

**Спецификация (§17).** Спецификация собирается и при некритичных
предупреждениях.

| Уровень | Примеры |
| --- | --- |
| `error` | неизвестный материал (`BOM_MATERIAL_NOT_FOUND`), деталь без размеров (`BOM_PART_WITHOUT_SIZE`), неразмещённая деталь (`BOM_PART_NOT_PLACED`), ошибки нижних слоёв |
| `warning` | неподтверждённое правило, отсутствующий формат листа, недостающая связь деталей |

Неразмещённая деталь — ошибка **спецификации**, а не раскроя: по такой
спецификации изделие изготовить нельзя, сколько бы листов ни купили.

**Тест.** Test 17–18.

## 11. Неподтверждённые правила

**Спецификация (§18).** Централизованный список; спецификация не прячет
ограничений.

**Доменное правило.** Список собирается из статусов правил
(`HardwareRule.status`/`unknownId`, `DrillingRule` — то же самое),
поэтому не может отстать от кода: подтвердили правило, поменяли статус —
строка исчезла сама. Руками задаются только ограничения без
объекта-правила: параметры раскроя, умолчания кромки, конструкция короба
ящика — и у каждого назван файл-источник.

Категории: `CUTTING`, `DRILLING`, `HARDWARE`, `MATERIAL`, `EDGE`,
`CONSTRUCTION`.

Одно неизвестное может блокировать несколько правил (`T-HW-03` — и
крепёж корпуса, и крепёж задней стенки), поэтому строки различаются полем
`rule`: технологу нужно видеть, ЧТО не посчитано, а не только чего не
хватает.

**Реализация.** `collectConfirmations`, `src/bom/confirmations.ts`.

**Тест.** Test 16.

## 12. Детерминизм и хранение

В результате нет ни одного значения, зависящего от времени или
случайности: `calculationTimestamp` намеренно отсутствует (§3, §21) —
он сломал бы сравнение спецификаций и снапшот-тесты. `version` —
константа формы структуры, а не отметка расчёта.

Спецификация не сериализуется (§23): это производная величина, как
детали, раскрой и присадка. Старые файлы проектов открываются и считаются
без миграции — спецификация к формату документа не привязана.

**Тест.** «в результате нет отметки времени», property 4–5.

## 13. Чего здесь нет

PDF, XLS/XLSX, цен, себестоимости, склада, закупок, поставщиков, заказов,
производственного workflow, ЧПУ, планировщика, финального интерфейса,
регистрации и бэкенда. Технический вывод спецификации
(`formatProductionDebug`) — инструмент проверки конвейера, живёт только в
сборке разработчика.
