# Правила расчёта фурнитуры

Документ описывает единственную систему расчёта фурнитуры (PROMPT 16).
Каждое правило описано по одной и той же форме: **Правило — Вход —
Формула — Результат — Источник — Тесты — Статус**. Статус обязателен и
означает ровно то, что написано:

| Статус | Значение |
| --- | --- |
| `CONFIRMED` | правило подтверждено референсом и реализовано |
| `IMPLEMENTED` | количество следует из конструкции модели и реализовано |
| `AMBIGUOUS` | количество считается, но часть характеристик не подтверждена |
| `NEEDS_CONFIRMATION` | величина неизвестна; количество НЕ выдаётся |

Неизвестное правило не маскируется под готовую реализацию: если величины
нет, движок возвращает предупреждение с уже посчитанным входом (сколько
створок, какой периметр, сколько стыков) и не создаёт ни одной позиции.
Выдуманное число выглядело бы как расчёт и было бы принято за истину —
пустая строка с объяснением честнее.

---

## 1. Фурнитура — производная величина

Ни одно количество не хранится в модели. Поля вида `door.hingeCount` нет и
не будет: число петель вычислимо из створки, а хранимая копия немедленно
разошлась бы с моделью после первого изменения габарита. Цепочка
зависимостей — одна и однонаправленная:

```
Furniture → Geometry → Content → Двери/Ящики → Hardware Rules → HardwareItem → HardwareBOM
```

Стрелки не заворачиваются обратно: правила читают геометрию и модель, но
ничего в них не меняют (тест «расчёт не изменяет проект»). Поэтому любое
изменение слева пересчитывает всё, что справа, автоматически — команды
`setHardwareQuantity()` не существует, и добавить её значило бы завести
второй источник истины.

**Что вызывает пересчёт:** габариты, толщина материала, число секций,
наполнение ячейки, число полок и их тип крепления, число ящиков, тип
направляющей, наличие и тип фасада, способ открывания, задняя стенка,
цоколь и конструктивные модификаторы — то есть всё, от чего зависит
геометрия, потому что вход правил — именно она.

## 2. Реестр

Реестр — уже существовавший `HardwareLibrary` (`src/domain/hardware/types.ts`,
с PROMPT 1). Второго реестра не заведено. На PROMPT 16 тип
`HardwareItem` из этого файла переименован в `HardwareDefinition`: он
никогда не содержал количества и описывал именно определение, а имя
`HardwareItem` понадобилось производной сущности.

Встроенные определения (`src/hardware/registry.ts`) живут в коде и **в файл
проекта не пишутся**: запись копировала бы справочник в каждый документ, и
переименование позиции в коде оставляло бы старые файлы со старым именем.
`project.hardware.items` дополняет и перекрывает встроенный реестр —
пользовательское определение переживает сериализацию и побеждает.

Каталога производителей нет: определение отвечает на вопрос «что это»,
а не «чьё оно» (`docs/BRAND_INDEPENDENCE_AUDIT.md`).

## 3. Производная позиция

```ts
interface HardwareItem {
  id: string;              // hw:<правило>/<источник>/<определение>
  definitionId: HardwareId;
  kind: HardwareKind;
  unit: HardwareUnit;
  quantity: number;        // целое, ≥ 0
  sourcePartId?: PartId;   // деталь-источник
  sourceNodeId?: NodeId;   // ячейка, полка, ящик, створка
  ruleId: string;          // правило, породившее позицию
  reason: string;          // формируется системой, не пользователем
}
```

Идентификатор выводится из правила и источника, а не из порядкового
номера: позиция остаётся той же при изменении количества и исчезает вместе
со своим источником — та же политика идентичности, что у `Part`
(`docs/DATA_MODEL.md` §5.7).

## 4. Правила

### 4.1 Петли распашных дверей

- **Правило:** количество петель на створку зависит от её высоты по
  ступенчатой таблице порогов.
- **Вход:** створки распашных фасадов (`facade.type === 'hinged'`,
  `leaf.hingeSide !== 'none'`) и высоты уже построенных деталей роли
  `facade`.
- **Формула:** `hingeCountForHeight(height, HINGE_COUNT_TABLE)` — первый
  порог, в который укладывается высота. `HINGE_COUNT_TABLE` **пуста**.
- **Результат:** позиций нет; предупреждение с числом створок и их
  высотами.
- **Источник:** `T-DOOR-05` — «Пороги количества петель по высоте фасада:
  не задано».
- **Тесты:** `tests/unit/hardware/engine.test.ts` Test 1–4, 6.
- **Статус:** `NEEDS_CONFIRMATION`.

Реализован интерфейс правила, а не догадка: заполнение таблицы — всё, что
нужно, чтобы правило заработало; алгоритм при этом не меняется (ветка
расчёта существует и покрыта тестом Test 4 на подставной таблице).

### 4.2 Крепёж петель

- **Правило:** крепёж петли — отдельная позиция спецификации.
- **Вход:** створки, которым нужны петли.
- **Формула:** `количество петель × точек крепления на петлю`.
- **Результат:** позиций нет; предупреждение с обеими недостающими
  величинами.
- **Источник:** `T-DOOR-05` (число петель) и `T-HW-03` (число точек
  крепления).
- **Тесты:** Test 5.
- **Статус:** `NEEDS_CONFIRMATION`.

### 4.3 Направляющие ящиков

- **Правило:** комплект направляющих ставится по обеим сторонам короба.
- **Вход:** все ящики изделия (`LeafFill.kind === 'drawers'`) и тип
  направляющей каждого (`drawer.slide.type`).
- **Формула:** `slidesPerDrawer(type)` — 2 для всех четырёх известных
  типов, потому что все они парные. Число живёт в одной функции, а не
  константой в правиле: непарный тип (центральная подвесная) поменяет
  только её.
- **Результат:** по позиции на ящик, `unit: pcs`, источник — id ящика.
- **Источник:** конструкция самой направляющей; модель и длина —
  `T-DRW-01`, в позицию не входят.
- **Тесты:** Test 7–9 и «каждая позиция ссылается на конкретный ящик».
- **Статус:** `AMBIGUOUS` (количество считается, артикул — нет).

### 4.4 Полкодержатели

- **Правило:** съёмная полка лежит на опорах по углам; стационарная
  держателей не требует.
- **Вход:** детали роли `shelf-adjustable`. Детали `shelf-fixed`
  исключены — им крепёж «на всякий случай» не добавляется.
- **Формула:** `supportsPerShelf()` = 4 (углы прямоугольной пласти).
- **Результат:** по позиции на полку, источник — id детали полки.
- **Источник:** геометрия детали; сама схема опирания (держатель, шкант,
  планка) — `T-SHF-02`.
- **Тесты:** Test 10–12.
- **Статус:** `AMBIGUOUS`.

### 4.5 Крепёж задней стенки

- **Правило:** крепёж ставится по периметру стенки с постоянным шагом.
- **Вход:** детали роли `back` (одна или по одной на секцию), их периметры
  и способ монтажа.
- **Формула:** `ceil(периметр / шаг)`, шаг — `BACK_WALL_FASTENER_SPACING`,
  **не задан**.
- **Результат:** позиций нет; предупреждение с числом сегментов, суммарным
  периметром и способом монтажа.
- **Источник:** `T-HW-03`. Расстояние между креплениями не придумывается.
- **Тесты:** Test 13–14.
- **Статус:** `NEEDS_CONFIRMATION`.

### 4.6 Крепёж корпуса

- **Правило:** крепёж ставится в стыках «вертикаль — горизонталь».
- **Вход:** `findCarcassJoints(parts)` — стыки боковин и перегородок с
  горизонтами (крышка, дно, стационарная полка). Список стыков геометрия
  знает точно.
- **Формула:** `стыков × крепежа на стык`, второе — не задано.
- **Результат:** позиций нет; предупреждение с числом найденных стыков.
- **Источник:** `T-HW-03`.
- **Тесты:** Test 15.
- **Статус:** `NEEDS_CONFIRMATION`.

### 4.7 Ручки

- **Правило:** одна ручка на фасад со способом открывания «ручка».
- **Вход:** уже построенные детали роли `handle` (PROMPT 12). Считается по
  деталям, а не по конфигурации: деталь уже прошла проверки движка, и это
  ровно один источник количества вместо двух.
- **Формула:** мощность множества деталей роли `handle`.
- **Результат:** по позиции на ручку, источник — id детали и ячейки.
- **Источник:** модель `OpeningSystem` — у фасада ровно один способ
  открывания.
- **Тесты:** Test 16, 18.
- **Статус:** `IMPLEMENTED`.

### 4.8 Крепёж ручек

- **Правило:** крепёж ручки — отдельная позиция.
- **Вход:** детали роли `handle`.
- **Формула:** `ручек × точек крепления на ручку` — второе зависит от типа
  ручки и не подтверждено.
- **Результат:** позиций нет; предупреждение с числом ручек.
- **Источник:** `T-HW-08`.
- **Тесты:** Test 16 («крепёж ручки — отдельное правило»).
- **Статус:** `NEEDS_CONFIRMATION`.

### 4.9 Push-to-open

- **Правило:** один механизм на фасад со способом открывания
  «push-to-open».
- **Вход:** детали роли `push-to-open`.
- **Формула:** мощность множества этих деталей.
- **Результат:** по позиции на механизм.
- **Источник:** модель `OpeningSystem`; тип механизма и точка установки —
  `T-HW-04`/`T-HW-07`, в позицию не входят.
- **Тесты:** Test 17.
- **Статус:** `IMPLEMENTED`.

**Двойного учёта нет.** Push-to-open существует и как конфигурация фасада,
и как деталь, но позиция спецификации порождается только одним путём — от
детали. Тест 17 фиксирует, что push-to-open не создаёт ручки, а тест 18 —
что ручка не создаёт второй позиции из конфигурации.

## 5. Движок

`calculateHardware(project, options?)` — единственная точка входа
(`src/hardware/engine.ts`). Функция чистая и детерминированная: не читает
часы, не генерирует случайных значений, не обращается к React и DOM —
граница проверена тестом `tests/unit/architecture/boundaries.test.ts`.

Порядок работы: нормализованная модель → геометрия (готовая передаётся
через `options.geometry`, иначе строится здесь) → детали и Content →
правила → позиции → проверки → агрегация.

**Аварийная остановка.** Изделие, геометрия которого содержит ошибку,
фурнитуры не получает: считать количество по деталям, которые не удалось
построить, значит выдать число, не соответствующее ничему.

## 6. Проверки

| Код | Что ловит |
| --- | --- |
| `HARDWARE_UNKNOWN_DEFINITION` | ссылка на определение, которого нет в реестре |
| `HARDWARE_INCOMPATIBLE_DEFINITION` | категория или единица позиции не совпадает с определением |
| `HARDWARE_QUANTITY_NOT_INTEGER` | дробное количество |
| `HARDWARE_QUANTITY_NEGATIVE` | отрицательное количество |
| `HARDWARE_WITHOUT_SOURCE` | позиция не привязана ни к детали, ни к узлу |
| `HARDWARE_SOURCE_NOT_FOUND` | источник не существует (в том числе удалённый Content) |
| `HARDWARE_DUPLICATE_ID` | одинаковый идентификатор у двух позиций |
| `HARDWARE_SKIPPED_BROKEN_GEOMETRY` | изделие пропущено из-за ошибки геометрии |

Позиция, не прошедшая проверку, в спецификацию не попадает: сложить
дробное количество в строку значило бы разнести ошибку по всему итогу, где
её уже не найти.

## 7. Хранение

`HardwareBOM` **не сохраняется** (§22). Это производная величина, как и
список деталей: сохранённая спецификация разошлась бы с моделью после
первого же изменения габарита. Тесты `persistence.test.ts` фиксируют, что
в файле проекта нет ни количеств, ни встроенного реестра, и что расчёт до
и после сохранения совпадает побайтово.

## 8. Чего здесь нет

Цен, поставщиков, каталогов брендов, складов, закупок, заказов, карты
раскроя, карты присадки, экспорта и производственного интерфейса. Позиция
`calculated / override / effective` архитектурно возможна (правило
объявляет `status`, движок принимает подменный набор правил), но ручного
переопределения количества в интерфейсе нет: оно немедленно стало бы вторым
источником истины.

Отдельной системы фурнитуры «на каждый тип Content» тоже нет: правило —
один интерфейс `HardwareRule`, и полки, ящики, двери и крепёж проходят
через один и тот же движок.
