# Публикация на GitHub Pages

PROMPT 40. Как готовое приложение попадает в production и как вернуть
предыдущую версию, если что-то пошло не так.

**https://artemu1453.github.io/FurnityreBuilder/**

## Required CI

Выкладка структурно не может обогнать проверки. Один workflow, три задачи
по цепочке `needs`:

```
verify  ─→  build-pages  ─→  deploy  ─→  smoke
```

| Задача | Что делает | Блокирует |
| --- | --- | --- |
| `verify` | одиннадцать ворот качества | публикацию |
| `build-pages` | сборка под фактический базовый путь, `check:release` | публикацию |
| `deploy` | публикация артефакта, отдаёт адрес | — |
| `smoke` | проверка ОПУБЛИКОВАННОГО по этому адресу | прогон краснеет |

`needs` не запускает задачу, пока предыдущая не завершилась успехом.
Значит любая красная проверка из `verify` — линтер, типы, тесты, сборка,
самостоятельность, размер чанка, готовность пакета, оба прогона E2E —
останавливает публикацию, не доводя до неё.

Список ворот целиком — `docs/CI_QUALITY_GATES.md`.

**Так было не всегда.** До PROMPT 40 публикация жила отдельным workflow и
запускалась по тому же push, что и CI, — то есть параллельно. Коммит с
красными воротами попал бы в production, и ничто бы этому не помешало.

Связка через `workflow_run` рассматривалась и отвергнута: она берёт
голову ветки, а голова к моменту запуска может уже уехать вперёд, и
выложится не тот коммит, который проверяли. Цепочка `needs` внутри одного
прогона такой возможности не оставляет.

## Build

```bash
APP_BASE=<base_path из configure-pages> npm run build
```

Базовый путь не пишется руками. Его отдаёт `actions/configure-pages`, и
он же меняется сам при подключении собственного домена: страницы проекта
живут в подкаталоге `/FurnityreBuilder/`, домен сделал бы базой корень.

Собранное складывается в `dist/` — пять шагов подряд: типы, Vite,
манифест, service worker, `404.html` (`docs/DEPLOYMENT.md` §1).

После сборки выполняется `npm run check:release`: он сверяет базовый путь
между разметкой, манифестом и service worker'ом. Разойдясь, они дают
белый экран без единого сообщения, и выкладка — последнее место, где
такую сборку ещё можно не отдать людям.

## Pages

Официальные действия GitHub, актуальные версии, никаких сторонних:

| Действие | Зачем |
| --- | --- |
| `actions/configure-pages@v5` | адрес и базовый путь |
| `actions/upload-pages-artifact@v3` | выгрузка `dist/` |
| `actions/deploy-pages@v4` | собственно публикация |

Стратегия — **GitHub Actions** как источник (не ветка `gh-pages`):
публикуется артефакт сборки, а не коммит с собранными файлами. В
репозитории нет ни `dist/`, ни ветки с артефактами.

Что попадает в публикацию: только содержимое `dist/`. Ни исходников, ни
`node_modules`, ни тестов, ни конфигурации разработки.

### Права

Выданы точечно, по задачам, а не всему workflow:

| Задача | Права |
| --- | --- |
| `verify` | `contents: read` |
| `build-pages` | `contents: read`, `pages: write`, `id-token: write` |
| `deploy` | `pages: write`, `id-token: write` |

`contents: write` не выдаётся никому: workflow ничего не коммитит.

### Одновременность

У задачи `deploy` своя группа `pages`, начатая публикация не обрывается —
оборванная на середине оставила бы людям половину сборки. Очередь при
этом не копится: GitHub держит в ней только самый свежий прогон, поэтому
старая версия не может встать поверх новой.

## Rollback

Отдельной инфраструктуры выпусков не заводится. Откат — это обычный
коммит:

```bash
git revert <плохой-коммит>
git push origin claude/furniture-designer-audit-cjvvuf
```

Дальше всё идёт само:

```
revert
  ↓
verify — те же ворота
  ↓
build-pages
  ↓
deploy
  ↓
предыдущая рабочая версия снова в production
```

Три вещи, о которых стоит знать заранее:

1. **Откат проходит те же ворота.** Если revert ломает проверки,
   публикации не будет — и это правильно: чинить надо вперёд, а не
   выкладывать вслепую.
2. **Проекты пользователей не затрагиваются.** Код живёт в Cache Storage,
   проекты — в IndexedDB, и выкладка их не касается
   (`docs/PWA_OFFLINE.md`).
3. **У открытых вкладок обновление не мгновенное.** Service worker
   предложит новую версию кнопкой; до нажатия человек продолжает
   работать на прежней. Это относится и к откату: он доходит тем же
   путём, а не подменяет код под руками.

Быстрее отката работает только `workflow_dispatch`: запустить прогон
вручную на нужном коммите. Но публикуется при этом голова ветки, поэтому
для настоящего возврата версии revert надёжнее.

## Проверка после выкладки — автоматическая

Успешная выкладка не доказывает, что приложение работает. Поэтому за
`deploy` идёт задача `smoke`: она открывает **опубликованный** адрес и
проверяет, что оболочка не пустая, критические файлы доехали, интерфейс
на месте, одно настоящее действие проходит, а консоль и сеть молчат.

Адрес берётся из вывода самой выкладки, а не из конфигурации. Готовность
определяется по отпечатку сборки — задача ждёт, пока по адресу окажется
именно та версия, которую собрали, и не дольше пяти минут.

Падение `smoke` означает, что выложенная версия сломана у пользователя,
даже если ворота были зелёными. При падении выгружаются отчёт, трассы и
снимки экрана.

Подробно: `docs/PRODUCTION_SMOKE_TESTING.md`.
