## Модель, которая теперь одна

**«В этом отделении N полок.»**

| Вопрос | Где на него отвечают | Переходы |
| --- | --- | --- |
| «пусть здесь будут полки» — ДЕЙСТВИЕ | кнопка у изделия «Добавить полки»; шаг 6 «Наполнение» | 0 → N |
| «сколько их» — ПАРАМЕТР | шаг 5 «Полки», поле «Полок в выбранном отделении» | N → M, N → 0 |
| «сколько их сейчас» — СОСТОЯНИЕ | инспектор и сводка шага «Ячейки», строка «Наполнение» | — |

Источник истины один и он в домене: количество — это длина списка
`fill.shelves`. Второго счётчика в интерфейсе не заведено; всё, что
показывается, читается из модели (`shelfCountOf`).

## Производственные последствия (§10)

Проверены не рассуждением, а прогоном конвейера целиком —
`tests/unit/integration/shelf-production.test.ts`:

| Проверка | Результат |
| --- | --- |
| Оба входа дают одно состояние модели | совпадает: вид наполнения и количество |
| Геометрия полок: размеры, положение, раскрой, кромка | совпадает деталь в деталь |
| Деталировка, кромка, раскрой, фурнитура, присадка | совпадают целиком |
| N полок → N деталей в раскрое | 1, 2, 5 — сходится |
| N → 0 | производственный результат равен результату до полок |
| Правка числа на отделении с ящиком | ничего не меняется; фасады ящиков на месте |

## Отмена и повтор (§14)

Архитектура истории **не менялась**: `SetFill` и до FR-08 писался одним
шагом. Проверено сквозным сценарием: 0 → 1 кнопкой, 1 → 4 полем, две
отмены дают `1` и `0`, два повтора — `1` и `4`. Секции при этом не
затрагиваются.
