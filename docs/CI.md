# CI

Что запускается на каждый push и pull request, в каком порядке и почему
именно в таком.

---

## 1. WORKFLOW

`.github/workflows/ci.yml`, одна задача `verify` на `ubuntu-latest`,
Node 22, кэш npm, установка через `npm ci`.

```
npm ci
  ↓
check:assumptions   неподтверждённые правила зарегистрированы
lint                границы слоёв, чистые слои, стиль
typecheck           tsc --noEmit
test                1702 модульных и property-проверки
build               tsc + vite build
check:brand         ни одного внешнего запроса
check:bundle        главный чанк в пределах порога
  ↓
playwright install chromium
test:e2e            123 сценария в двух проектах
```

Порядок намеренный: сначала дешёвые проверки, затем сборка, затем
проверка собранного артефакта в браузере. Ошибка типа не должна ждать
пяти минут E2E.

---

## 2. ПОЧЕМУ ИМЕННО ЭТИ ШАГИ

| Шаг                 | Что ловит                                                     |
| ------------------- | ------------------------------------------------------------- |
| `check:assumptions` | правило, придуманное без записи в `UNKNOWNS.json`             |
| `lint`              | импорт через границу слоя, React в чистом слое                |
| `typecheck`         | всё, что `vitest` не проверяет: он не типизирует тесты        |
| `test`              | инварианты, отмену, детерминированность, регрессию количеств  |
| `build`             | то, что собирается только в production (мёртвые ветки, чанки) |
| `check:brand`       | внешний запрос или упоминание референса                       |
| `check:bundle`      | библиотека, въехавшая в загрузку по умолчанию                 |
| `test:e2e`          | связки между разделами и настоящий браузер                    |

`typecheck` стоит отдельным шагом не для красоты: `vitest` выполняет
тесты без проверки типов, и тест с неверной формой команды проходит
зелёным. На PROMPT 30 это поймало четыре ошибки в новых тестах.

---

## 3. ДЕТЕРМИНИРОВАННОСТЬ

CI не зависит от сети сверх npm и Playwright: приложение не делает
внешних запросов (`check:brand` это проверяет), тестовые данные
собираются последовательными идентификаторами и фиксированным временем,
случайности нет ни в одном расчёте.

Внешних сервисов, отчётов о покрытии и публикаций артефактов в
workflow нет. Каждый добавленный сервис — новая причина красного CI, не
связанная с кодом.

## 4. ЛОКАЛЬНО

```bash
npm run verify   # всё, кроме E2E: тот же порядок, что в CI

PLAYWRIGHT_CHROMIUM_PATH=... npx playwright test --project=chromium
PLAYWRIGHT_CHROMIUM_PATH=... npx playwright test --project=chromium-dev
```

Два проекта E2E запускаются **раздельно**: совместный запуск поднимает
оба сервера и роняет соединение (`E2E_SCENARIOS.md` §1). В CI это
скрыто внутри `npm run test:e2e`, где Playwright управляет серверами сам.

---

## 5. ЧЕГО В CI НЕТ И ПОЧЕМУ

| Чего нет           | Почему                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| Отчёта о покрытии  | процент покрытия не отличает проверенный инвариант от вызванной строки                                                    |
| Визуальных снимков | инфраструктуры нет; расхождение в один пиксель красит CI чаще, чем находит дефект                                         |
| Матрицы браузеров  | приложение работает на WebGL 2 и Pointer Events; вторая среда — вторая причина ложных падений без второго класса дефектов |
