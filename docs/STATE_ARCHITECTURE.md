# Архитектура состояния

Реализация: `src/state/`, `src/interaction/`.
Проверки: `tests/unit/state/`, `tests/unit/interaction/`.

---

## 1. ТРИ УРОВНЯ

| Уровень | Что хранит | Где живёт | Undo | Сохраняется |
| --- | --- | --- | --- | --- |
| **Документ** | `Project` — вся мебель | `useDocumentStore` | да | да |
| **Сессия** | выделение, наведение, инструмент, вид, панели, viewport, уведомления | `useSessionStore` | нет | нет |
| **Взаимодействие** | текущий жест: точка захвата, смещение, скорость | поля `DragController`, вне стора | нет | нет |

Смешение этих уровней — самая частая причина того, что онлайн-конструктор
«тормозит и странно себя ведёт»: уровень зума попадает в историю, а
перетаскивание дёргает весь домен на каждый кадр.

Разделение введено с первого коммита и проверяется тестом
`tests/unit/state/separation.test.ts`, а не соблюдается на честном слове.

---

## 2. ИСТОЧНИК ИСТИНЫ

**Источник истины — доменная модель `Project` внутри `useDocumentStore`.**

Из этого следует:

- геометрия, деталировка, валидация и экспорт вычисляются из `Project`
  и нигде не хранятся;
- `Part[]` не является состоянием — это производная величина;
- интерфейс не хранит собственных копий размеров: поле ввода читает
  значение из документа и отправляет команду;
- расхождение между схемой и деталировкой невозможно по построению —
  они читают один и тот же результат одного расчёта.

Компонент, заводящий `useState` для мебельного значения, нарушает это
правило. React-состояние допустимо только для того, что действительно
принадлежит экрану.

## 3. КОМАНДЫ

Документ мутируется исключительно через именованные команды
(`src/state/commands.ts`):

```ts
execute({ type: 'SetDimension', furnitureIndex: 0, axis: 'width', value: 1200 });
```

Что это даёт:

- единственная точка записи истории;
- компонент не знает, как устроен проект внутри;
- воспроизведение дефекта по журналу команд;
- новые действия добавляются веткой `switch`, без изменения UI.

Реализованные команды: `SetProjectName`, `SetFurnitureName`, `SetDimension`,
`SetCarcassFlags`, `SplitNode`, `CollapseNode`, `SetChildSize`, `SetFill`,
`SetRoot`, `SetSectionCount`, `SetConstructionScheme`, `SetTolerances`,
`SetEdgeSizingPolicy`, `SetMaterialAssignment`, `UpsertMaterial`,
`RemoveMaterial`.

`SetRoot` (PROMPT 4) заменяет дерево секций изделия целиком заранее
построенным деревом — атомарная альтернатива серии `SplitNode` для
операций вроде «построить равномерную сетку 2×3», где промежуточные
состояния (сетка наполовину построена) не имеют смысла как отдельные шаги
истории. Дерево строится ЧИСТЫМИ функциями домена
(`createSections`/`createUniformGrid`, `src/domain/furniture/sections.ts`)
с id из `IdFactory`, переданной вызывающей стороной — сама команда не
генерирует id, как и остальные команды, работающие со структурой дерева.

`SetSectionCount` (PROMPT 7) меняет число секций верхнего уровня, правя
только хвост списка детей: первые N секций остаются теми же узлами со
своими id, ячейками и полками. Это не оптимизация, а требование к
идентичности (`docs/DATA_MODEL.md` §5.7): до неё число секций меняли через
`SetRoot`, и переход 3 → 4 менял id у всех секций разом, включая те, к
которым пользователь не прикасался — а на id ссылаются выделение,
история, будущий drag и экспорт. Обе команды остались: `SetRoot` — когда
структура строится заново, `SetSectionCount` — когда меняется количество.

`SetChildSize` (переработана на PROMPT 8) меняет размер одной секции, ряда
или колонки — это `SizeSpec` ребёнка деления. Команда одна на все три
случая: чем является ребёнок, определяет ось его родителя, а не тип
команды. Ребёнок адресуется по `childId`; раньше принималась позиция
в массиве, но позиция идентичностью не является — добавление соседней
секции сдвигает индексы, и команда «сделай вторую секцию шириной 500»
после этого попадала бы не в ту секцию.

Запланированные перечислены в константе `PLANNED_COMMANDS` — список
существует в коде, чтобы «пока не реализовано» было видно, а не
подразумевалось.

### Что команды сознательно не делают

`SetDimension` **не округляет и не ограничивает** значение. Команда фиксирует
намерение пользователя как есть; о недопустимости сообщает валидация.
Поле, округляющее ввод на каждом нажатии, «прыгает» под пальцами.

`RemoveMaterial` **не подставляет** другой материал вместо удалённого.
Ссылки остаются битыми, и валидация показывает это явно. Тихая подстановка
изменила бы проект без ведома пользователя.

## 4. НЕИЗМЕНЯЕМОСТЬ

`Project` описан как глубоко `readonly`. Изменения выполняются через Immer:

```ts
const [next, patches, inverse] = produceWithPatches(project, (draft) => {
  applyCommand(draft, command);
});
```

Свойства, которые это даёт:

- **скрытых мутаций нет** — черновик существует только внутри `produceWithPatches`;
- **структурное разделение** — неизменённые поддеревья сохраняют ссылку,
  поэтому мемоизация расчёта работает по `===`, без глубокого сравнения
  (проверено тестом: правка габарита не меняет ссылку на библиотеку материалов);
- **патчи бесплатно** — та же операция даёт дельту для истории и,
  в будущем, для автосохранения.

## 5. ИСТОРИЯ

История хранит **патчи, а не снимки**. Снимок проекта на каждое движение
ползунка — это мегабайты мусора за минуту работы.

```ts
interface HistoryEntry {
  label: string;
  patches: Patch[];
  inverse: Patch[];
  selection: string[];
}
```

Глубина — 200 шагов, дальше кольцевое вытеснение.

Отменяется состояние **домена**, не интерфейса: undo не возвращает прокрутку
панели и уровень зума. Выделение на момент действия сохраняется в записи —
undo без контекста дезориентирует.

### Транзакции и коалесценция

Один жест обязан быть одним шагом отмены. Иначе пользователь жмёт Ctrl+Z
сорок раз, чтобы отменить одно перетаскивание.

```
pointerdown → beginTransaction('Перетаскивание')
pointermove → execute(...)   ← сливается в ту же запись
pointerup   → endTransaction()
Escape      → cancelTransaction()   ← откат по обратным патчам, следа в истории нет
```

Три случая проверены тестами:

- серия из четырёх команд внутри транзакции даёт одну запись, и один undo
  возвращает состояние до жеста;
- отмена жеста восстанавливает базовое состояние и не оставляет записи;
- жест без изменений (нажал и отпустил) не оставляет пустого шага.

## 6. РАЗДЕЛЕНИЕ INTERACTION STATE И DOMAIN STATE

Требование производительности: недопустима цепочка

```
pointermove → полный React render → полный пересчёт геометрии → полный layout
```

Реализованное разделение:

```
pointerdown  → beginTransaction, снимок базы ИЗ ДОМЕНА, setPointerCapture
pointermove  → onMove(frame, base): обновляется только транзиентное
               представление; домен НЕ трогается
pointerup    → onCommit: одна команда → пересчёт → endTransaction
Escape       → onCancel: возврат к базе, cancelTransaction
```

`DragController` хранит транзиентные данные в собственных полях — не в
Zustand и не в React-состоянии. Ни одно движение указателя не вызывает
перерисовку дерева компонентов.

Базовое состояние снимается **из домена**, а не из DOM: измеренная
геометрия элемента зависит от масштаба и анимаций и не является истиной
о мебели.

### Где нужен «живой» пересчёт

Для перетаскивания полки достаточно транзиентного слоя. Для изменения
габарита пользователь должен видеть, как перестраивается изделие целиком.
Там применяется предпросмотр не чаще одного раза на кадр, **вне истории**,
с фиксацией одной командой на `pointerup`. Механизм заложен разделением
уровней; сам предпросмотр — этап 08 плана.

## 7. ЧТО ГДЕ ЛЕЖИТ

| Данные | Уровень | Почему |
| --- | --- | --- |
| Ширина ячейки | документ | свойство мебели, попадает в деталировку |
| Наполнение ячейки | документ | свойство мебели |
| Материал детали | документ | свойство мебели |
| Выделенная ячейка | сессия | не сохраняется, не отменяется |
| Наведение | сессия | транзиентно |
| Масштаб и панорама | сессия | свойство просмотра, не изделия |
| Открытая панель | сессия | свойство экрана |
| Признак непостоянного хранилища | сессия | состояние среды, не проекта |
| Смещение при перетаскивании | взаимодействие | живёт до `pointerup` |
| Скорость указателя | взаимодействие | нужна только для передачи в пружину |

Проверено тестом: сериализованный проект не содержит подстрок
`selected`, `viewport`, `hovered`.
