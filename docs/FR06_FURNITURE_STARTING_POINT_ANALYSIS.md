## Current root furniture model

```ts
export interface Furniture {
  readonly id: FurnitureId;
  readonly name: string;
  readonly kind: FurnitureKind;
  readonly dimensions: Dimensions;      // width, height, depth, panelThickness
  readonly carcass: CarcassSpec;        // боковины, крышка, дно, задняя стенка, цоколь
  readonly root: SectionNode;           // дерево: лист или деление
  readonly facades: readonly FacadeGroup[];
  readonly placement?: Placement;
}
```

Изделие — это **габарит + короб + дерево внутреннего деления + фасады**.
Ничего, что делало бы шкаф шкафом, а комод комодом, в этой структуре
нет.

## Actual supported variants

Тип видов существует:

```ts
/** Влияет только на пресеты и подсказки. Геометрия для всех видов одна. */
export type FurnitureKind = 'wardrobe' | 'shelving' | 'cabinet' | 'dresser';
```

**Где он используется — полный список по репозиторию:**

| Место | Что делает |
| --- | --- |
| `domain/furniture/types.ts:7` | объявление типа |
| `domain/furniture/types.ts:524` | поле `Furniture.kind` |
| `domain/furniture/defaults.ts:358` | `kind: overrides.kind ?? 'wardrobe'` |
| `persistence/schema.ts:235` | `z.enum([...])` — сохраняется в файл |
| `workflow/fingerprint.ts:34` | входит в отпечаток для обнаружения изменений |

**И это всё.** Ни геометрия, ни фурнитура, ни присадка, ни раскрой, ни
BOM, ни экспорт, ни один компонент интерфейса значение не читают и по
нему не ветвятся. `fingerprint` не исключение: ему нужно заметить
изменение поля, а не понять его смысл.

Обещание в комментарии — «влияет на пресеты и подсказки» — **не
выполнено**: ни одного пресета и ни одной подсказки, зависящей от вида,
в проекте нет. Значение всегда `'wardrobe'`, потому что его никто не
меняет: органа управления для него не существует.

### Ответ на вопрос §2

| Вид мебели | Поддержан как отдельный доменный тип | Собирается из универсальной структуры |
| --- | --- | --- |
| Шкаф (wardrobe) | **нет** | **да** |
| Стеллаж (shelving) | **нет** | **да** |
| Тумба (cabinet) | **нет** | **да** |
| Комод (dresser) | **нет** | **да** — фасадами ящиков |
| Открытое хранение | **нет** | **да** — короб без фасадов |
| Прочее корпусное | **нет** | **да**, пока это короб с делением |

Четыре значения `FurnitureKind` — **ярлык без поведения**. Отличить по
ним изделия невозможно, потому что различия нигде не выражены.

## Universal construction capabilities

Что действительно умеет универсальная структура
(`PRODUCT_CAPABILITY_TRUTH.md`):

* габарит W/H/D и толщина плиты;
* короб: боковины, крышка, дно, задняя стенка, цоколь, царги;
* вертикальное деление на секции перегородками;
* ряды и колонки внутри отделения;
* наполнение отделения: полки, ящики;
* фасады: распашные двери, фасады ящиков, сторона петель, накладной и
  вкладной, ручка, push-to-open;
* надстройки: столешница, антресоль, свесы, фальшпанели, навеска;
* материалы по ролям, кромка;
* производство: деталировка, чертежи, раскрой, фурнитура, спецификация.

Разница между «шкафом» и «комодом» в этой системе — **это разница в
наполнении и фасадах, а не в типе объекта**.

## Existing terminology

| Слово | Где | Что означает в модели |
| --- | --- | --- |
| Изделие | имя по умолчанию «Изделие 1», инспектор | корневой `Furniture` |
| Корпус | шаг 2, `CarcassSpec` | боковины, крышка, дно, задняя стенка, цоколь |
| Секция | шаг 3 | ребёнок верхнего деления по X |
| Отделение / ячейка | шаги 4–7 | лист дерева — пространство |
| Наполнение | шаг 6 | `LeafFill`: пусто, полки, ящики |
| Фасад | шаг 7 | `FacadeGroup` |

Слова «шкаф», «тумба», «комод», «стеллаж» в интерфейсе **не
употребляются вовсе** — и это честно: модель их не различает.

## Current first user instruction

Первого указания нет.

При открытии: `h1` — «Новый проект», под ним габарит `1000 × 2000 ×
500 мм`, панель «Размеры» с подписью «Габарит изделия и толщина плиты» и
четыре поля. Поиск по видимому тексту не даёт ни одного вхождения слов
«шкаф», «тумба», «комод», «кухня», «шаблон», «тип изделия», «с чего
начать», «начните».

## Where ambiguity appears

**Не в том, что нет выбора типа.** Выбирать нечего — типов нет.

Двусмысленность в другом: человек видит **готовый объект из пяти
деталей** и не понимает трёх вещей:

1. **Что это такое.** «Изделие 1» ничего не сообщает. Это заготовка? Чей-то
   проект? Пример?
2. **Что из этого получится.** Что вообще можно построить — шкаф?
   стеллаж? только полку?
3. **Что делать после размеров.** Одиннадцать шагов есть, но какой из
   них следующий по смыслу, а не по номеру, — не сказано.

**Понятен ли этот объект как отправная точка?**

Сам объект — да: это пустой короб. **Но нигде не сказано, что это пустой
короб** и что дальше его делят и наполняют. Отсюда и вопрос «что я
вообще строю».

## Решение

### Чем является приложение (§3)

**Вариант B — универсальная система построения корпусной мебели.**

Не конфигуратор нескольких продуктов: продуктов в модели нет. Один
объект — короб с делением, — из которого человек собирает то, что ему
нужно.

### Стартовое понятие (§4)

**«Пустой корпус».** Слово взято из модели, а не придумано: так
называется `CarcassSpec`, так подписан шаг 2 «Корпус», и ровно это
описывает `createDefaultFurniture` — «Пустой корпус заданных габаритов:
каркас и одна нераздёленная секция».

### Выбора типа мебели НЕ появится (§6)

Добавлять «Шкаф / Стеллаж / Тумба / Комод» было бы обещанием, за
которым ничего нет: все четыре дают **побитово одинаковое** изделие.
Человек, выбравший «Комод», получил бы шкаф и решил, что приложение
сломано.

### Пресетов НЕ появится (§7)

Проверено по пяти условиям §7:

| Условие | Выполнено |
| --- | --- |
| A. Модель может их выразить | **нет** — архитектуры пресетов не существует; `kind` ни на что не влияет |
| B. Не вводят выдуманного поведения | не проверялось: отпало на A |
| C. Улучшают первую сборку | вероятно, но это гипотеза |
| D. Отличимы от ручной сборки | нечем отличать |
| E. Расчёт производства не меняется | да, но это не довод «за» |

Условие A не выполнено, поэтому пресеты в этом PROMPT не создаются.
Отдельная запись об этом — в `PRODUCT_GAP_REGISTER.md`.

### Что вместо этого

Объяснение вместо ветвления (§6, §10): короткая, непостоянная по весу и
ничего не блокирующая подпись, которая отвечает на три вопроса выше и
стоит рядом с первым действием, а не вместо него.
